## 1. 工作区事实

- 本仓库包含共享若依平台和四个相互独立的业务项目：面试项目、智能选品项目、智能体桌面端项目、生产排产项目。
- 四个活跃工程根目录为 `ruoyi-backend/`、`frontend/`、`miniapp/` 和 `python/`。`ruoyi-backend/pom.xml` 是共享若依 Java / Maven 聚合入口，`ruoyi-admin` 装配各业务 HTTP 模块；上游基线位于各工程的 `_reference/`，只供对照。
- 面试项目主要使用 `ruoyi-backend/ruoyi-interview/`、`frontend/portal-web/`、`miniapp/interview-mobile/` 和相应公共契约。
- 智能选品项目使用 `ruoyi-backend/ruoyi-fashion/`、`python/fashion-ai-runtime/`、`contracts/fashion/`，并通过 `frontend/admin-web/` 提供管理界面。
- 智能体桌面端项目使用 `ruoyi-backend/ruoyi-aden/`、`frontend/desktop/aden-desktop/`、`python/aden-agent-runtime/`、`python/aden-runner/` 和对应原型。
- 生产排产项目使用 `ruoyi-backend/aps/` 中的 Java 模块，求解 Worker 保持独立进程；需求、设计与 `prototype/production-workbench-v2/` 的状态以项目控制页为准，不得从原型或模块存在推断生产实现已完成。
- `contracts/` 保存公共 API / 事件契约；具体 Feature 的候选契约可随 Feature 资料包保存。
- 工程目录的旧新映射、上游基线保留和恢复方法见[目录映射与恢复说明](文档/若依框架/工程按技术类型归档架构.md#3-旧新路径与恢复)。迁移过渡期保留的旧根目录只作为运行中进程的原路径，不作为第二套活跃工程；`backend/` 与 `apps/` 是更早的旧路径。
- 当前产品、实现、验证和发布状态必须从对应事实源读取，不能从文件数量、旧阶段或历史报告推断。
- 2026-10-01 用户明确纠正：四项目并行隔离的是运行通道，不隔离数据库。各通道沿用所属项目原有数据库、账号、密钥与业务数据；不得因独立端口或对话新建、克隆或初始化另一套数据库。实际连接及启动限制唯一维护在[四项目并行开发启动指南](文档/若依框架/四项目并行开发启动指南.md)，跨项目业务数据所有权边界继续保留。

## 2. 开始工作时的加载顺序

1. 采用用户级 `AGENTS.md`、本文件及适用目录规则，按需查[项目规范索引](文档/规范/README.md)；上下文已有且仍有效的规则不重复回读。
2. 需要定位业务资料时，从[工作区文档总览](文档/README.md)选择若依框架或明确业务项目；普通问答和简单操作不固定遍历全部入口。
3. 进入对应项目控制页，再按任务读取产品、Feature、架构、决策、验证或归档资料。
4. 修改具体功能时读取该 Feature 控制页及其规格、设计、任务和验证；不把其他项目或跨功能旧计划当作任务源。
5. 各级 `归档/` 默认不加载，只在追溯历史决定、旧路径或迁移证据时按需读取。

## 3. 文档与目录规则

- 文档根目录固定为 `文档/`。共享若依资料位于 `文档/若依框架/`，业务资料只位于 `文档/项目/面试项目/`、`智能选品项目/`、`智能体桌面端项目/` 或 `生产排产项目/`。
- 文档目录、事实唯一归属、命名、元数据、归档和链接要求以[文档组织规范](文档/规范/文档组织规范.md)为项目级事实源。
- `文档/` 内项目自有目录和人读文件使用清晰中文名称。工具约定的 `AGENTS.md`、`README.md`、`LICENSE*`，OpenAPI / AsyncAPI / JSON 等机器文件，以及 Feature ID、API、AI、Agent、RuoYi 等必要稳定标识可保留，但必须有清晰中文语义。
- 业务工程、源码、配置、第三方上游和可运行原型目录不因文档中文命名规则而改名；需要改这些路径时另做工程迁移和运行验证。
- 批量改名必须同步修正所有入链，保留旧路径到新路径映射、迁移前原文、语义说明和可执行恢复方法，并通过文档链接检查。
- 每个 L2/L3 功能只在所属项目的 `功能/<FEAT-ID>-中文语义/` 维护一个控制页和一个任务事实源。
- 根 `文档/开发记录/` 只放跨项目迁移；项目实现记录放所属项目。当前与归档、业务项目与若依依赖不得混写成同一事实。
- 不新建第二套按阶段、Agent、窗口或波次拆分的重复状态文档；新的项目文档不得散落在仓库根目录。

## 4. 实施与数据边界

- 默认沿用现有 RuoYi、Vue 3、TypeScript、Spring Boot 和模块边界，优先修改业务工程而非上游基线。
- 面试项目业务事实由 PostgreSQL 统一承载，包括题库、面试、语音元数据、评测、学习、计费和业务事件。RuoYi 平台账号、认证、角色、菜单和权限继续由 MySQL 承载；两侧只通过稳定用户标识关联，不建立跨库外键、跨库 `JOIN` 或跨库事务。
- 其他独立业务项目默认使用 MySQL 作为唯一权威业务数据库；只有经该项目设计明确说明并获批准时才采用 PostgreSQL 或增加第二种业务数据库。
- 智能体桌面端以 RuoYi 为唯一中心控制面；Python、Runner 和 Electron 不持有第二套任务、审批或审计真相。
- 智能体桌面端的日常启动、用户体验、联机检查和页面验收必须使用用户本机已安装的 `Aden Local Test.exe`；当前入口为 `C:\Users\admin\AppData\Local\Programs\Aden Local Test\Aden Local Test.exe`。不得以 `npm run dev`、源码 Electron 入口或工作区 `out/` 启动窗口替代本机安装版；构建和技术测试仍在源码工程完成。启动前核对实际安装路径、版本及安装目录 `resources/app/local-test.json` 的中心服务地址。
- 智能体桌面端源码修改后，必须完成对应构建并同步到上述本机安装版，再从安装版启动检查实际效果。桌面 `out/` 默认使用 `frontend/desktop/aden-desktop` 的 `npm run sync:local`（`scripts/sync-local-test.ps1`）；同步前退出已确认属于目标安装目录的进程，保留旧产物备份，同步后核对关键文件哈希并重新打开安装版。仅构建成功、修改源码或改了工作区 `out/` 不算交付完成；构建、同步或安装版启动失败应记录实际阻塞。扩展、Native Host、安装器或后端变更按各自分发范围更新和验证，不能用仅同步桌面 `out/` 冒充全部组件已更新。不得覆盖其他安装目录、真实配置或其他项目进程。
- 智能选品的 Java / MySQL 边界持有正式商品、库存、价格、报价和写入；Python Runtime 不直接拥有业务数据库或正式副作用。
- 配置、账号、Provider、数据库、对象存储、桌面控制和语音链路按真实环境影响判断授权；不得把本地 Mock、原型或文件存在说成真实联机。
- 面试本机日常通道必须启用已批准的语音识别、题目朗读和音频写入，沿用原库托管密钥与已验证配置；不得因为通道隔离默认关闭这些能力。启动前核对配置与目录，缺项明确停止并报告。离线测试或故障演练若需关闭，单独说明场景和恢复条件，不覆盖日常通道。具体操作和证据见[启动指南](文档/若依框架/四项目并行开发启动指南.md)。
- 无明确 Git 授权时只保留工作区修改，不执行暂存、提交、推送、分支、标签或发布。

## 5. 最低检查

- 文档修改：检查中文命名、模块归属、相对链接、当前与归档边界、唯一事实源、状态语义、迁移恢复和未提交内容保护。
- Java 修改：运行与改动模块匹配的 Maven 定向测试或说明未运行原因。
- Vue / TypeScript 修改：运行对应工程的类型检查、测试或构建；涉及页面行为时按浏览器专题执行验证。
- 契约或数据库变化：检查消费者、兼容、迁移顺序、失败恢复和证据记录。
- 智能选品方案池请用户手工验收前，先展示并保存该 Feature 的逐项手工清单，再打开可访问的前端。该清单以 `文档/项目/智能选品项目/功能/FEAT-FASHION-001-服装智能选品生产首版/证据/` 下当前轮次的手工验收文件为入口；每个页面场景保存实际截图并回读，缺少必需截图不得记通过，按执行和阻塞事实记未执行或受阻，已观察到的失败保留未通过。Java、MySQL 和接口技术验证单独记录，不计入手工验收通过数；通用判定以用户级 `specs/core/evidence.md` 为准。

## 6. 四项目验收执行摘要

面试、智能选品、智能体桌面端、生产排产均采用用户级 `C:\Users\admin\.codex\specs\core\evidence.md` 的现行规则；以下只声明项目落点，不另维护通用正文：

1. 每项功能在所属 `文档/项目/<项目>/功能/<FEAT-ID>-中文语义/` 的已有文档和验收记录中维护要求版本、验收前提、步骤、预期和核对方法；内部沿用固定标识及历史对应，用户可见内容按中文业务名称与普通顺序号展示。页面、字段、规则出处和证据位置写在对应业务点，执行后记录实际情况及不足的业务影响。已有文档引用具体章节/条目及版本，关键要求不明只阻塞相关项。各对话沿用同一功能记录，先展示并保存清单，不照抄程序输出作为正确答案。
2. 技术验证、页面或业务验收、用户接受决定分别记录和计数。Java/前端构建、接口或 Worker 检查成功不能代替功能通过；用户决定单列范围、版本与明确确认依据。
3. 实际不符预期记未通过；缺环境或必需截图导致无法完成判定记受阻；未执行且无已确认阻塞记未执行。已观察到失败的项保留未通过，并单列截图缺口。
4. 原失败与修复后的复验证据均保存到该 Feature 的证据目录；已通过项保留版本和证据基线，仅重验本次受影响项及未通过项。沿用项注明原版本、证据和影响判断，换对话或轮次不从头清零。
5. 每轮在该 Feature 的既有轮次证据目录交付按中文业务点组织的 `verification-report.html`，区分本轮执行与沿用基线。只有用户本人或经用户明确指定的业务负责人接受所列范围和版本才记“用户接受”；格式例外和真实阻塞按用户级验收正文处理。
