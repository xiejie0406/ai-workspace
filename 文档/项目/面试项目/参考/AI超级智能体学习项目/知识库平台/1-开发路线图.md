# KnowFlow Agent 分阶段开发路线图

> 适用项目：KnowFlow Agent 企业知识库智能体平台  
> 当前版本：v1.0  
> 更新时间：2026-04-29  
> 文档目的：明确开发顺序、阶段产物、阶段文档和验收标准。后续按本文件一阶段一阶段完成。

---

## 0. 总体原则

KnowFlow 不是单独做一个 AI 问答 Demo，而是在传统企业知识管理业务上增加 AI Agent 能力。

因此开发顺序必须遵循：

```text
先传统业务闭环
再 RAG 问答
再 Agent 诊断
再 SOP / 报告
最后补权限、配置和工程化
```

每个阶段都要形成两类成果：

| 成果 | 说明 |
| --- | --- |
| 代码成果 | 前端页面、后端接口、数据库表、AI 能力或联调逻辑 |
| 阶段文档 | 本阶段做了什么、接口怎么设计、数据怎么流转、如何验收 |

## 1. 项目最终形态

### 1.1 传统业务系统

传统业务是项目的“身体”，没有它，AI 模块就像玩具。

| 模块 | 作用 |
| --- | --- |
| 知识库管理 | 新建知识库、分类、描述、健康状态 |
| 文档管理 | 上传文件、网页入库、文档列表、失败重试 |
| 文档入库流程 | 上传、解析、切片、向量化、抽样质检 |
| 分段管理 | 查看 chunk、编辑、禁用、复制引用 |
| 问答日志 | 记录问题、答案、引用、用户反馈、风险等级 |
| 知识质量任务 | 把未命中、低评分、引用异常转成待办 |
| SOP 管理 | 流程模板、执行记录、异常上报 |
| 报告中心 | 健康报告、问答报告、审计报告 |
| 用户权限 | 用户、角色、知识库访问控制 |
| 系统设置 | 模型配置、检索参数、安全与审计开关 |

### 1.2 AI Agent 增强能力

AI 是传统业务的“增强层”，必须绑定具体业务场景。

| AI 能力 | 绑定业务 |
| --- | --- |
| RAG 问答 | 员工基于企业知识库提问 |
| 引用溯源 | 每个答案显示文档、页码、分段和相关度 |
| 无答案兜底 | 没有可靠来源时不编造，生成知识缺口 |
| 低质量问答诊断 | 分析差评、未命中、引用不相关的原因 |
| SOP 生成 | 从回答或文档生成可执行流程 |
| 知识库健康分析 | 汇总命中率、失败文档、低评分问题 |
| 报告生成 | 基于日志和知识库状态生成运营报告 |

## 4. Phase 1：传统业务后端底座

### 4.1 目标

先做业务系统，不急着接大模型。  
这一阶段完成后，KnowFlow 应该像一个普通企业知识库系统，可以管理知识库、文档、日志和质量任务。

### 4.2 后端模块

| 模块 | 接口能力 |
| --- | --- |
| 知识库 | 新建、查询、更新、删除、健康状态统计 |
| 文档 | 文档记录创建、列表、状态更新、删除 |
| 分段 | 分段列表、详情、禁用、编辑 |
| 问答日志 | 日志写入、列表、筛选、详情 |
| 质量任务 | 创建任务、分派、状态流转、关闭 |

### 4.3 推荐包结构

src/main/java/com/yupi/yuaiagent/knowflow/

├── service/
├── repository/
├── model/

│   ├── dto/

## 5. Phase 2：文档入库与向量化

### 5.1 目标

把“上传文档 -> 解析文本 -> 智能切片 -> 向量化 -> 可问答”跑通。

### 5.2 核心流程

```text
上传文件
  -> 创建 kf_document
  -> 创建 kf_ingestion_task
  -> 解析文本
  -> 生成 chunk
  -> 写入向量库
  -> 更新文档状态为 ready
  -> 生成抽样质检问题
```

### 5.3 后端能力

| 能力 | 说明 |
| --- | --- |
| 文件上传 | 支持 PDF、Word、Markdown、txt |
| 网页入库 | 支持 URL 抓取正文 |
| 文档解析 | 复用 Spring AI Reader、Jsoup 等能力 |
| 分段策略 | 按标题、段落、token 长度切片 |
| 向量写入 | 写入 PgVector |
| 失败重试 | 保存失败原因，允许重新解析 |

### 5.4 本阶段文档

| 文档 | 建议路径 | 内容 |
| --- | --- | --- |
| 文档入库流程设计 | `docs/02-architecture/knowflow-ingestion-design.md` | 状态机、任务流、失败处理 |
| 分段与向量化策略 | `docs/02-architecture/knowflow-chunking-vector-design.md` | chunk 规则、metadata、向量字段 |

### 5.5 验收标准

- 上传一份文档后能看到入库进度；
- 文档解析成功后能看到分段；
- 分段能写入数据库和向量库；
- 解析失败能展示原因并重试；
- 知识库详情页能查看真实分段。

## 6. Phase 3：RAG 问答与引用溯源

### 6.1 目标

让员工能基于企业知识库提问，并且答案必须带引用来源。

### 6.2 技术架构

```text
用户问题
  -> Query Rewrite
  -> 权限过滤
  -> 向量召回
  -> 重排/过滤
  -> Prompt 组装
  -> LLM 流式回答
  -> 引用来源返回
  -> 写入问答日志
```

### 6.3 后端接口

| 接口 | 作用 |
| --- | --- |
| `POST /api/knowflow/chat` | 普通问答 |
| `GET /api/knowflow/chat/sse` | SSE 流式问答 |
| `GET /api/knowflow/citations/{id}` | 查询引用详情 |
| `POST /api/knowflow/feedback` | 提交有用/无用反馈 |

### 6.4 本阶段文档

| 文档 | 建议路径 | 内容 |
| --- | --- | --- |
| RAG 问答接口设计 | `docs/02-architecture/knowflow-rag-chat-api.md` | 请求、响应、SSE 事件 |
| 引用溯源设计 | `docs/02-architecture/knowflow-citation-design.md` | citation 字段、chunk 关联、前端展示 |

### 6.5 验收标准

- 前端问答页可以真实提问；
- 回答通过 SSE 流式输出；
- 答案中能看到引用编号；
- 点击引用能看到文档、页码、分段内容；
- 每次问答都写入日志。

## 7. Phase 4：问答日志与质量闭环

### 7.1 目标

把 AI 答错、答不出、引用不准，从一次性用户反馈变成可处理的业务任务。

### 7.2 核心闭环

```text
用户提问
  -> AI 回答
  -> 用户反馈无用 / 系统发现无引用
  -> 写入问答日志
  -> 创建知识质量任务
  -> 管理员补文档或重建索引
  -> 重新测试同类问题
  -> 关闭任务
```

### 7.3 后端能力

| 能力 | 说明 |
| --- | --- |
| 日志筛选 | 按知识库、质量、风险、时间筛选 |
| 详情抽屉 | 展示问题、答案、引用、反馈 |
| 质量任务 | 创建、分派、处理、关闭 |
| 复测记录 | 用同一问题重新跑 RAG |
| 工作台风险 | 汇总低评分、未命中、失败文档 |

### 7.4 本阶段文档

| 文档 | 建议路径 | 内容 |
| --- | --- | --- |
| 质量闭环设计 | `docs/02-architecture/knowflow-quality-loop-design.md` | 日志、任务、复测、状态流 |
| 工作台指标设计 | `docs/02-architecture/knowflow-dashboard-metrics.md` | 命中率、风险数、低评分统计 |

### 7.5 验收标准

- 无用反馈能进入日志；
- 未命中问题能创建知识补充任务；
- 任务能分派、处理、关闭；
- 工作台能展示真实风险队列；
- 管理员能复测问题。

## 8. Phase 5：Agent 诊断能力

### 8.1 目标

在传统业务闭环上增加 Java Agent 能力，让系统能自动分析问题原因和处理建议。

### 8.2 Agent 定位

第一版不做复杂多 Agent，先做一个“知识库运营诊断 Agent”。

```text
KnowledgeDiagnosisAgent
输入：问题、回答、引用、用户反馈、知识库状态、文档状态
输出：问题原因、处理建议、推荐任务、风险等级
```

### 8.3 推荐架构

```text
RAG + Tool Calling + 轻量 Workflow
```

| 能力 | 作用 |
| --- | --- |
| RAG | 获取相关文档和历史案例 |
| Tool Calling | 查询日志、文档、分段、任务 |
| Workflow | 固定诊断步骤，保证结果稳定 |
| 结构化输出 | 返回 JSON，便于创建任务 |

### 8.4 Agent 工具

| Tool | 作用 |
| --- | --- |
| `KnowledgeBaseTool` | 查询知识库健康状态 |
| `DocumentTool` | 查询文档和入库状态 |
| `QaLogTool` | 查询问答日志和用户反馈 |
| `ChunkTool` | 查询引用分段和相似分段 |
| `QualityTaskTool` | 创建知识质量任务 |

### 8.5 本阶段文档

| 文档 | 建议路径 | 内容 |
| --- | --- | --- |
| Agent 架构设计 | `docs/02-architecture/knowflow-agent-architecture.md` | Agent 类型、工具、流程 |
| 诊断 Prompt 与结构化输出 | `docs/02-architecture/knowflow-agent-prompt.md` | Prompt、JSON Schema、案例 |

### 8.6 验收标准

- 对一条低评分问答，Agent 能给出原因；
- Agent 能判断是缺文档、引用错、分段差，还是权限问题；
- Agent 能推荐补文档、重建索引、人工复核等动作；
- Agent 输出可以直接创建质量任务；
- 整体仍在 Java / Spring AI 项目内完成。

## 9. Phase 6：SOP 与报告中心

### 9.3 报告能力

| 问答会话报告 | 问题、回答、引用、反馈 |
| 审计报告 | 用户、时间、知识库、引用来源 |
| SOP 执行报告 | 执行步骤、负责人、异常 |

### 9.4 本阶段文档

| 文档 | 建议路径 | 内容 |

### 9.5 验收标准

## 11. 推荐执行顺序

接下来实际开发按这个顺序执行：

```text
1. Phase 1：传统业务后端底座
   先做知识库、文档、分段、问答日志、质量任务。

2. Phase 2：文档入库与向量化
   让文档真正可以上传、解析、切片、入向量库。

3. Phase 3：RAG 问答与引用溯源
   让 AI 问答真正接上企业文档。

4. Phase 4：问答日志与质量闭环
   让反馈和未命中进入业务处理流程。

5. Phase 5：Agent 诊断能力
   用 Agent 自动判断为什么答不好，以及怎么修。

6. Phase 6：SOP 与报告中心
   做差异化能力，用于简历亮点。

7. Phase 7：权限、配置、部署
   补企业级完整度。
```
