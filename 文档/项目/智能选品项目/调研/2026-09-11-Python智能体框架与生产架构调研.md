## 1 调研问题和结论

本次不是回答“Python 能不能调用大模型”，而是回答以下生产问题：

1. 市面上的 Python 智能体框架用什么抽象组织模型、工具、状态和多智能体协作？
2. Agent 的运行循环到底怎样工作，在哪里暂停、恢复和重试？
3. 对话记忆、业务事实、运行 checkpoint 和文件产物应如何区分？
4. 人工审批、工具权限、成本、可观测性和评测由谁负责？
5. 本项目应选择哪个框架，哪些能力不能交给 Agent？

调研结论如下：

- 主流框架的共同核心不是“多写几个角色 Prompt”，而是“模型循环 + 结构化工具 + 显式状态 + 有界执行 + 人工中断 + 可观测事件”。
- Agent 适合开放式目标、动态选择工具和需要根据工具结果继续推理的任务；步骤固定、金额敏感或必须可复算的流程更适合普通函数或显式 Workflow。
- 多 Agent 是编排方式，不是服务拆分方式。多个逻辑 Agent 可以运行在同一 Python 进程内，也可以只是一个主 Agent 调用几个专业 Agent 工具。
- 框架自带 Session、Memory 或 Checkpoint 不等于业务数据库。商品、库存、价格、客户、报价和图片授权必须继续由业务服务掌握。
- 对本项目，推荐“Java 业务控制面 + 独立 Python AI Runtime”，Python 内部以 PydanticAI 的类型化 Agent 为首选，以显式 Workflow 管流程；不直接让 Python 或模型写商品、库存和报价表。

## 2 先统一术语

| 概念 | 本文定义 | 典型例子 |
| --- | --- | --- |
| 模型调用 | 一次请求得到文本、标签、向量或图片，没有自主循环 | 从商品图提取颜色和风格标签 |
| Agent | 模型基于目标在多轮中选择工具、观察结果并决定下一步，直到输出或停止 | 根据客户要求搜索商品、检查库存、生成搭配并解释 |
| Workflow | 应用代码明确规定节点、分支、循环、并行、审批和终态 | 需求确认后才能选品，图片采用后才能进入正式 PPT |
| Tool | Agent 能请求执行、但由应用代码实现和校验的能力 | product_search、inventory_check、quote_calculate |
| Handoff | 当前 Agent 把后续控制权转交给另一个 Agent | 总控把当前请求交给搭配 Agent |
| Agent-as-tool | 主 Agent 调用专业 Agent，完成后仍由主 Agent 汇总 | 总控调用选品 Agent 和搭配 Agent |
| Session/Thread | 多次用户交互共享的对话上下文 | 一名销售围绕同一客户方案持续对话 |
| Run | 一次输入触发的一次有界执行 | 用户点击“重新生成四档搭配” |
| Step/Span | Run 内的一次模型、工具、校验、交接或审批步骤 | inventory_check 的一次调用 |
| Checkpoint | 为暂停、崩溃恢复或重放保存的有限运行状态 | 已完成选品，正在等待图片任务 |
| Memory | 跨步骤或跨会话保留的上下文；不是天然可信事实 | 经明确确认的偏好摘要 |

一个生产 Agent 的最小运行循环可以抽象为：

```text
接收已认证请求
  → 选择已发布 Agent 版本与预算
  → 构造最小上下文
  → 调用模型
  → 解析结构化输出
  → 如果是最终结果：校验并结束
  → 如果是工具调用：校验工具名、参数、权限、版本和预算
  → 如果需要审批或外部长任务：持久化 checkpoint 并暂停
  → 执行工具并记录结果
  → 将结果加入上下文，再次调用模型
  → 达到目标、期限、步数或失败阈值后结束
```

## 3 主流框架的共同生产架构

从各官方文档可以归纳出九个通常独立演进的层次。这里是对官方能力的项目化归纳，不表示任何一家框架使用完全相同的命名。

| 层次 | 责任 | 不能混入的事实 |
| --- | --- | --- |
| API/Channel | REST、SSE、WebSocket、定时任务和事件入口 | 不在入口层写 Prompt 业务规则 |
| Agent Definition | 名称、指令、模型、工具、输出 Schema、handoff 和预算 | 不把运行中的对话状态写进全局 Agent 对象 |
| Runner/Loop | 模型调用、工具执行、结果回灌、终止、最大步数 | 不无限自主循环 |
| Workflow/Graph | 节点、边、条件、并行、循环、人工暂停和恢复 | 不用长 Prompt 代替关键流程顺序 |
| Tool Gateway | 工具发现、参数校验、权限、超时、幂等、审批和错误转换 | 不让模型构造任意 HTTP、SQL 或文件路径 |
| State/Session | 对话历史、当前 Run 状态、checkpoint 和可见摘要 | 不把缓存摘要当商品或报价事实 |
| Provider Layer | LLM、视觉、Embedding、Rerank、生图供应商适配 | 不把供应商 DTO 传播为业务契约 |
| Policy/Guardrail | 输入、输出、工具和数据边界的前后置检查 | 不把审批当作服务端授权替代品 |
| Observability/Evals | trace、step、token、费用、延迟、错误、Golden Set 和在线反馈 | 不保存或展示模型隐藏思维链 |

成熟实现通常把开放式推理放在 Agent Loop，把金额、权限和不可逆写入放在 Workflow 或业务服务。Google ADK 2.0 的图工作流文档也明确把 Agent、函数和工具作为不同节点组合，以显式执行路径提高可预测性；Microsoft Agent Framework 官方则直接建议：能用函数解决时，不应为了形式使用 Agent。[Google ADK Graph Workflows](https://adk.dev/graphs/)、[Microsoft Agent Framework Overview](https://learn.microsoft.com/en-us/agent-framework/overview/)

## 4 代表性 Python 智能体框架

### 4.1 OpenAI Agents SDK

官方核心抽象是 Agent、Runner、Tool、Handoff、Guardrail、Session 和 Trace。Agent 保存指令、工具、模型、结构化输出和可选 handoff；Runner 驱动循环：调用模型，遇到工具则执行并回灌，遇到 handoff 则切换 Agent，遇到最终输出则结束，超过 max_turns 则失败。[Agents](https://openai.github.io/openai-agents-python/agents/)、[Running agents](https://openai.github.io/openai-agents-python/running_agents/)

其多 Agent 有两种主要模式：

- Manager 模式：专业 Agent 作为工具被主 Agent 调用，主 Agent 保留最终控制权。
- Handoff 模式：当前 Agent 将后续对话控制权交给专业 Agent。

工具层支持 Python function tool、托管工具、MCP 和 Agent-as-tool；工具可配置超时、错误格式、输入/输出 guardrail 及人工批准。Trace 覆盖模型、工具、handoff、guardrail 和自定义 span。[Tools](https://openai.github.io/openai-agents-python/tools/)、[Agent orchestration](https://openai.github.io/openai-agents-python/multi_agent/)、[Guardrails](https://openai.github.io/openai-agents-python/guardrails/)、[Tracing](https://openai.github.io/openai-agents-python/tracing/)

SDK 可以把审批中断和运行状态序列化后恢复，也能用 Session、Conversations API、previous_response_id 或应用自己保存的历史延续对话；这些是会话和中断恢复原语，不等同于通用耐久工作流引擎。官方资料没有据此承诺 exactly-once 工具副作用、工作流级持久定时器或任意节点崩溃恢复，因此关键写操作仍需业务幂等账本、Outbox、回查和补偿。[Running agents](https://openai.github.io/openai-agents-python/running_agents/)、[Human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/)

适用判断：SDK 的 Agent Loop、handoff、tool guardrail 和 trace 完整，使用 OpenAI 模型时接入直接；本项目同时涉及多模型和独立视觉供应商，因此可以借鉴其抽象，但不应把供应商绑定写进领域层。

### 4.2 LangGraph

LangGraph 把 Agent/Workflow 建模为 State、Node 和 Edge：State 是共享快照，Node 是执行函数，Edge 决定下一节点；图编译后由运行时执行。它强调低层编排、持久化、流式输出、human-in-the-loop 和长任务恢复，而不是替开发者决定 Prompt 或 Agent 角色。[LangGraph Overview](https://docs.langchain.com/oss/python/langgraph/overview)、[Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)

Checkpoint 按 thread 保存每个图步骤的状态，可支持恢复、人工中断、时间旅行和故障重启；跨 thread 的长期记忆使用 Store。Interrupt 会保存状态并等待 approve/edit/reject 等外部决定。官方也要求把外部 API 调用封装为幂等 task，避免恢复时重复副作用。[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)、[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)、[Functional API](https://docs.langchain.com/oss/python/langgraph/functional-api)

适用判断：当流程有大量分支、并行、长时间暂停和可重放要求时，LangGraph 的显式图与 checkpoint 很强；本项目已经规划自己的 run/run_step/checkpoint 和 Java 业务状态，如果直接再启用一套框架持久化，会形成双状态源，必须先设计统一的 Store/Checkpointer 适配，不能默认叠加。

### 4.3 PydanticAI

PydanticAI 的 Agent 是指令、模型、工具/Toolset、依赖类型和结构化输出类型的容器。它把输入、工具参数和最终输出都放在 Python 类型与 Pydantic 校验之下，Agent 本身可复用，运行依赖通过 RunContext 注入。[Agents](https://pydantic.dev/docs/ai/core-concepts/agent/)

底层使用 pydantic-graph 驱动模型请求、模型响应和工具节点；复杂应用可以从单 Agent，逐级演进到 Agent delegation、程序化 handoff、图控制和 Deep Agent。Deferred Tool 可以表示等待人工批准或交给外部系统执行的长任务；恢复时以 tool_call_id 对齐结果。官方同时提醒，人工批准不能替代服务端认证授权。[Multi-agent Applications](https://pydantic.dev/docs/ai/guides/multi-agent-applications/)、[Deferred Tools](https://pydantic.dev/docs/ai/tools-toolsets/deferred-tools/)

其 durable execution 可与 Temporal、DBOS、Prefect、Restate 等运行时集成；观测建立在 OpenTelemetry 之上，pydantic-evals 提供代码化数据集、实验和评估。[Durable Execution](https://pydantic.dev/docs/ai/capabilities/durable_execution/overview/)、[Pydantic Evals](https://pydantic.dev/docs/ai/evals/evals/)、[Observability](https://pydantic.dev/docs/ai/integrations/logfire/)

生产设计必须区分三层：PydanticAI Core 提供类型化 Agent 循环；Harness 提供 Memory、Guardrail、StepPersistence 等较高层能力；Temporal、DBOS 等外部引擎才负责更完整的 durable workflow。Harness 当前为 0.x，官方提醒 minor 版本之间可能有破坏性变化；StepPersistence 也明确不是任意图节点的完整 checkpoint，崩溃后的外部副作用仍可能处于 unknown_after_crash，不能把它当作自动去重保证。[Capabilities](https://pydantic.dev/docs/ai/capabilities/overview/)、[Step persistence](https://pydantic.dev/docs/ai/harness/step-persistence/)、[Retries](https://pydantic.dev/docs/ai/core-concepts/retries/)

适用判断：本项目最重视结构化输入输出、工具参数重建、外部长任务和多供应商适配，PydanticAI 与这些要求吻合；持久化仍应接入项目已有 Agent Control，而不是另建框架会话真相库。

### 4.4 Google Agent Development Kit（ADK）

ADK 的 Agent/LlmAgent 由模型、指令和工具组成；Runner 驱动 Agent 并产生 Event，SessionService、ArtifactService 和 MemoryService 分别处理对话、文件和长期记忆。ADK 同时提供顺序、并行、循环、协作以及 2.0 图工作流，并允许在节点间混合 Agent、工具、函数和人工输入。[ADK Agents](https://adk.dev/agents/)、[Agent Runtime](https://adk.dev/runtime/)、[Event Loop](https://adk.dev/runtime/event-loop/)、[Sessions](https://adk.dev/sessions/session/)

图工作流强调显式路由与结构化节点；工具确认可暂停动作并等待外部响应。部署可以采用 API Server、容器、Cloud Run、GKE 或 Google 托管运行时。[Graph Workflows](https://adk.dev/graphs/)、[Action confirmations](https://adk.dev/tools-custom/confirmation/)、[Deployment](https://adk.dev/deploy/)

适用判断：事件、Session、Artifact、Memory 和图工作流的分层完整，特别适合 Google 模型和云环境；本项目没有确定 Google Cloud 作为运行平台，也不能仅因框架完整就引入它的全部状态服务。

### 4.5 Microsoft Agent Framework

Microsoft 当前的新路线是 Microsoft Agent Framework，而不是把 AutoGen 当作新项目默认。官方把 Agent Framework 描述为 AutoGen 和 Semantic Kernel 的直接后继：Agent 管模型、工具、Session、Context Provider 和中间件；Workflow 用显式图连接 Agent 与普通函数，并支持 checkpoint、HITL 和多种编排。[Framework Overview](https://learn.microsoft.com/en-us/agent-framework/overview/)、[Official repository](https://github.com/microsoft/agent-framework)

Agent 入口为 run/stream，工具循环由执行管线处理；Workflow 支持 sequential、concurrent、handoff、group chat 等模式。Human-in-the-loop 通过外部 Request/Response 通道暂停并恢复，checkpoint 保存 workflow 状态和待处理请求。可观测性采用 OpenTelemetry，部署既可以自托管，也可以进入 Microsoft/Azure 托管路径。[HITL](https://learn.microsoft.com/en-us/agent-framework/workflows/human-in-the-loop)、[Checkpoints](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints)、[Hosting](https://learn.microsoft.com/en-us/agent-framework/hosting/)

Microsoft 官方在 2026-04-02 宣布 Agent Framework 1.0 GA；但这不表示所有 Python functional workflow、hosting、connector 和 integration 扩展都处于相同稳定等级，实施仍要核具体包。AutoGen 官方仓库已进入 maintenance mode，既有系统可维护，新项目不应再把它当作 Microsoft 当前默认路线。[Microsoft Agent Framework 1.0](https://devblogs.microsoft.com/agent-framework/microsoft-agent-framework-at-build-2026-announce/)、[AutoGen repository](https://github.com/microsoft/autogen)

适用判断：如果未来生产环境以 Azure、Foundry 和 Microsoft 生态为主，这是应重新评估的候选；当前项目尚无该平台决定，不应预先绑定。

### 4.6 CrewAI

CrewAI 使用 Agent、Task、Crew、Process 和 Flow。Crew 是一组 Agent 与任务，Process 可选择顺序或层级管理；层级模式由 manager Agent 分配和复核任务。Flow 使用 start/listen/router 等事件驱动节点，管理结构化或非结构化 State，并可持久化与恢复。[Crews](https://docs.crewai.com/en/concepts/crews)、[Processes](https://docs.crewai.com/en/concepts/processes)、[Flows](https://docs.crewai.com/en/concepts/flows)

适用判断：它适合以“角色协作”快速表达自动化，对业务演示很直观；本项目的关键风险是金额、库存、版本、图片授权和外部费用，需要更强的工具边界与显式状态控制，因此不把 Crew/角色自治作为首选生产内核。

## 5 横向比较

| 框架 | 最强抽象 | 状态/恢复 | HITL | 多 Agent | 供应商倾向 | 本项目判断 |
| --- | --- | --- | --- | --- | --- | --- |
| OpenAI Agents SDK | Agent Runner 与 tools/handoffs | Session、可序列化中断状态；不是通用工作流引擎 | 工具批准、暂停恢复 | Manager、Agent-as-tool、handoff | OpenAI 路径最直接 | 借鉴 Loop/Guardrail；作为备选运行时 |
| LangGraph | 显式 State/Node/Edge 图 | 原生 checkpoint、thread、store | interrupt/approve/edit/reject | 子图和图编排 | 模型无关 | 复杂耐久图的升级候选 |
| PydanticAI | 类型化 Agent、Toolset、Output | 可接多种 durable runtime；可外置状态 | deferred/approval tool | delegation、handoff、graph | 多 Provider | 首选 Agent 内核 |
| Google ADK | Runner/Event/Services 与图工作流 | Session、State、Memory、resume | tool confirmation、human node | 父子 Agent、协作和图 | Google 生态强 | 暂不选，保留评估 |
| Microsoft Agent Framework | Agent pipeline + Workflow graph | Session、checkpoint、durable hosting | RequestPort/approval | 多种内建 orchestration | Azure/Microsoft 强 | Azure 路线出现时重评 |
| CrewAI | Agent/Task/Crew/Flow | Flow state/persist | Flow/Task 人工反馈 | sequential/hierarchical crew | 多 Provider | 原型友好，非当前生产首选 |

横向表只比较官方公开抽象，不是性能排名。框架是否适合生产仍取决于具体版本、Provider、数据地域、许可、压测、故障恢复和团队维护能力；本轮没有安装或运行上述框架。

## 6 对本项目有用的编排模式

### 6.1 单 Agent + 受限工具

适合需求理解和一次选品。Agent 只有 product_search、inventory_check、combo_validate 等只读或确定性工具，最终返回结构化建议。优点是最容易限制成本和步数，应作为首期默认。

### 6.2 Manager + 专业 Agent-as-tool

适合用户一句话同时要求解析需求、选品、搭配和图片准备。总控仍负责最终汇总，专业 Agent 各自只接收最小上下文。比无条件 handoff 更适合本项目，因为销售需要一个统一结果，而不是在多个角色之间漂移。

### 6.3 显式 Workflow + 局部 Agent

适合完整报价链：业务代码固定“确认需求 → 硬过滤 → AI 排序 → 组合校验 → 人工采用 → 生图 → 人工复核 → 报价重算”。只有需求理解、审美排序和说明文字是 Agent/模型节点，其余都是确定性节点。这是本项目推荐的主模式。

### 6.4 Handoff

只在专业角色需要独立持续对话时使用，例如图片复核会话转给视觉助手。首期不需要让每个内部步骤都 handoff；handoff 会扩大上下文管理、权限和调试成本。

### 6.5 自由多 Agent Crew

不用于金额、库存和正式方案确认。即使实验使用，也必须在沙箱、只读工具、固定预算和 Golden Set 内运行，结果只能作为候选。

## 7 框架选型建议

本项目推荐路线为：

```text
FastAPI 内部服务入口
  + Pydantic v2 契约与配置
  + PydanticAI Agent/Toolset/typed output
  + 显式 Workflow（先用普通代码或 pydantic-graph）
  + HTTPX Provider/Java Tool Adapter
  + OpenTelemetry trace/metrics
  + pytest + 代码化 Golden Set/Evals
```

选择原因：

1. 商品、组合、图片和报价建议都必须有严格结构，Pydantic 类型可同时约束 API、Tool 和模型输出。
2. Deferred Tool 能自然表达“等待销售批准”和“图片任务外部执行”，但批准后仍由 Java 重新鉴权。
3. Provider 选择尚未固定，需要隔离 OpenAI、国内 LLM、视觉理解和生图供应商。
4. 当前业务已经设计 run、step、checkpoint 和人工采用语义，首期没有必要再引入第二套 Agent 持久化平台。
5. 如果后续图分支、并行、长暂停和重放复杂度显著增加，可以用验证过的 LangGraph、ADK、MAF 或耐久运行时替换 Workflow 层，不改变 Java/Python 公共契约。

本次只形成推荐，不锁定依赖版本。正式安装前必须完成版本、Python 支持矩阵、许可证、供应链风险、Provider 兼容、最小样例和故障恢复 Spike。
