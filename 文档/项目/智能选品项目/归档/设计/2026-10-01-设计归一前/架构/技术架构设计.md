## 1 架构结论

首期只落三个生产代码项目，不把共享契约和基础设施算成项目：

| 项目 | 形态 | 首期落点 | 主要责任 |
| --- | --- | --- | --- |
| Java 业务控制面 | 现有 Maven 多模块中的新业务模块 | `ruoyi-backend/ruoyi-fashion` | RuoYi 身份/RBAC、MySQL 业务事实、API、事务、AI Run 控制、确定性报价、文件与审计 |
| 内部运营工作台 | 现有 Vue 3 管理端中的新业务域 | `frontend/admin-web/src/views/fashion`、`frontend/admin-web/src/api/fashion` | 商品运营、客户方案、搭配、图片、报价、交付和配置界面 |
| Python AI 执行面 | 唯一新建 Python 项目 | `python/fashion-ai-runtime/` | 类型化 AI 工作流、模型/视觉/生图适配、输出护栏、trace 与 eval |

`contracts/fashion/` 保存由 Java 和 Python 共同消费的 OpenAPI/事件/Schema；它不部署。MySQL、对象存储、队列和观测是环境能力，不另建业务仓库。

## 2 系统上下文与调用链

```text
Chrome 下载图片 ──► 文件/ZIP ──► admin-web
                                      │
内部销售/运营 ─────────────────────────┤ RuoYi API
                                      ▼
                    platform-backend / ruoyi-fashion
                       │          │           │
                       │          │           ├──► MySQL（唯一业务事实）
                       │          └──────────────► 对象存储
                       │
                       ├──► fashion-ai-runtime ──► 模型/视觉/生图 Provider
                       │            │
                       ◄────────────┘ Java Tool Gateway
                       │
                       └──► 确认报价三层留档 / 导出任务
```

主链只有 Java 对外。Java 创建 Run、冻结业务输入和预算，使用服务身份调用 Python；Python 需要实时商品事实时，只能调用按 Run、用户和权限裁剪的 Java Tool Gateway。Python 返回的是建议或候选，Java 检查 SKU、价格、库存、权限、版本和预算，人工采用后才进入业务事务。

## 3 业务域与功能边界

用户可见功能按平台基础、商品中心、数据更新、客户需求、选品搭配、图片工作台、报价中心、交付中心、AI Agent 控制九个模块规划。下表把它们聚合为五个协作域，便于表达 Java、Python 与 Admin 的职责；聚合域不是新的数据库模块，也不改变[任务清单](../../../../功能/FEAT-FASHION-001-服装智能选品生产首版/任务清单.md)的十阶段执行顺序。

| 域 | PRD 范围 | Java 责任 | Python 责任 | 管理端责任 |
| --- | --- | --- | --- | --- |
| 商品数据 | REQ 01–05 | 导入校验/发布/恢复、当前价、库存、素材元数据、可推荐资格 | 可选视觉标签建议，不改变商品事实 | 映射、差异、错误、批次、图片确认 |
| 客户与选品 | REQ 06–08 | 客户归属、Brief 版本、硬过滤、候选业务复核和采用 | 自然语言解析、候选排序、1–4 品类搭配和解释 | 条件确认、锁定、替换、重搭、排序 |
| 视觉 AI | REQ 09–11 | 图片任务、预算预留、输入版本、轮询回查、采用与作废 | Provider 适配、提示、结果校验、质量/安全标签 | 任务创建、对比、复核、采用与降级 |
| 报价 | REQ 12–15 | 当前价/库存读取、数量守恒、折扣/费用/税、例外、确认后三层报价版本 | 可解释缺口，不输出正式金额 | 输入商务参数、显示阻断、确认版本 |
| 交付 | REQ 16–17 | 确认报价版本投影、PPTX/CSV/ZIP 任务、受控下载、审计 | 可生成受控文案建议，不读取内部敏感字段 | 预览、选择模板、下载、失败恢复 |

跨域能力包括身份/RBAC、客户归属、契约版本、MySQL 迁移、文件安全、幂等、预算、审计、观测、评测和恢复。它们不是“后面再补的公共代码”，而是对应业务切片的完成条件。

## 4 数据所有权与一致性

- RuoYi 账号、角色、菜单和认证继续使用平台 MySQL；`ruoyi-fashion` 以稳定用户标识关联，不建跨项目数据库事实。
- 服装商品、当前销售价、库存、客户、方案、报价、导入、文件元数据和 AI 控制记录由服装 MySQL 表统一承载；详细表结构以[数据库设计 v2.3](数据库设计.md)为准。
- 当前 Spring Context 同时存在 RuoYi MySQL `dynamicDataSource` 和面试项目 PostgreSQL，且 `interviewJdbcTemplate` 为 `@Primary`。Fashion 必须用限定名注入 `fashionJdbcTemplate` 与 `fashionTransactionManager`/`fashionTransactionTemplate`，并让 migration、Repository、事务和 MySQL 命名锁显式绑定同一 `dynamicDataSource`；不得依赖按类型自动选择。
- v2.3 共 6 个模块、16 张 `fq_*` 业务表：商品资料 `fq_product`；库存 `fq_stock`；客户 `fq_customer`；报价方案 `fq_quote`、`fq_quote_combo`、`fq_quote_detail`、`fq_quote_image`、`fq_quote_file`；导入管理 `fq_import_batch`、`fq_import_detail`；AI Agent `fq_ai_agent`、`fq_ai_agent_version`、`fq_ai_conversation`、`fq_ai_message`、`fq_ai_run`、`fq_ai_run_step`。其中前 10 张是核心业务表，后 6 张是 AI 表。
- Python 没有业务数据库凭据，也不缓存可作为权威事实的客户、价格或库存。Run 状态、Step 账本、租约、fencing、预算、幂等、有限供应商事件和采用事实由 Java 写入现有 `fq_ai_run`、`fq_ai_run_step` 字段，不新增预算桶、费用流水、回调收件箱、outbox、checkpoint 或通用事件表。
- 首期一个 SKU 只有一套当前销售价。已确认报价把原价、调整、数量、价格批次和税费口径复制到不可变明细；后续调价不重写历史报价。
- 已确认报价历史由 `fq_quote`、`fq_quote_combo`、`fq_quote_detail` 三层确认后锁定并在修订时复制，不建独立报价快照表。导出只读该确认版本。
- 固定导入模板由 Java 代码或受控配置维护，`fq_import_batch` 固化实际映射，不建 `fq_import_template`。首期通用 AI 反馈延期，不建 `fq_ai_feedback`；普通对话内容仍进入消息表，但不能冒充结构化反馈或训练授权。
- 大文件进入受控对象存储，数据库只保存稳定键、摘要、版本、权限和状态。临时 URL 不是业务主键。

归档的 44 表第一版已经被明确否决，只能解释历史取舍，禁止用于生成 DDL、实体、Mapper、迁移或任务拆分。当前 16 张 `fq_*` 业务表已经批准为设计边界，但尚未建库、执行迁移或完成数据库、权限、并发与容量验证。

## 5 Python 单项目内部结构

唯一 `python/fashion-ai-runtime/` 按责任分层，不为每个 Agent 新建工程：

```text
python/fashion-ai-runtime/
├─ src/fashion_ai/
│  ├─ api/                    # 内部 HTTP、服务认证、错误和版本适配
│  ├─ application/workflows/  # use case、deadline、budget、取消和降级
│  ├─ agents/                 # typed Agent；运行配置由 Java 固定版本
│  ├─ domain/                 # 与 FastAPI/Provider 无关的值对象和状态
│  ├─ ports/                  # 模型、图片、Java Tool 与事件边界
│  ├─ providers/              # LLM、vision、image adapter
│  ├─ tools/java_gateway/     # Java 白名单 Tool 客户端
│  ├─ guardrails/             # 输入、输出、内容、URL/文件边界
│  ├─ telemetry/              # trace、metrics、脱敏日志
│  └─ prompts/                # 渲染器与开发 fixture，不持有生产发布真相
├─ evals/                     # golden set、回归门和发布比较
└─ tests/                     # unit/contract/integration/fault/security/eval
```

当前首个切片只建立了较小的 `api/application/models/config` 骨架；上图是目标结构，不代表所有包已经存在。P0 由 Java 进程内有界 Dispatcher 领取 MySQL 中的 Run、图片和文件任务，提交领取事务后再调用 Python；Python 不直连数据库或自行抢占业务任务。同一 Python 镜像以后可在 Java Gateway 发放租约的前提下启动 API 与 Worker 两类进程，但仍共享同一代码项目、版本和发布门，不构成 P0 的第四个部署项目。

详细 Run/Step/Tool、状态机、超时、预算、观测和评测设计见 [Python 智能体架构设计](Python智能体架构设计.md)。

## 6 契约与交互规则

- 候选机器契约位于 [`contracts/fashion/ai-runtime.openapi.yaml`](../../../../../../../contracts/fashion/ai-runtime.openapi.yaml)，由 Python 模型确定性导出并做完整结构比较；Java 客户端接入前再完成服务认证、通用 Agent Run 信封和兼容策略评审。
- 所有变更请求携带稳定幂等键和期望版本。Java 创建 `runId`、`runAttempt`、租约、`fencingToken` 和预算，并在现有 Run / Step 记录中持久化有限事件事实；Python 不能自行扩展调用权限或费用上限。
- Python 请求必须携带调用截止时间，实际超时取调用方剩余时间和服务端硬上限的较小值；超时、拒绝、重试与结果未知使用稳定错误语义。
- Tool 参数和结果执行 Schema 校验。任何模型输出在展示或采用前再做输出校验；正式写入前必须由 Java 重验。
- 浏览器不持有服务间凭据；Provider Secret 不进入浏览器、日志、Prompt、数据库业务字段或导出文件。

## 7 首个端到端开发切片

首个可验收纵向切片按以下顺序闭环：

1. 销售在 `admin-web` 输入自然语言需求并补充客户、预算、数量和品类档位。
2. Java 校验身份与客户归属，建立 Brief/Run，冻结允许的商品范围和预算。
3. Python 将需求解析为类型化草案；缺少关键字段时返回待确认问题，不猜测。
4. 用户确认后，Java 执行 SKU/上下架/价格/库存硬过滤，将最小候选上下文交给 Python 排序与搭配。
5. Python 返回候选、分数与约束解释，不返回客户详情、价格、库存或正式报价。
6. Java 重验候选；用户采用后写入新方案 revision。
7. Java 以 SKU 当前销售价和已确认商务参数生成确定性报价预览。

该切片先不调用真实模型，可用可替换 Analyzer 或受控 fixture 验证服务边界；启用 Provider 必须通过第 8 节安全门。

## 8 Provider 与生产部署安全门

当前 disabled 骨架只允许保留为本地开发起点。以下条件全部满足前，不得称为 Provider-ready，不得绑定共享地址或发生真实模型费用：

- Java/Python 服务身份认证、授权、轮换和 401/403 契约；
- ASGI 解析前请求体上限、文件类型/尺寸限制、SSRF 防护和 413 契约；
- `runAttempt`、`executionLeaseId`、`fencingToken`、委托身份、Resolved Agent Spec、预算、幂等和有限事件字段在现有 Run / Step 两表中的持久化；
- Tool 白名单、出站网络白名单、日志/trace 脱敏、秘密扫描和最小数据集；
- Provider 超时/429/取消/晚到结果/账单未知的故障测试；
- 需求、排序、搭配、视觉和图像 Golden Set 的发布阈值；
- 部署拓扑、容量、告警、备份恢复、回滚和实际环境冒烟。

## 10 恢复与变更控制

- 数据迁移遵循兼容新增、回填、校验、切换读写，再决定是否清理；每次数据库动作需要备份、行数/摘要、失败恢复和消费者检查。
- AI 版本以不可变 Agent/Prompt/Tool/Model 规格绑定 Run；回滚发布指针不改历史 Run。
- 报价和交付只读已确认且锁定的 `fq_quote`、`fq_quote_combo`、`fq_quote_detail` 三层版本；外部任务未知时先按 Run / Step 中的有限事件标识回查，不自动重复产生费用。
- 拆分 Python 服务、引入第二种业务数据库、多价表、Portal/移动端或浏览器扩展都属于边界变化，必须新建决策与迁移/验收范围。
