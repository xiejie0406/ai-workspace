## 3. 调用与信任边界

```text
内部浏览器
    │ 仅调用 Java API
    ▼
frontend/admin-web/src/{views,api}/fashion ──► ruoyi-backend/ruoyi-fashion ──► fashion-ai-runtime
                              │                              │
                              ▼                              └─► 受控 Provider（当前 disabled）
                     MySQL 业务事实 / 对象存储引用
```

| 边界 | 规则 |
| --- | --- |
| 浏览器 → Java | 使用若依身份和 RBAC；服务端重新检查客户归属、字段权限、版本和状态 |
| Java → Python | 仅服务到服务调用；使用 HMAC-SHA256 v1 key ring、audience、实际正文摘要、时间窗与 nonce；JDK client 固定 HTTP/1.1，避免 Uvicorn cleartext h2c upgrade 丢失 POST 正文；生产部署仍必须使用私网 TLS |
| Python → Provider | adapter 默认关闭；密钥仅在运行环境注入，不能进入浏览器、请求正文、trace 或仓库 |
| Python → 数据 | 不直连服装业务 MySQL；只处理 Java 提供的最小、带版本上下文 |
| Python → Java 结果 | 结果是候选/草案；Java 按最新事实复核，通过人工采用事务后才写业务状态 |

浏览器不得直连 Python。CORS、隐藏 URL 或前端环境变量都不能替代这一约束。

## 4. Java 与 MySQL 权威模型

`platform-backend` 新增 `ruoyi-fashion` 模块，沿用现有若依构建、认证和模块装配。业务表和 migration 只能从[数据库设计 v2.3](../架构/数据库设计.md)生成：首期恰好是商品资料、库存、客户、报价方案、导入管理、AI Agent 六个模块，共 16 张 `fq_*` 业务表，其中 10 张核心业务表、6 张 AI 生命周期表。T01～T16 migration 已在临时隔离 MySQL 8.0.46 反复执行，并完成约束、并发、10 万级容量、重启及逻辑备份恢复验证；非隔离数据库未迁移。

Spring Boot 4 的共享 `ObjectMapper` 使用 Jackson 3。Fashion 的 `JsonNode`、`ObjectMapper`、`TypeReference` 和异常类型统一采用 `tools.jackson`；兼容注解仍沿用平台提供的 annotation 包。需要被 `@Repository` 异常翻译或 `@PreAuthorize` 方法安全切面代理的实现类不得声明为 `final`。这两项约束已经由完整 `ruoyi-admin.jar` 启动/重启脚本实际验证，避免仅凭模块单测遗漏容器装配错误。

P0 migration 的精确表名为：`fq_product`、`fq_stock`、`fq_customer`、`fq_quote`、`fq_quote_combo`、`fq_quote_detail`、`fq_quote_image`、`fq_quote_file`、`fq_import_batch`、`fq_import_detail`、`fq_ai_agent`、`fq_ai_agent_version`、`fq_ai_conversation`、`fq_ai_message`、`fq_ai_run`、`fq_ai_run_step`。禁止读取归档第一版，禁止创建 `fq_import_template`、`fq_ai_feedback`，也不建设独立报价快照、价格版本、库存版本、审计、预算账本、回调收件箱或 outbox 表。

| 聚合/记录 | Java 权威规则 |
| --- | --- |
| 商品与 SKU | 商品、颜色、尺码、来源、图片引用和上下架状态由 Java 验证；SKU 稳定唯一 |
| 当前销售价 | P0 每个 SKU 恰好一套当前销售价，直接保存在 `fq_product`；多价表和价格版本表不预埋为已支持 |
| 库存与导入 | 当前库存保存在 `fq_stock`；价格/库存导入的批次、前后值、错误和恢复证据保存在 `fq_import_batch`、`fq_import_detail`，发布事务失败时当前行保持不变 |
| 客户方案 | 客户归属来自已认证主体和 Java 数据，不把名称、联系人、内部备注交给 Python |
| 搭配与采用 | 候选、锁定、替换、`quoteRowVersion/comboVisualHash`、来源 run 和人工采用动作分开记录 |
| 报价 | 金额使用 `DECIMAL`，由 Java 以十进制计算并按规则半入舍入到分；税费/折扣/费用、尺码数量、库存时效和授权例外均由 Java 确定性计算 |
| 确认版本与交付 | `fq_quote`、`fq_quote_combo`、`fq_quote_detail` 三层在确认时冻结并构成历史报价版本；导出只读该三层记录，不另建快照表，也不因当前价或库存变化而重算 |
| 审计与幂等 | 真实主体、动作、版本、请求键、采用/拒绝及失败原因由当前 16 表的业务字段与 RuoYi 平台能力追溯；前端提示不构成审计，不另建独立审计表 |

数据库采用 MySQL 作为本独立业务项目的唯一权威业务数据库。由于当前 Spring Context 还存在面试项目 PostgreSQL 及其 `@Primary interviewJdbcTemplate`，Fashion 的 migration、Repository、写事务和 MySQL 命名锁必须通过限定名绑定同一 `dynamicDataSource`，禁止依赖按类型自动注入。P0 由公共 `FashionCatalogWriteLock` 使用单一 `fashion:{database}:catalog-write` 串行保护商品资料/主图、当前价格、当前库存的发布与人工修改及报价确认；文件解析、AI 和外部调用均在锁外，命名锁只在事务 commit/rollback 完成后释放。`fq_ai_agent`、`fq_ai_agent_version`、`fq_ai_conversation`、`fq_ai_message`、`fq_ai_run`、`fq_ai_run_step` 六张表由 Java/MySQL 持有 Agent 生命周期权威状态；Python 只执行 Java 下发的有界任务，不建立第二套 Agent、对话、消息、Run、Step 或采用状态源。上述逻辑模型已由数据库设计 v2.3 固定为 P0 输入；IMP-02～IMP-09 已完成数据库、业务、Worker 和交付实现，IMP-10 已完成本地隔离容量、重启与逻辑恢复演练；候选环境迁移和多实例演练仍未执行。

## 5. Python Runtime 边界

当前 [`ai-runtime.openapi.yaml`](../../../../../../../contracts/fashion/ai-runtime.openapi.yaml)覆盖 health、capabilities、requirement-analysis、product-attribute-suggestion 和 selection-styling，并与 [`ai-control-gateway.openapi.yaml`](../../../../../../../contracts/fashion/ai-control-gateway.openapi.yaml)、共享 JSON Schema、认证规范和双向向量构成内部契约基线：

- 请求包含 UUID `request_id`、稳定 `run_id`、`idempotency_key`、`deadline_at` 和 `version`。
- 客户只以稳定 `customer_ref` 进入请求；响应草案禁止携带客户归属字段。
- 需求草案可表达方案名、受众、场景、季节、风格、颜色、排除项、人数/套数、交付日期、尺码、独立/递进模式、1–4 品类档位和多口径预算。
- 响应固定为待人工确认，且不能携带商品、SKU、价格或库存事实。
- Provider disabled 时返回 503；非法输入返回不回显正文的稳定 422；在 JSON 解析前按实际 ASGI 字节限制 413。
- 内部接口要求 HMAC 服务身份、request/correlation ID 和 W3C Trace Context；active/previous key 支持轮换，nonce 按服务全局防重放。

该契约与测试证明 fail-closed 输入输出、双向认证、解析前 body limit、候选和图片任务结构；Java 侧 Run 调度/持久化、费用状态和采用边界已有自动化证据。本机真实 socket 已验证 HMAC、非空 POST、correlation/trace、503 映射及 Python 进程重启前后调用，并据此修复 JDK h2c upgrade 与 Uvicorn 不兼容造成的空正文签名失败。它仍不证明真实视觉模型质量、生产 Provider 费用、私网 TLS、共享 nonce store、采集端或多实例部署已经完成。

真实视觉试点采用封闭分母：试点开始前登记 40 个唯一任务 ID，结果集必须与登记集合完全一致，且 1/2/3/4 品类组各 10 个；不得删除失败任务或用新任务替换。`fashion-evaluate-visual-trial` 只读取脱敏结果，强制 Provider/模型/配置、输入输出规格和人工复核规则一致，提交/复核/采用时间带时区且采用发生在复核后，按 PRD 计算首轮可用率、两轮内可交付率、每组 8/10、全部费用、每张采用图成本及采用耗时。账单未结或无采用证据保持 `blocked`；质量、费用、数据授权、关键商品身份或缺件触发 `fail`。聚合报告带源文件 SHA-256，但该工具不调用 Provider，也不替代真实样本、业务复核、UAT 或发布决定。

`fashion-evaluate-candidate-readiness` 是 IMP-10.7/10.8 的最终离线交叉门：先读取原始候选授权清单并重算 SHA-256，再核对候选输入预检、视觉聚合和技术/UAT 证据清单全部引用该摘要，视觉报告费用上限与预检获批上限完全一致，并精确覆盖七个技术 gate 与 `UAT-01～UAT-06`。质量门固定为 PRD 的每组 8/10；获批人民币费用上限不少于 0.01 元且最多两位小数，避免预检报告四舍五入改变授权语义。预检的 16 表、无网络/写库/Provider、Secret 拒绝和排除发布声明，以及视觉报告的封闭分母、失败保留、无外部动作和无发布决定声明均为 Literal 契约。已执行 gate 和业务决定必须记录非空身份及带时区时间；每个 gate 必须提供证据包内相对文件路径，工具实际读取不超过 50 MiB 的文件并重算 SHA-256；绝对路径、目录越界、缺失、疑似 Secret/私钥或摘要不一致即拒绝。只有原始授权清单、视觉、技术、六组 UAT 和业务决定全部通过才可写 `ReleaseReady=true`，而 `ReleaseAuthorized` 永远为 false；该本地判定不能代签 UAT，也不能触发部署或发布。

## 6. 通用 Agent Run 冻结语义

文本解析、候选排序、搭配和视觉任务复用 Java/MySQL 中 `fq_ai_run` 与 `fq_ai_run_step` 的同一运行语义，不为每个能力或 Python Runtime 复制一套任务状态。IMP-01 冻结的 ID、版本、deadline、错误、取消、幂等、attempt、lease 与 fencing 契约已经在后续阶段实现并测试：

1. `run_id`、`quoteRowVersion/comboVisualHash`、prompt/schema/provider 版本和截止时间固定，不从晚到结果读取“当前报价”。
2. 每次执行持有有期限 lease；续租和接管必须产生单调 fencing token，旧 worker 无权提交结果。
3. `idempotency_key` 的作用域、请求摘要、冲突返回和保留期明确；相同键不同输入必须拒绝。
4. 取消、超时、Provider 未知结果、部分成功和重试分别有状态，不能把“已受理”写成“已成功”。
5. trace 默认脱敏，不记录客户原文、联系人、密钥和未授权图片；eval 数据需单独批准用途。
6. Java 采用结果时校验 run、`quoteRowVersion/comboVisualHash`、商品/图片版本和人工身份；晚到或旧版本结果只留审计，不覆盖当前报价。

P0 不新增队列服务或第四个部署项目。Java/RuoYi 进程内的有界 Worker/Dispatcher 从 MySQL 领取 Agent、图片和交付任务：领取与租约落库后先提交事务，再调用 Python、Provider 或文件生成；结果使用 lease/fencing 条件在新事务提交。Python 不直连 MySQL，也不自行领取业务任务。重新领取、续租、取消、晚到结果拒绝以及本地 MySQL 重启/逻辑恢复均已有证据；候选环境 Java/Python 多实例恢复仍未演练。

共享若依启动时，`fashion.enabled` 为模块总开关，缺省 `true`；显式设为 `false` 并重启后，Fashion 的 HTTP、业务服务、持久化、迁移配置与进程内 Worker 均不装配。总开关不替代细分开关：`fashion.migration.enabled` 和 `fashion.ai-runtime.worker-enabled` 仍默认关闭，真实图片 Provider 仍须显式启用；图片与文件交付 Worker 沿用原有的独立默认值，启用模块时会轮询已有任务。

## 商机驱动套装选品技术增量（草案）

日期：2026-09-26；状态：Draft。交互详见[商机驱动套装选品交互设计](商机驱动套装选品交互设计.md)。仅设计，尚未修改业务代码或数据库；本节替代“手工勾选即主流程”的设计解释。

### 当前差距

当前 `ProductAttributeFields.categoryPath` 是平台品类自由文本，不能充当正式三级分类。`FashionSelectionService` 和候选查询主要以大类 `category_code` 工作，已有人工采用要求完整 SKU 数量。需求已在 `fq_quote.requirement_text/requirement_json` 保存，可复用客户需求工作单，避免另建 CRM 真相。

### 数据设计候选与兼容

- 正式分类需要稳定编码、一级/二级/三级名称、有效状态、分类版本；树只由已维护的商品分类归纳/映射形成。建议在现有字典体系定义版本化叶子编码和完整路径，不用可任意拼写的商品文本作为关联键。重复路径、缺级、歧义交由商品资料维护明确修正；大类编码保留表示套装位置。
- 商品新增独立的标准叶子分类引用（候选名 `category_leaf_code`）；`categoryPath` 继续保存来源原值。字段及字典结构在数据库设计复核后迁移，不能直接把现有来源文本当已确认分类自动回填。未映射旧商品保持可查，匹配时说明排除原因。
- 需求 JSON 的新版结构包含原文修订、字段值/口径/来源片段/明示或推断状态、硬条件/偏好、待确认项、组成位置和允许叶子集合。保留既有字段适配器，不静默覆盖历史快照。
- 推荐草稿与已采用 SKU 明细分开：建议由现有方案容器的版本化文档保存款色选择、分类版本、候选事实摘要和缺口，正式采用后才落完整 SKU 分配。暂不增加业务表；具体 JSON 承载列、容量、索引与删除/保留规则须在数据库设计中定稿后实施，不强塞进需求 JSON 形成混合真相。

### 处理链路

1. Java 保存客户原文及修订；Python 识别结构化条件，只返回已提供分类目录中的编码及依据，不直接写库。
2. Java 校验分类存在、权限、字段类型与修订；Admin 展示待修正结果。用户确认后生成需求版本。
3. Java 按叶子分类、可见范围及状态检索内部商品；按款色聚合 SKU，同时保留各尺码价格/库存事实。未知硬条件单列待核实，不冒充合格。
4. 先应用硬过滤，再匹配偏好和跨单品的颜色/风格一致性。使用有界候选组合，不能对全部 SKU 无限制笛卡尔积。Python 可排序并建议搭配；无论排序来源，Java 再校验各位置分类、身份和总预算。
5. 返回套装商品引用、逐条匹配依据、排除摘要、未确认项、价格区间/口径、快照版本。不返回凭空商品或模型计算的最终金额。
6. 保存/替换传需求版本、候选快照和 rowVersion；Java 事务检查最新事实及幂等。需求变化使旧候选失效，旧异步结果保留为历史但不得采用。
7. 完整尺码分配后沿用现有采用/报价服务再校验；不跳过库存或确认条件。缺尺码草稿不能用虚拟 S/M/L 补齐。

### API 契约建议（非现有可用端点承诺）

在现有 `/fashion/quotes/{id}` 资源下扩展职责，具体路径先查现有 OpenAPI 后定稿：

| 操作 | 请求核心 | 返回核心 |
|---|---|---|
| 识别需求 | 原文、工作单修订、请求幂等号 | runId、执行状态、识别字段及依据 |
| 确认条件 | 已修正字段、分类位置、rowVersion | requirementRevision、待确认项 |
| 匹配套装 | requirementRevision、锁定款色、候选分页 | outfits、缺口摘要、catalogSnapshot |
| 查替换商品 | 位置、当前组合、需求/事实版本 | 候选及替换后的预算与缺口 |

## 方案池技术增量（v0.2）
