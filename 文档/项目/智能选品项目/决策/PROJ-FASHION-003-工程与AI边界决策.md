## 1 决策结果

| ID | 已确定事项 | 结果 | 主要理由 |
| --- | --- | --- | --- |
| FASHION-ADR-001 | 生产代码项目数量 | 首期恰好 3 个：`ruoyi-backend/`、`frontend/admin-web/`、`python/fashion-ai-runtime/` | 复用现有 RuoYi 和管理端，只新增必要的 AI 运行时，避免重复身份、权限和前端工程 |
| FASHION-ADR-002 | Python AI 项目数量 | 只有一个 `python/fashion-ai-runtime/` | 需求解析、选品搭配、视觉、生图适配和评测按 Python 包分层；不按 Agent 拆微服务 |
| FASHION-ADR-003 | Java 与 Python 边界 | Java 是业务控制面和正式副作用入口；Python 是 AI 执行面 | 把模型的不确定性与权限、金额、库存、事务和审计隔离 |
| FASHION-ADR-004 | 数据库所有权 | 服装业务事实统一使用 MySQL，由 Java 访问；Python 无业务库凭据 | 符合仓库内独立业务项目的数据库规则，避免跨库事务和双写事实源 |
| FASHION-ADR-005 | 首期价格模型 | 一个 SKU 一套当前销售价；报价确认时复制到不可变明细 | 与数据库 v2.3 一致；客户价、渠道价、阶梯价和预约价没有已确认业务依据 |
| FASHION-ADR-006 | 机器契约 | `contracts/fashion/` 是唯一共享契约目录，不计为第四个项目 | 契约需要被 Java/Python 共同消费，但不单独部署 |
| FASHION-ADR-007 | 首期客户端 | 只在 `frontend/admin-web/` 建内部工作台 | 团购/批发客户首期接收文件，不需 Portal、移动端或客户自助登录 |
| FASHION-ADR-008 | 京东图片获取 | P0 使用现有 Chrome 插件下载，文件或 ZIP 上传，人工映射确认 | 不让自研扩展阻断核心业务；扩展只有在真实样本和权限边界验证后才进入 P1 |
| FASHION-ADR-009 | 首期数据库规模 | v2.3 固定为 6 个模块、16 张 `fq_*` 业务表：10 张核心业务表和 6 张 AI 表 | 以业务主从关系和独立生命周期为建表边界，不再为技术中间状态预建业务表 |
| FASHION-ADR-010 | 报价历史 | 由 `fq_quote`、`fq_quote_combo`、`fq_quote_detail` 确认后锁定和复制修订 | 三层已经保存客户、组合、SKU、金额、库存和图片证据，不再另建报价快照表 |
| FASHION-ADR-011 | 导入模板与 AI 反馈 | 固定导入模板由代码或配置维护；首期通用 AI 反馈延期 | 批次固化实际映射即可解释历史；反馈评估不是首期 Agent 执行闭环的必要表 |
| FASHION-ADR-012 | Agent 可靠性持久化 | 租约、fencing、预算、幂等和有限事件语义进入现有 Run / Step 字段 | 不新增预算桶、费用流水、回调收件箱、outbox、checkpoint 或通用事件等技术表 |

## 2 三个项目的职责

| 项目 | 本轮落点 | 负责 | 明确不负责 |
| --- | --- | --- | --- |
| Java 业务项目 | `ruoyi-backend/ruoyi-fashion` | RuoYi 身份/RBAC、客户、商品、当前价、库存、方案、报价、导入、文件元数据、AI Run 控制、预算、幂等、审计和 MySQL 事务 | 不把生成模型结果直接当正式价格、库存或报价 |
| 管理端项目 | `frontend/admin-web/src/views/fashion` 及对应 API/路由 | 商品、数据批次、客户方案、搭配、图片、报价、交付和管理员配置页面 | 不直连 Python，不保存 Provider Secret，不在浏览器确认权限和金额事实 |
| Python AI 项目 | `python/fashion-ai-runtime/` | 类型化需求解析、候选排序、搭配推理、解释、视觉理解、生图 Provider 适配、输出护栏、trace 和 eval | 不直连 MySQL，不自行改变业务状态，不直接对浏览器开放，不计算或确认正式报价 |

同一 Python 代码库以后可以从同一镜像启动 API 进程和 Worker 进程，以便分别扩缩容；这仍是一个项目，不是两个服务仓库。

## 3 依赖方向

```text
内部用户 / Chrome 文件
          │
          ▼
      admin-web
          │  RuoYi Token
          ▼
platform-backend / ruoyi-fashion ─────► MySQL、对象存储
          │  服务身份、最小上下文、deadline、预算
          ▼
 fashion-ai-runtime ─────► 经批准的模型/图片 Provider
          │
          └──────────────► Java Tool Gateway（白名单只读或受控动作）
```

禁止的依赖包括：浏览器直连 Python、Python 直连 MySQL、模型自行访问任意 URL/Shell/文件系统、Python 绕过 Java 写正式方案或报价，以及 Java/Python 各自维护一套可变业务状态。

## 4 首期范围与延期项

P0 保留 PRD 的 17 项需求和 32 项验收条件，并按开发顺序分为商品数据、客户与选品、视觉 AI、确定性报价、交付五个域。视觉 AI 仍是完整首期的一部分，只是排在确定性业务闭环之后接入。

数据库 P0 只采用 v2.3 的 16 张 `fq_*` 业务表：商品资料 1 张、库存 1 张、客户 1 张、报价方案 5 张、导入管理 2 张、AI Agent 6 张。该数量是当前设计边界，不表示这些表已经创建、迁移或通过数据库测试。

以下进入 P1 或新需求：可由管理员动态维护的导入模板、通用 AI 反馈/训练数据管理、多客户/渠道价表、预约价、ERP 实时同步、自研浏览器扩展、Portal/移动端、客户在线接受、订单/支付、超过四槽位、3D/视频，以及按 Agent 拆独立服务。

## 5 仍待落实的生产门

以下选择不影响本地 fail-closed 骨架开发，但在启用 Provider 或共享网络部署前必须完成并取得证据：

- Java/Python 服务认证和密钥轮换方式；
- 解析前请求体限制、文件隔离、SSRF 与恶意内容防护；
- 通用 Agent Run / Step 的 `runAttempt`、`executionLeaseId`、`fencingToken`、委托身份、预算、幂等和有限事件字段持久化；这些语义进入现有两表，不新增技术表；
- 文本模型、视觉模型和生图 Provider 的真实样本、费用、许可、数据保留和降级策略；
- 对象存储、队列、观测、告警、备份恢复及生产部署目标；
- 用户 UAT、上线批准和发布/回滚执行包。

这些门的状态只在 [FEAT-FASHION-001 任务清单](../功能/FEAT-FASHION-001-服装智能选品生产首版/任务清单.md)和[验证记录](../功能/FEAT-FASHION-001-服装智能选品生产首版/验证记录.md)维护。

## 6 变更与恢复

如未来出现同一 SKU 同时需要多套有效价格的真实业务，必须新建需求，补价表主从模型、迁移顺序、消费者兼容和回滚方案，不能直接改变本决策并覆盖现有报价含义。若单一 Python Runtime 的容量或隔离实测不能满足目标，应先按模块和进程隔离验证，再通过新 ADR 决定是否拆服务；本记录不以未经验证的扩展性假设提前拆分。

已归档的 44 表第一版已被明确否决，只能用于追溯历史取舍，禁止作为 DDL、实体、Mapper、迁移脚本或任务拆分的输入。需要恢复其中某项能力时，必须先形成基于 v2.3 的新需求与兼容方案，不能直接恢复旧表结构。本 ADR 的产品与架构边界已经批准；`IMP-01`～`IMP-10` 执行包仍待审核，尚未建库、执行迁移或取得数据库验证与用户验收。
