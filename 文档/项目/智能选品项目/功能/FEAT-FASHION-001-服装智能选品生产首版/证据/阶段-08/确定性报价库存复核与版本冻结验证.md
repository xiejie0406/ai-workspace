## 1. 结论

IMP-08 的实现、自审和最低自动验证已完成，退出门结果为 **Pass**。REQ 12、REQ 13、REQ 14、REQ 15 及 AC 11、AC 12、AC 13、AC 19、AC 20、AC 23、AC 25 已取得生产代码、隔离 MySQL 和自动化场景证据，但不等于用户 UAT、非隔离数据库迁移或生产发布。

报价计算只在 Java 使用 `BigDecimal`、显式 scale 与 `RoundingMode.HALF_UP`；Python 未参与金额、库存或确认。报价确认在公共目录写锁和同一 MySQL 事务中重新读取当前商品、价格、库存、主图、采用图和权限事实，再冻结 `fq_quote`、`fq_quote_combo`、`fq_quote_detail` 三层。没有新增价格版本、库存版本、报价快照或审批表，数据库仍严格为 6 个模块、16 张 `fq_*` 业务表。

## 4. 关键确认场景

1. 报价工作区读取当前事实后，以客户、方案版本、采购量、商务条款、备注、组合视觉、采用图片及各行商品/价格/库存/视觉版本计算精确输入 hash。
2. 正式确认前检查方案头采购量与组合套数、每个尺码行数量、1～4 品类、商品状态、当前价、税率/币种、库存时效、主图权限和采用图复核状态。
3. 采用图片必须匹配当前 `comboVisualHash` 和任务输入 hash，结果需成功、允许用于方案、对象 SHA 一致，且最新人工复核为通过；旧图或失败图不能冻结进正式报价。
4. 销售可直接确认不超过 10% 的普通折扣；超限折扣或任一手工单价需要负责人对精确内容 hash 审批。申请人不能审批自己的请求，过期或内容变化后的审批不能复用。
5. 正式确认使用目录写锁、事务和行锁做最终重读；两次相同输入并发确认只允许一次合法状态推进，相同已确认 hash 可安全幂等返回。
6. 已确认工作区显示冻结单价、库存、图片与金额，同时只把当前事实变化标记为变化，不回写历史值。后续修改通过复制修订完成。

## 5. 执行中发现与修正

1. 首次使用 Windows PowerShell 5 执行隔离脚本时，脚本的 UTF-8 无 BOM 内容被错误解析，失败发生在数据库创建前；改用仓库要求的 PowerShell 7 `pwsh` 后再运行，不将该次解析失败记为数据库验证。
2. 首轮真实 MySQL 场景发现 `JSON_TABLE` 返回列与表字段比较时存在 collation 混用，同时早期 IMP-08 测试商品污染候选数量；查询改为显式兼容 collation，报价专用测试商品改为未确认属性，随后连续完整重跑通过。
3. 自审发现初版未返回固定尺码配比下的最大可供套数；补充备选和合并两种算法，并在库存不足问题中返回可执行上限。
4. 自审发现方案头 `requested_qty` 与组合 `set_qty` 之间缺少显式一致性门；补充 `QUOTE_QTY_MISMATCH` 阻断和单元测试。
5. 自审发现只校验被采用图片的外层状态仍不足；补充结果对象 SHA、使用许可、当前视觉 hash、任务输入 hash 和最新人工复核通过校验。
6. Vitest 曾使用不支持的 `--runInBand` 参数，CLI 在测试运行前退出；去掉该参数后执行标准 `npm run test:unit`，最终 9 files / 35 tests 全过。
7. 数据层允许草稿保存零参考价，以便清晰显示问题；Java 正式确认仍无条件阻断零单价、100% 优惠和零应付。DDL 因此把明细价格检查调整为非负，而不是放宽正式报价规则。
