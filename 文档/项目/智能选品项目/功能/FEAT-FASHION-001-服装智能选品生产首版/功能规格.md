## 4. P0 项目与角色范围

### 4.1 `ruoyi-backend/ruoyi-fashion`

- 复用若依账号、认证、角色、菜单和权限，实施服务端客户归属与字段权限。
- 用 MySQL 保存数据库设计 v2.3 定义的 10 张核心业务表和 6 张 AI 生命周期表；字段、关系和表名不在本规格重复定义。
- 实施当前价格/库存表与导入批次明细的一致事务、乐观并发、业务幂等、预算和费用校验、确认报价三层冻结及下载授权。
- 只把最小必要、带版本的候选上下文交给 Python；收到结果后重新验证并由人工采用。

### 4.2 `frontend/admin-web/src/api/fashion` 与 `frontend/admin-web/src/views/fashion`

- 为内部商品运营、销售和负责人提供商品、导入、方案、搭配、图片复核、报价和交付页面。
- 前端状态不作为权限、价格、库存、预算、采用或报价真相。
- 所有请求只进入 Java API；不得通过配置或浏览器代码绕过 Java 直连 Python。

### 4.3 `fashion-ai-runtime`

- P0 目标能力是需求解析、候选排序、搭配、提示管理、文本/视觉 Provider adapter、输入输出护栏、trace 和 eval。
- 不直连服装业务 MySQL，不读取客户联系人/内部备注，不拥有商品、价格、库存、报价或采用状态；Agent、版本、对话、消息、Run、Run Step 六类生命周期事实也只由 Java/MySQL 持有。
- 当前只实现 disabled 契约骨架；返回 503 是正确 fail-closed 行为，不是需求解析已实现。

## 5. 明确排除与 P1

- `contracts/fashion/` 只保存共享契约，不单独部署。
- `frontend/portal-web/`、`miniapp/interview-mobile/`、Chrome/Edge 扩展及任何浏览器采集插件开发不进入本 Feature P0。
- 首期一个 SKU 一套当前销售价。多客户价、多渠道价、阶梯价、预约价、自动回退和复杂价格优先级统一进入 P1，必须另有需求、迁移和兼容方案。
- 全网爆款发现、销量预测、自动供应商选择、下单、支付、合同签署和客户自助门户不在 P0。

## 6. 完成定义

只有以下条件同时成立，才可将生产 P0 声明为已实现候选：

1. 三个代码项目的 P0 任务均有实际实现及定向验证，Java/MySQL 权威边界无绕行。
2. REQ 01–17 对应的 AC 01–32 形成可追溯证据；未执行项不得标 Pass。
3. 真实 Provider 和视觉 AI 在受控数据、费用和停止条件下完成质量验证，失败样本保留。
4. PPTX 和下载在指定桌面软件中实际打开、编辑、另存，并核对内容与已确认报价三层记录一致。
5. 用户或业务负责人在[验收记录](验收记录.md)给出明确结论；进入开发的批准不能替代验收。
