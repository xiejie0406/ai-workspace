## 1. 文档目的和使用规则

本文件回答五个问题：十个阶段分别解决哪些需求、实现哪些业务模块、落到哪些目标文件、使用什么技术、做到什么程度才能进入下一阶段。它是 FEAT-APS-001 唯一实施任务事实源；其他文档只维护产品、架构、数据库或实际证据，不另建第二份十阶段计划。

`IMP-01`～`IMP-10` 是交付顺序，不是协作规范中的治理 Stage 1～10。2026-09-12 用户已批准本计划、推荐基线和列明的本地实施影响；当前治理状态为 **Stage 7 / InProgress**，从 IMP-01 开始。

状态定义：

| 状态 | 含义 |
| --- | --- |
| `Todo` | 未开始，或虽有设计/原型但生产实现与验证未完成 |
| `InProgress` | 已在批准范围内实施，尚未满足本阶段出口 |
| `Blocked` | 存在不能在当前授权或事实条件下安全解决的阻断 |
| `Done` | 列明产物已经实现，最小验证实际通过，失败和限制已记录 |

文件存在、接口返回 200、页面能打开、求解器返回一组时间、原型已演示，都不能单独把阶段改为 `Done`。每个阶段至少同时满足：实现完成、自审完成、阶段证据通过、阻断问题关闭、限制如实记录。

## 2. P0 目标、结果和非目标

### 2.1 十阶段完成后应具备的能力

P0 最终应形成一个单站点、多车间的生产排程闭环：

1. 维护车间、工作中心、人员/设备/工位/工具、单表多技能和绝对可用时间窗。
2. 维护产品、工序阶段、资源要求和版本化路线 DAG；把多产品订单稳定展开为生产批、任务、依赖和基础物料需求。
3. 在求解前发现缺路线、缺工时、缺资源、缺日历、循环、单位和数量关系错误，并返回可定位的业务原因。
4. 用 OR-Tools CP-SAT 在人员、设备、容量、日历、前置、数量和锁定约束下生成有限产能候选；状态区分可行、最优、超时有解、超时无解和证明无解。
5. 支持数量门槛、连续转移批、受控拆批、人工共享加工批、人机分阶段占用、不可中断和受控可中断。
6. 提供设备、人员、车间/工序三类甘特，支持影响分析、人工计划、时间/资源/全锁、版本比较和系统内原子发布。
7. 支持开工、暂停、恢复、完工、真实资源占用、部分报工、待检/合格/不良、冲正、返工/补产和不可变数量事件。
8. 形成车间每日生产表、人力累计产能、峰值缺口、产品行/订单预计完成和原因解释。
9. 通过权限、幂等、并发、故障恢复、容量、安全、浏览器和用户验收门，并保留可审计证据。

### 2.2 本十阶段明确不做

- 不做多工厂/跨厂协同，不恢复 `aps_factory`、`factory_id`；一个 APS 业务库服务一个生产站点。
- 不做完整 BOM、MRP、采购、库存、工资、QMS/CAPA、维修工单或通用 BI。
- 不执行 `SAME_START` 同步组；首版必须把来源同步关系持久保留，返回 `UNSUPPORTED_SYNC_RULE` 并阻止数据就绪和发布，不能静默丢失或降级。其他同步类型仍不在 P0 契约中。
- 不做具名人员/设备速率、人员组合效率、多机看护、顺序相关换型、清洗 campaign 或多维批容量。
- 不做多 Worker 抢占、续租、自动接管和旧 Worker fencing；29 表不足以支持这些语义。用户已批准将 APS-AC-22 调整为 P1，引擎设计已同步；P0 环境禁止启动第二 Worker。
- 未确定真实接收方、ACK、重试和补偿责任前，不做 ERP/MES 可靠外发，不用假 Outbox 声称已下达。用户已批准将该能力转为 P1；PRD AC-15 当前只验系统内并发与原子发布。
- 不让浏览器直接访问 Worker 或数据库，不把 DHTMLX/vis 原生对象写进领域模型、API 或 MySQL。
- 不直接复用原型的 `localStorage` 与 `javascript-lp-solver` 作为生产实现。
- 不在本计划中执行真实生产迁移、真实账号联调、费用、Git 写操作或正式发布。

### 15.1 已批准开工方案

以下口径由现有 REQ-07、BR-38～44、AC-17～19 和 M25～M29 共同推导，并已由用户于 2026-09-13 接受。后续按本节实现，不在代码、页面和数据库中各维护一套状态规则。

本轮还用官方制造系统资料做了交叉检查：Odoo 的工作单暂停会结束当前计时记录，恢复时新建计时记录，支持 M26 多实际段而不是覆盖一段；Dynamics 365 支持部分完工量和错误量，进入最终“报告为完工”后不再接收普通数量报告，支持 M27 区分进度报工与最终报工；SAP 将质量检验库存和冻结库存明确排除在非限制使用库存之外，支持待检/隔离量不进入下游可用量；SAP 的完工确认撤销不会自动撤销相关业务状态，支持以反向事件重算聚合状态而不是倒退历史 run。参考：[Odoo 工作单](https://www.odoo.com/documentation/master/applications/inventory_and_mrp/manufacturing/basic_setup/manufacturing_work_orders.html)、[Dynamics 365 完工报告](https://learn.microsoft.com/en-us/dynamics365/supply-chain/production-control/report-production-orders-as-finished)、[SAP 库存状态](https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/91b21005dded4984bcccf4a69ae1300c/fc62bd534f22b44ce10000000a174cb4.html)、[SAP 完工确认撤销](https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/21aead0c98bd4755abdacd91c99e3393/5287bf53f106b44ce10000000a174cb4.html)。这些资料只验证通用边界，最终产品口径仍以本 Feature 经用户确认的规则为准。

执行 run 状态机：

```text
创建派工
  ↓
READY ──开工──→ RUNNING ──暂停──→ PAUSED ──恢复──→ RUNNING
  │                 │
  │                 ├─完工报工且需质检──→ WAIT_QUALITY ──全部处置完成──→ COMPLETED
  │                 └─完工报工且无需质检、数量已放行──────────────→ COMPLETED
  └─未开工取消──→ CANCELLED

PAUSED ──受控取消──→ CANCELLED
```

状态规则：

| 当前状态 | 允许动作 | 必须同时满足 | 明确拒绝 |
| --- | --- | --- | --- |
| `READY` | 开工、未开工取消 | 作业来自创建 run 时的当前正式计划；开工时再次检查任务前置、物料、技能、日历、设备状态和实际占用 | 候选计划开工、同作业存在另一活动 run、资源已被占用、`SAME_START` 未支持约束 |
| `RUNNING` | 部分报工、操作人/资源受控切换、阶段推进、暂停、末阶段完工报工 | 所有实际段写 M26；换人换机先关闭原占用，再校验并打开新占用；阶段推进原子关闭当前阶段占用并打开下一计划阶段；报工累计不得超过成员剩余量 | 直接取消、非末阶段完工、跳过阶段、倒填覆盖既有事实、用计划结束时间伪造实际结束 |
| `PAUSED` | 恢复、受控取消 | 暂停先关闭活动占用；工艺要求保留的设备/工装以 `PAUSE_HOLD` 继续占用；恢复重新校验资源 | 自动释放需保留资源、无处置地取消已有产出 |
| `WAIT_QUALITY` | 放行、隔离、拒收、返工/报废/让步使用处置 | 所有产出均有最终数量去向；返工或补产在同事务创建有来源血缘的新 M15/M16 | 取消运行、把待检量直接提供给下游 |
| `COMPLETED`、`CANCELLED` | 只读、合法更正/冲正 | 更正追加新事实，不修改 M25 终态；重新计算任务、批次和订单聚合条件 | 恢复原 run、物理删除、原地改报工数量 |

补充约束：

1. 新 run 只能从当时唯一当前 `PUBLISHED` 作业创建；已开工 run 即使来源计划后来变为 `SUPERSEDED`，其真实执行仍可继续和报工，但旧版本不得再创建新 run。
2. `READY → CANCELLED` 可直接执行；`PAUSED → CANCELLED` 若已有产出，必须在同一事务保留产出并为未完成量创建补产或明确剩余处置。`RUNNING` 必须先暂停，`WAIT_QUALITY` 必须先完成质量处置，不能用取消掩盖在制品。
3. 同一计划作业最多存在一个非终态 run，`run_no` 按作业递增。前一 run 受控取消后，只能为“计划量减有效累计加工量减其他非终态分配量”的剩余数量创建下一 run；计划已被替换时，剩余量必须进入基于真实执行事实生成的新正式版本，不能继续从旧版本派工。
4. M16 任务状态按全部 run 和有效数量账聚合推进为 `DISPATCHED/RUNNING/PAUSED/WAIT_QUALITY/COMPLETED/CANCELLED`；M15、M14、M13 只在全部必需子项满足数量和质量条件后逐级完成，单个产品或单次 run 完成不等于订单完成。终态 run 的报工被冲正后，run 本身不恢复运行，但任务/批次/订单聚合完成条件必须重算，出现的缺口进入待处置、返工或补产。
5. 生命周期命令携带 `expectedRowVersion`。同一目标状态的响应丢失重试返回当前结果；在后续状态变化后到达的旧命令因行版本过期而拒绝。报工、质量数量事件分别由 M27/M29 的唯一 `request_id` 做持久幂等。
6. 权限沿用已预置五个稳定码：`execution:view`；`execution:start` 覆盖创建、开工、恢复和受控换人换机；`execution:pause` 覆盖暂停与取消；`execution:report` 覆盖进度/完工报工及报工更正；`execution:quality` 覆盖放行、隔离、拒收和处置。服务端仍叠加车间/工作中心数据范围。
7. 开工只打开最小 `segment_no` 的资源占用；暂停/恢复只处理当前阶段，换资源保留原 `source_plan_allocation_id`；阶段推进必须携带幂等键和 `expectedRowVersion`，同一活动阶段只能推进到紧邻下一阶段。只有最后计划阶段允许完工报工，避免把中间阶段完成误写为整个 run 完工。

数量和质量账：

| 动作 | M27 报工 | M28 产出批投影 | M29 不可变事件 | 下游可用量 |
| --- | --- | --- | --- | --- |
| 进度/完工报工 | `processed = good + pending + rejected`；累计有效加工量不超过成员/run 分配量 | 同一报工按合格、待检、拒收最多拆成三条同质产出批，ID 由报工及桶稳定派生 | 每条产出批先记 `PRODUCE: NULL → PENDING_QUALITY` | 仍为 0，直到满足质量策略 |
| 无独立质检的合格量 | 保存授权报工事实 | 合格产出批变为 `RELEASED` | 同事务记 `QUALITY_RELEASE: PENDING_QUALITY → AVAILABLE` | 只增加本次合格放行量 |
| 需要独立质检 | 报工只表达现场分类 | 保持 `PENDING` 或被质量人员置 `HOLD` | 隔离本身不搬数量；放行时才记 `QUALITY_RELEASE` | 待检/隔离均为 0 |
| 报废 | 不改原报工 | 处置为 `SCRAP`，增加 `scrapped_qty` | `SCRAP: PENDING_QUALITY/AVAILABLE/RESERVED → SCRAPPED` | 对应量扣除；批准补产时创建 `REPLENISH` 批 |
| 返工 | 不改原报工 | 处置为 `REWORK`，来源量进入不可交付处置桶 | `ADJUST: PENDING_QUALITY → ADJUSTMENT`，原因必填 | 创建带父批和来源理由的 `REWORK` 批；返工合格只按最终末端净放行量计交付 |
| 让步使用 | 不改原报工 | 处置为 `USE_AS_IS`，记录批准人和时间 | `QUALITY_RELEASE: PENDING_QUALITY → AVAILABLE` | 批准后增加可用量 |
| 报工更正 | 新增 `CORRECTION`，内容是被更正记录的替代快照并指向当前有效记录 | 原产出批关闭，新产出批由更正记录重新生成 | 先按原事件反向追加 `REVERSE`，再追加更正后的事件；原记录不删不改 | 由完整事件链复算，事务失败整体回滚 |

M28 的 `available/reserved/consumed/scrapped` 是由 M29 事件复算并在同事务维护的当前投影，不是第二套可独立编辑的数量真相。预留、取消预留、投入、转序、报废、调整和冲正均先校验可用余额，任何时点不得出现负桶或下游累计投入超过已分配放行量。

执行水位不新增第 30 张表：每次 M25～M29 业务事务都锁定并递增所属 M25 `row_version`，当前单站点 `executionRevision = SUM(row_version + 1)`。新 run 使水位增加 1，任一后续执行/质量事务也至少增加 1；输入编译在一致性事务中由服务端计算该值，不信任客户端自报。不同 run 可并发提交，聚合水位仍随每笔已提交事实单调增加；旧候选因此变成 `STALE_INPUT`。

执行数量账使用不增加表的生产 V004：当前 V001 的 M29 `REVERSE` 形状要求起止桶都非空，无法严格冲正 `PRODUCE: NULL → PENDING_QUALITY`。V004 只调整该 CHECK，允许反向事件精确交换原事件的起止桶（包括一端为 `NULL`）；服务层锁定原事件、校验同产出批/单位/数量和相反方向，`uk_quantity_event_reversal` 保证每条原事件最多冲正一次。活动 run carry 使用生产 V005，为 M20 `aps_plan_job` 增加可空 `carry_run_id`、唯一约束和指向 M25 的外键，并约束只有 `CARRY` 作业可携带该值。阶段化执行使用生产 V006，为 M26 增加可空 `source_plan_allocation_id` 及 `(plan_segment_id, source_plan_allocation_id)` 复合外键；新记录必须保存来源分配，历史记录只在分段和资源唯一吻合时安全回填，否则保持 `NULL/UNKNOWN`，不得猜测。测试专用前进探针顺延为 V007。V001 保持不可变，表数仍为 29，当前 schema 为 66 个外键。

## 20. 失败、停止和恢复原则

1. migration 只前进修复；破坏性变更前需备份和恢复演练，不把反向 SQL 当唯一恢复方案。
2. API、Worker、菜单和新页面通过功能开关启用；失败时可停止 Worker、隐藏入口，当前正式计划保持不变。
3. 候选可标废弃；正式计划历史不删除。需要恢复时创建并发布替代版本，保留原版本。
4. 报工、实际占用、质量和数量只允许更正/冲正，不允许删除或被求解器覆盖。
5. 外部写入默认关闭；未确定接收方、ACK、幂等和补偿责任前，不声称可靠下达。
6. OR-Tools、JDK、甘特组件升级必须重跑相同黄金集、性能与许可证检查；不能用升级顺手改变业务口径。
7. 需要增加第 30 张业务表、第二 Worker、MQ、跨站点或新外部写入时，停止受影响实现并回到设计/授权门。
8. 需要真实账号、真实业务数据、费用、生产迁移、发布或 Git 写操作时，必须取得相应明确授权。

交付出口：订单能够修改合法草稿、展开、释放并进入完整预检；缺技能、无窗口、路线缺项、单位不符或关系不支持均有对象名称和修正路径；不要求用户编写SolverInput或填写内部标识。

**第四批：排程工作台与正式发布对齐新设计。**

1. 复用PlanLauncher与计划目录；按订单、车间名称选择，候选和当前正式版可辨，目录受权限过滤。现有最近200项限制明确展示；确需搜索更早版本时补服务端过滤/分页，不能在浏览器只筛前200条却称查询全部历史。
2. 请求进度、取消、失败和重新排程连续可用；三视图共享同一筛选集合和选中作业，显示订单、工序、人机、数量、时段与未排原因。
3. 人工调整、锁定、插单、拆合批及版本比较组织成对应业务动作，展示影响并定位冲突；沿用原受控草稿和独立校验。
4. 发布前汇总当前基线、输入新鲜度、未排及变更影响；服务端继续复验并原子切换唯一当前正式版。回执后刷新正式状态与派工列表，过期或并发冲突保留原版本。

交付出口：计划员从订单进入候选、解释问题、审阅调整并发布，随后直接打开正式作业派工；过期、越权、未校验候选和不合法结构调整保持拒绝。

**第五批：现场执行与质量数量闭环可操作。**

1. 现场入口以正式作业和执行单列表进入详情；按订单、工序、资源及状态查询，替换普通入口的Run标识输入。共享加工批的报工成员必须明确选择；加载不到成员时保留缺关系的拒绝说明，不用手填标识绕过。
2. 派工、开停工和阶段推进展示计划依据、实际资源及剩余数量；换资源只列具备资格和可用条件的候选，服务端复验状态、日历、资格及实际占用。
3. 报工、质量处置、数量预留/转移/消耗、冲正和返工补产从有来源的批、需求、目标任务或执行单选择；操作人取已认证身份或合法代理选择，不能让自由文本替代审计身份。
4. 复用ExecutionLifecycleService、ProductionReportingService、RecoveryOrderService及既有数量事务；提交去重、余额并发与拒绝恢复由服务端维护，前端只预提示并展示回执。

交付出口：现场人员从派工到部分报工、完工及质量处置连续操作；待检/隔离不进入下游可用量；超量、重复消耗、非法阶段和过期版本被拒绝；数量流水能回查来源及冲正关系。

**第六批：报表、权限及跨模块衔接收口。**

1. 日报、人力和订单交期改用业务名称筛选；展示站点时区、截止水位、日冻结/当前/实际来源和单位，沿用原人时去重、峰值及UNKNOWN ETA口径。
2. 从汇总下钻到订单、任务、计划作业、实际占用或产出批；CSV和打印沿用同一筛选及权限范围，不能只核对导出文件能生成。
3. 核对普通角色的菜单、按钮、目录、详情、候选、保存和导出范围；服务端做最终裁决，空范围不得查询全站点。对当前订单等列表/详情逐一检查范围，不能因新增选择组件仅做前端过滤。
4. 串联前五批的返回、刷新、异常恢复和已通过基线；构建受影响组件并只更新已核实的APS运行版本。技术检查及开发自测完成后整理实际缺口，正式业务验收按用户后续安排启动。

交付出口：管理人员按名称查询结果并能解释明细来源；各角色只见授权范围；技术、联机、业务验收和用户接受分别记录。

### 27.4 前后端模块与必要改动

后台处理统一按“认证及车间范围 → 校验对象、状态和版本 → 事务或可信只读编译 → 业务回执 → 列表/详情回查”执行。目录在服务端过滤，不返回对象后再由前端删除；业务冲突返回可定位问题，系统失败保留原事实和原输入。

### 27.5 检查、版本交付与停止恢复

每批先核对改动和既有证据，保护共享工作区及其他项目修改；完成对应功能的定向Java测试、APS类型检查和必要单元/浏览器开发检查。受影响契约同时查消费者及正反例；不为同义字段或可逆文案生成镜像测试。当前可用命令入口为`npm run typecheck:aps`、`npm run test:unit:aps`、`npm run test:e2e:aps`及相应Maven模块定向测试，执行范围按改动选择。

运行更新遵循启动指南：只更新已确认归属的APS API/Worker或前端组件，保留当前包和配置，核对实际版本及单Worker身份；共享打包先核对其他项目正在使用的产物，不能从共享target任取最新包。原库前提未满足时只记录未联机，不从构建通过推断完整闭环。

旧日历枚举、已生效工艺、冻结订单任务、历史计划、执行与数量账保留；出现权限泄漏、数量不守恒、计划不原子或输入语义改变时停止受影响交付并修复。界面/查询回退到保留版本，避免覆盖后来修改；原库DDL不能承诺整批回滚，也不自动整库恢复覆盖其他项目的数据。

设计仍只在产品正文维护，进度只在本任务清单维护，技术事实写验证记录，业务及用户决定写验收记录。每批交付可查看页面、版本依据和实际缺口；既有通过基线只在未受影响且条件一致时沿用。用户先前暂停正式验收的指令继续有效，本方案不开始验收，不执行生产发布、外部业务写入或Git写动作。

### 27.6 后续业务验收方法

以下是将来验证六批交付的方法，不填写当前通过结果；完整规则和独立样例引用唯一设计第15章。业务写入使用经确认的角色、对象及数据范围。

| 业务点 | 前提与操作 | 正确结果及核对 |
|---|---|---|
| 资源与日历可维护 | 资源维护角色，建立具体人员及设备；添加有效技能、可用窗口和一段不可用时间，再编辑并回查 | 原窗口保留，净窗口扣减正确；结束不晚于开始时拒绝且不丢输入；截图资源详情/错误状态，并核对实际保存值及UTC转换 |
| 工艺完整且版本隔离 | 工艺角色，准备已具备技能的人员设备；配置准备/运行/卸料与人机要求，生效路线，再复制新版本 | 阶段、时长及角色准确回读；旧订单仍冻结原版本；环路或缺必要资源拒绝；截图阶段/资源表单及路线校验 |
| 订单完整预检 | 计划角色，建立多产品订单并展开释放；故意缺一项技能或窗口，执行完整预检后由定位入口修正 | 找到具体对象并返回原选择范围；资源检查不冒充完整预检；重查通过后仍在创建/发布复验事实；核对任务网络与问题来源 |
| 计划可解释并安全发布 | 使用独立确定时长、日历和依赖的样本；求解、调整、比较、发布；再用过期事实尝试发布 | 候选符合独立预期，只有一个当前正式版；过期版本被拒绝且原版本保持；截图甘特、影响与拒绝，并核对正式基线 |
| 执行与数量有来源 | 正式作业存在，现场/质量角色授权；部分报工、质量放行、目标选择与流转；尝试超量或重复消耗 | 待检和隔离不进入可用量；余额、来源和冲正一致；非法请求不改原账；截图报工/质量/流转，并独立核对数量 |
| 报表与权限一致 | 至少两个不同范围的角色和订单，具备计划与实际事实；按名称查询、下钻、导出并尝试读取其他范围 | 人时不重复，未知交期明确；汇总与明细一致；越权目录/详情/导出均拒绝；页面与实际数据分别核对 |

拟执行顺序：联机前提核对 → 第一批资源 → 第二批工艺 → 第三批订单与就绪 → 第四批排程发布 → 第五批执行质量 → 第六批报表收口。第一批开发可以从资源表单与技能/日历编辑开始，后续每批承接前一批已可回查的输入。
