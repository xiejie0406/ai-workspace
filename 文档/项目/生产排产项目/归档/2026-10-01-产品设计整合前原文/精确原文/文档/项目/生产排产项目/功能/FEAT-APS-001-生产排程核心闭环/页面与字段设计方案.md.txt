## 需求与业务逻辑

本系统让计划员明确订单要生产什么、数量和交期，按产品工艺选择合格人员与设备，在日历和已有占用允许的时间内安排生产，再由正式计划、派工、报工和质量数量记录跟踪实际完成。

1. 车间、产线和工作中心表达组织及工作范围；具体人员、设备、工位、工装才是被占用的资源。
2. 产品关联生效工艺路线；工序分为准备、加工、卸料等阶段，各阶段说明时间和所需资源。
3. 订单提供产品数量与交期，展开并释放为可排任务、批次、依赖和物料需求。
4. 排程生成候选，负责人复验并发布为正式计划；现场据此派工、开停和报工。
5. 合格、待检、报废和数量流转分别留痕，报表读取这些事实，反馈后续重排与交期判断。

本次重点补齐组织基本信息、人员/设备业务资料、专属产能、列表到新增的完整交互，以及订单到正式计划再到报工的页面衔接。产线实体、资源专属产能及新查询入口属于拟补设计；原有接口按现有契约复用。认可本文的组织方式不代表新增数据模型、复杂组合效率或全部实施范围已获批准。

### 产能口径

产能必须对应具体资源、产品规格、工序、阶段和有效版本。每小时/每批是维护口径；上午、下午和一天是选择日期后按净日历与已有占用计算的结果。

| 业务例子 | 前提 | 正确计算 |
|---|---|---|
| 张师傅焊锡主控板A，每小时60件 | 净4小时，没有准备及其他任务 | 上午理论处理240件 |
| 相同资源和产品工序 | 净8小时，相同条件 | 全天理论处理480件；两技能共用这8小时 |
| 焊锡100件，另计准备20分钟 | 每小时60件，卸料0 | 20+100/60×60=120分钟 |
| 炉每批最多200件，每批4小时 | 周期含装卸，连续净8小时，允许尾批 | 最多2批400件；300件需求仍用2批8小时 |
| 每批另计30分钟准备卸料 | 连续净8小时 | 完成1整批；不能按400件计算 |
| 不可中断炉需连续4小时 | 可用窗口分别只有3小时、3小时 | 不能拼成一整批，即使合计6小时 |

这些是给定条件的标准处理量，实际合格与放行量来自执行和质量记录；串行工位、不同产品单位和多人组合效率不得任意相加。

## 共用界面与后台约定

界面沿用管理端的表格、筛选、抽屉和表单习惯。名称和业务编码优先，关联标识自动携带。列表列是展示字段；新增和编辑各有独立输入定义，汇总数量、状态流转与审计信息由后台产生。长表在表格区域横向查看，详情展示完整内容。

列表默认按业务更新时间倒序，主数据可按编码排序；分页提供每页20、50、100条，返回后保持筛选与页码。已有集合查询若未支持分页，按模块接口说明补充页码、排序白名单及总数，不能假定已实现。查询与导出均受后台数据范围约束。

表单有可见标签、必填条件、默认值与单位。保存先检查输入，提交中禁重复；失败保留输入并定位字段，取消不写入，版本冲突提示重新读取。时间按站点时区显示，后台统一存储；数量单位必须匹配，禁止无规则换算。

### 共用技术与职责

| 部分 | 技术 | 处理职责 |
|---|---|---|
| 界面 | Vue 3、TypeScript、Element Plus；沿用 Pinia 和 Axios | 独立列表及表单、关联选择器、状态反馈、查询回查；提交业务意图 |
| 业务后台 | 若依、Spring Boot、MyBatis | 校验权限和输入、编排用例、读写业务资料、处理版本与事务 |
| 数据 | MySQL、InnoDB、Flyway | 唯一业务事实，约束和向前迁移；平台身份逻辑关联 |
| 自动排程 | 独立Java求解进程、OR-Tools CP-SAT | 根据可信快照求解，受时间/线程限制，整体保存候选 |
| 独立检查 | 独立约束校验器 | 不依赖求解器的假定，复算资源、日历、数量、依赖及发布条件 |
| 排程图 | DHTMLX Gantt、vis-timeline 的现有适配层 | 工序、设备和人员视图共用同一计划事实 |

精确版本、模块分层及运行方式沿用[引擎设计第2节](../../架构/APS排程引擎需求与技术设计.md#2-技术决定)。以下“已有契约”仅表示接口已定义；运行及业务结果由后续验收另记。拟补接口路径是设计候选，实施前同步唯一[接口契约](../../../../../contracts/aps/openapi/aps-api-v1.yaml)。

## 1. 资源与日历

### 1.1 模块用途与业务流程

1. 先维护车间、产线和中心基本信息，再登记唯一的人员、设备、工位。
2. 为具体资源维护资格、产品工序产能与绝对可用窗口。
3. 后台将资格、产能版本和净日历交给工艺选择与排程计算。

### 1.5 后端接口与数据处理

1. 车间/中心/资源沿用已有资料表，人员和设备按类型分列表；平台账号仅逻辑关联。
2. 产线及资源专属产能使用独立候选模型，不把同时装载容量改名当生产速率。
3. 产线归属须与车间一致；资格与产能有效期共同过滤资源；同一人员始终只占一条时间轴。
4. 产能小时方式换算为每件时长；批次方式按尾批、准备和周期口径计算；上午/全天产量由净日历推导。
5. 修改资格、产能或日历后，标出受影响候选并触发重新检查；旧正式计划保存冻结的解释版本。

### 1.6 实施顺序与业务验收例子

实施顺序：

1. 确认产线关系、产能粒度和组合效率边界。
2. 补数据模型、约束及向前迁移；定义输入输出契约。
3. 完成资料保存、查询、资格/有效期校验及净日历。
4. 分别实现列表和专用表单，接上权限、选择器和回查。
5. 把生效产能版本接入输入快照、求解时长和独立校验。

**1. 维护组织和具体资源**

- 前提：启用车间、一个中心及可选产线；测试人员张师傅。
- 操作：新增人员、关联焊锡技能，再重新打开详情。
- 预期：一人一个稳定身份；基本资料、资格可回查；列表资源数从记录统计。
- 核对：人员详情和中心关联列表；确认无重复资源；页面保存后重新打开，计算项按前述规则独立复算。
- 应保留的页面证据：本业务列表/详情及关键反馈，另保留必要的读取或数量对账。

**2. 按小时与批次维护产能**

- 前提：主控板A、焊锡工序；每小时60件，另计准备20分钟。
- 操作：新增并生效产能；计算100件任务；切换批次模式录200件/4小时。
- 预期：100件焊锡占120分钟；小时和批次输入互斥；缺必填或有效期冲突拒绝。
- 核对：表单错误位置、保存后详情及独立时长复算；页面保存后重新打开，计算项按前述规则独立复算。
- 应保留的页面证据：本业务列表/详情及关键反馈，另保留必要的读取或数量对账。

**3. 日历与技能不重复累计**

- 前提：同一人焊锡和装配两技能；净8小时已排2小时。
- 操作：查看当天剩余，维护请假后重新检查。
- 预期：剩余6小时；同一人两技能不产生16小时可用；不能跨不可中断窗口硬拼批次。
- 核对：净日历、人员负荷和受影响计划；页面保存后重新打开，计算项按前述规则独立复算。
- 应保留的页面证据：本业务列表/详情及关键反馈，另保留必要的读取或数量对账。

## 2. 工艺与产品

### 2.1 模块用途与业务流程

1. 建立产品单位和可复用工序，按阶段维护时间、人员和设备要求。
2. 在草稿路线中加入节点与依赖，完成检查后发布具体版本。
3. 订单选择生效路线版本，展开时冻结工序和数量条件。

### 2.6 实施顺序与业务验收例子

实施顺序：

1. 完善产品、工序与路线专用表单，拆出阶段和资源要求子表。
2. 复用完整工序和路线图契约，补选择器与错误字段定位。
3. 实现草稿检查、发布和复制版本流程。
4. 用多阶段人机占用及依赖反例定向验证。

**1. 产品与工艺完整维护**

- 前提：产品单位为件，具备焊锡工序和合格人员。
- 操作：新增路线，添加焊锡→装配→终检，检查并发布。
- 预期：节点依赖无循环；阶段时长和资源要求可回查；生效版本可被订单选择。
- 核对：路线图、阶段表及发布后详情；页面保存后重新打开，计算项按前述规则独立复算。
- 应保留的页面证据：本业务列表/详情及关键反馈，另保留必要的读取或数量对账。

**2. 拒绝非法路线及保留历史**

- 前提：已有生效路线第一版。
- 操作：在新草稿形成循环；再复制第二版调整工序。
- 预期：循环定位到具体节点；第一版仍保持不变；已展开订单不自动迁移。
- 核对：校验问题与两版路线详情；页面保存后重新打开，计算项按前述规则独立复算。
- 应保留的页面证据：本业务列表/详情及关键反馈，另保留必要的读取或数量对账。

### 3.4 编辑、详情和其他操作

**生产订单列表**：

未释放草稿可按候选编辑契约修改；已展开/释放结构采用差异确认、路线迁移或受控调整。派生结果不能直接手改。

详情补充：

- customerCode、externalId、备注、产品行、来源记录。
- 产品行自己的交期/最早开工时间优先规则须在编辑帮助明确。
- 仅对可排范围选择订单；订单结构释放不等于正式计划发布。

**订单产品行列表**：

未释放草稿可按候选编辑契约修改；已展开/释放结构采用差异确认、路线迁移或受控调整。派生结果不能直接手改。

详情补充：

- 每条组件/转移输入：demandNo、targetNodeCode、itemId、sourceLineNo、sourceNodeCode、demandType、requiredQtyPerUnit、uomCode、transferBatchQty。
- 跨产品关系：predecessorLineNo、predecessorNodeCode、successorNodeCode、dependencyType、thresholdQty、thresholdRatio、transferBatchQty、lagSeconds、consumesOutput。

### 5.5 后端接口与数据处理

### 5.6 实施顺序与业务验收例子

实施顺序：

1. 补请求/候选查询目录和业务选择入口。
2. 将资源产能版本接入不可变输入与求解时长。
3. 同步独立校验规则、错误解释和整体结果事务。
4. 补表单调整、人工计划锁和方案对比交互。
5. 验证人员互斥、批次窗口、过期输入与取消恢复。

**1. 生成可复算候选**

- 前提：主控板A100件；张师傅60件/小时，准备20分钟；净窗口充足。
- 操作：选择订单生成候选，打开人员/设备/工序视图及任务表。
- 预期：张师傅对应焊锡占120分钟；人员不重叠，前置和数量释放成立；三视图身份一致。
- 核对：三视图、任务明细及独立约束复算；页面保存后重新打开，计算项按前述规则独立复算。

### 7.6 实施顺序与业务验收例子

实施顺序：

1. 接通正式作业→待派工→执行单的选择链。
2. 按允许状态设计开停、换资源、阶段推进表单。
3. 分别实现报工、质量与数量动作，回查完整事实链。
4. 验证数量守恒、幂等、并发、非法状态和更正恢复。

**1. 派工开停与真实占用**

- 前提：当前正式作业100件，资源资格及净窗口满足。
- 操作：派工后开工、暂停、恢复并换人，查看占用。
- 预期：不伪造计划时间为实际时间；暂停恢复形成可追的实际段；来源分配保持。
- 核对：执行状态及实际占用列表；页面保存后重新打开，计算项按前述规则独立复算。
- 应保留的页面证据：本业务列表/详情及关键反馈，另保留必要的读取或数量对账。

**2. 报工、待检与数量守恒**

- 前提：执行单允许报工，数量100件。
- 操作：报工100：合格80、待检20；查看两个质量批；尝试下游使用待检量。
- 预期：加工量100，合格80和待检20分别追溯；待检不可下游使用；重复提交不重复产出。
- 核对：报工详情、质量批及数量事件/余额对账；页面保存后重新打开，计算项按前述规则独立复算。
- 应保留的页面证据：本业务列表/详情及关键反馈，另保留必要的读取或数量对账。

**3. 更正与质量恢复**

- 前提：有已报工记录及可处置待检量。
- 操作：追加更正原因，放行部分待检或生成返工补产。
- 预期：原记录保留；有效聚合与反向事件一致；返工批有父批来源。
- 核对：更正链、质量结果和恢复任务；页面保存后重新打开，计算项按前述规则独立复算。
- 应保留的页面证据：本业务列表/详情及关键反馈，另保留必要的读取或数量对账。

### 9.1 模块用途与业务流程

## 12. 本轮已批准的主流程衔接

2026-10-01 用户在本项目对话明确批准先修复“按订单/车间名称发起排程、选择候选或正式计划、从正式作业进入派工”的最小范围。新增产线、专属产能及第11节其他业务决定仍按原范围待确认。

### 需求与业务逻辑

计划员已有有效产品、路线、资源、日历和已释放订单后，在工作台按业务名称选择车间和订单，填写排程窗口并发起现有求解请求。请求进入等待或求解状态，页面定时查询到终态，连接失败保留请求供手动恢复；可行候选必须经过现有复验和系统内发布，才成为派工依据。现场从正式计划作业选择分配数量，不需要复制内部标识。旧正式版本、超量、重复活动派工及无权操作继续由原后台规则拒绝。

### 前端界面设计

入口仍为“生产排产系统→生产排程工作台”和“现场执行”。工作台新增新建排程表单、可检索计划选择与求解状态；正式计划新增作业表及创建派工入口。现场按深链自动带入计划/作业，也可选择当前正式版本，单位随作业读取；报工成员从该作业成员读取。旧高级标识输入保留兼容。加载、空资料、就绪失败、连接中断、取消及终态分别提示，自动查询在页面离开、终态、网络失败或等待上限后停止。

![主流程衔接设计图](线框图/主流程衔接.svg)

前端修改计划客户端和类型、工作台及现场执行页；新增工作台内的排程选择组件，复用现有车间/订单列表，不修改管理端公共页面、公共路由或共享样式。发起排程的站点默认当前测试站点，可填写部署站点；时间输入按本机时区转换为 UTC，窗口起止和非空选择先在表单校验，硬约束仍由服务端独立校验。

### 后台处理设计

新增 `GET /api/aps/v1/plan-versions`，权限沿用 `aps:planning:view`，只返回版本摘要、请求标识和状态。查询先按冻结输入中的**全部车间**过滤，再按版本倒序取最近200项；没有可见车间时返回空集合，不读其他范围的计划。详情、求解状态、取消、发布和执行单创建全部复用已有接口，MySQL保持唯一事实源，不新增表、不修改迁移或真实角色授权。

修改 APS 工作台控制器、应用查询服务、计划仓储端口及 MySQL 查询适配器，维护现有 OpenAPI；其余求解及正式发布规则沿用既有实现。客户端只提交选择和参数，资源范围、状态和数量合法性由后台裁决。

### 实施步骤与业务验收方法

先补范围过滤查询和契约，再接页面发起/状态恢复及正式作业派工。Java在独立本机构建目录完成定向检查；更新仅排产 API 的专属运行副本，保留旧包和配置，Worker没有行为修改时复用现有进程。验证先核对合成样本及独立预期，再从实际管理端选择订单、发起排程、读取候选、发布、刷新恢复并进入派工；证明主流程无需手填 UUID。超量派工、无权限和空范围另做定向检查。实际截图、计算回读和结果另记在验收记录及本轮证据中，不将设计图计作实际截图。
