## 1. 要回答的核心问题

排程引擎必须用同一套可复算逻辑回答：

1. 哪些订单和产品在本次计划范围内必须安排。
2. 每个产品要经过哪些工序，前后置、数量门槛、转移批和共享批怎样约束开始时间。
3. 每道工序需要哪个车间、工作中心、具体人员、设备、工位或容量资源。
4. 车间、人员和设备在什么时间可用，已有任务、请假、休息和维修占用了什么时间。
5. 每个阶段什么时候开始、什么时候结束、能完成多少数量。
6. 所有资源和工艺条件成立后，产品行及整个订单预计什么时候生产完成，是否晚于承诺。
7. 当计划员拖动任务、插入急单、锁定计划，或现场发生请假、故障、报工时，哪些任务需要重排，正式计划是否仍然有效。

它不是一个“甘特图自动摆条”功能。引擎输出必须经过独立校验、形成候选版本、允许人工比较，再由有权限的计划员发布。

## 2. 技术决定

### 2.1 选定架构

```text
Vue 3 + TypeScript 排程工作台
  ├─ DHTMLX Community：订单 / 产品 / 工艺任务树
  └─ vis-timeline：人员 / 设备 / 车间资源时间轴
                    │ 调整意图、求解命令、查询
                    ▼
Java 17 + Spring Boot 4.x 排程编排服务
  ├─ 数据就绪与输入快照
  ├─ 日历编译与候选资源生成
  ├─ 独立约束校验与业务解释
  ├─ 版本比较、锁定、发布和执行反馈
  └─ 求解任务编排、取消、超时和进度
                    │ 不可变 SolverInput
                    ▼
独立 Java `aps-solver-worker`
  └─ Google OR-Tools CP-SAT 9.15
                    │ 候选排程、状态、目标和 bound
                    ▼
MySQL 8.0.16+ / InnoDB
  └─ 29 表业务雏形事实、输入快照、候选版本、正式计划和执行数量
```

首版不引入 Python 求解服务，也不同时维护 OR-Tools 与 Timefold 两套生产模型。API 与 Worker 统一使用 Java 17，匹配共享 Maven 父工程；OR-Tools 的精确版本、原生库、CPU 和内存被隔离在独立 Worker 进程。业务 API 与 Worker 可以部署在同一主机，但必须可独立限流、停止和重启。P0 只允许一个 Worker 实例，不能把“进程分离”写成已经支持多实例扩缩。

2026-09-25 的共享若依装配调整使 APS Java HTTP API 默认随 `ruoyi-admin` 启用；`APS_ENABLED=false` 可关闭整个 APS 模块。默认启用要求先配置独立 `APS_DB_URL`、`APS_DB_USERNAME`、报表站点码 `APS_SITE_CODE` 并准备已迁移的 APS schema，缺项应明确启动失败；若单独关闭报表，可不配置站点码。Flyway 迁移与求解 Worker 仍各自默认关闭，Worker 继续是同一 Maven 工程中的独立 Java 进程；详见[共享 Java 模块装配说明](../../../若依框架/Java业务模块统一装配.md)。

这是独立生产排程产品的技术基线，不改动当前 AI Interview Coach 的业务数据库或进程。需要复用 RuoYi 身份时只通过稳定用户 / 部门 ID 和授权接口关联，不把 APS 求解模型嵌入身份库。

消息队列不是首版强制依赖。单实例雏形以 `aps_plan_version.request_id` 防止重复创建求解请求，并在计划版本保存输入快照和结果状态；尚未建立可供多 Worker 抢占、续租和接管的独立命令表。需要多实例自动重试或接入外部命令前，必须补充经评审的租约/幂等模型，不能把普通状态轮询冒充可靠队列。即使后续增加消息中间件，MySQL 仍是唯一权威业务事实源。

### 2.2 为什么选 CP-SAT

本需求属于柔性 Job Shop 的扩展：任务有先后关系，每个阶段可能选择不同人员和设备，多个资源必须同时可用，还包含日历、共享批、转移批、锁定、交期及计划稳定性。CP-SAT 的整数变量、区间变量、可选区间、`NoOverlap` 和 `Cumulative` 与这些约束直接对应。

Timefold Community 保留为备选。它的 Java 领域模型、评分解释、pinning 和滚动重排较友好，但复杂连续时间制造约束需要设计更多规划变量与评分模型。Choco 作为禁止 JNI 场景的纯 Java 后备，不进入第一轮 PoC。

### 2.3 不属于求解器的责任

OR-Tools 不负责：

- 订单、工艺和人员资料的维护与审批；
- 业务时区、班次模板和请假维修的合并；
- 数量账、质量放行、物料预留和返工血缘；
- 权限、人工计划、正式发布和 MES 回写；
- 把内部变量转成计划员可读的冲突原因；
- 自动判断哪个业务目标最重要。

这些责任由领域服务、MySQL 事务和明确的规则配置承担。

### 2.4 工程技术栈

| 层 | 采用技术 | 说明 |
| --- | --- | --- |
| 前端 | Vue 3、TypeScript `5.9.3`、Vite、Element Plus | 沿用现有管理端模式；DHTMLX Community `10.0.3` 与 `vis-timeline` `8.5.4` 通过适配层接入 |
| 业务 API | Java 17、Spring Boot 4.x、Jakarta Validation | 提供订单、资源、计划、人工计划、发布和执行反馈接口 |
| 数据访问 | MyBatis、Flyway | MySQL 访问沿用 RuoYi 风格；DDL 版本升级必须可前进执行和演练恢复 |
| 求解 Worker | Java 17、OR-Tools CP-SAT `9.15.6755`、Maven 3.9.x | 独立 Windows 进程加载原生库；Windows x86_64/JDK 17 目标运行时复验已通过；受控线程、内存、时限和取消 |
| 数据库 | MySQL 8.0.16+、InnoDB、utf8mb4 | 唯一权威业务事实源；不在 SQL 内搜索排程组合 |
| 异步命令 | M19 `request_id/status/row_version` 的单 Worker 状态流转 | P0 无 Inbox、租约、fencing 或 Outbox；多 Worker 接管与可靠外发进入 P1 数据模型评审 |
| API 形态 | REST / JSON，SSE 只传求解进度 | 正式计划和最终状态仍通过可重放查询获取 |
| 可观测 | Spring Boot Actuator、Micrometer、结构化日志 | 记录模型规模、时限、首解、状态、bound、内存和失败码；OpenTelemetry、Prometheus / Grafana 在部署环境明确后接入 |
| 测试 | JUnit 5、Testcontainers MySQL、黄金数据回归、Playwright | 求解器测试与独立校验器测试分开；页面验证不能代替约束验证 |
| 部署 | Windows x64，API 与 Worker 为两个独立 Java 进程 | 当前目标基线为 Windows 11 专业版 `10.0.26200`、Microsoft JDK 17.0.18；API 与 Worker 可同机但必须独立启停。具体 Windows 服务包装、安装目录、服务账号和正式主机版本在部署包中配置，不要求 Docker/WSL |

推荐 Maven 模块边界：

```text
aps-domain                 领域对象、规则编号、状态与值对象
aps-application            用例编排、权限、版本、发布和影响分析
aps-infrastructure-mysql   MyBatis、事务、单 Worker 计划状态持久化
aps-solver-contract        SolverInput、SolverResult 与版本化 Schema
aps-constraint-validator   与求解器独立的确定性硬约束校验
aps-solver-ortools         CP-SAT 变量、约束和目标编译
aps-api                    REST / SSE 与 RuoYi 身份适配
aps-worker                 求解命令领取、限流、取消、恢复和指标
```

`aps-domain`、`aps-application`、`aps-solver-contract` 和 `aps-constraint-validator` 通过 Maven Enforcer 约束向内依赖；其中独立校验器明确禁止 OR-Tools。这样可避免外层框架或求解器反向成为领域与发布校验的事实源。

### 2.5 IMP-01 兼容 PoC 事实

- Java：Microsoft JDK `17.0.18` 下 APS 9 个 reactor 项目 clean test 通过，OR-Tools Windows x86_64 JNI 成功加载并把最小 CP-SAT 模型求到 `OPTIMAL`；JDK `21.0.10` 也可构建 Java 17 字节码，但目标启动与打包命令必须显式使用 JDK 17。
- 前端：Node `24.15.0`、npm `11.12.1` 下，增量类型检查、27 个 APS Vitest 测试和现有管理端生产构建通过；这两个版本已成为当前 Windows 目标的构建基线，不是 Java 运行时依赖。
- 甘特：Chrome `152.0.7977.83` 中，500 资源/5,000 分段可真实渲染、销毁、重建并再次销毁，无 console/page error。三次收口复核的双帧 ready 位于 `4906.3～11575.0 ms`；当前 lockfile 重装后的最近一次 DHTMLX 为 `546.1 ms`、vis-timeline 为 `6206.0 ms`、ready 为 `8982.0 ms`。
- 路线判断：组件边界、事件适配和生命周期为功能兼容；首屏在同机仍出现约 4.9～11.6 秒波动，只能判为受限 Go。IMP-08 接入业务页面前必须在固定目标硬件上定义预算，并验证窗口化、筛选、滚动、缩放、增量重绘和交互延迟；没有这些证据时不能表述为生产性能通过。
- 许可证：当前安装包元数据表明 DHTMLX Gantt 为 MIT，vis-timeline 为 `Apache-2.0 OR MIT`，OR-Tools 为 Apache-2.0；项目保留第三方声明，但这不代替正式法务审查。
- 目标运行时：`scripts/aps/verify-windows-runtime.ps1` 已在选定 Windows 环境复验 OR-Tools JNI、`ruoyi-admin.jar`、`aps-worker-3.9.2.jar`、前端生产制品、默认关闭 Worker 启动及启用 APS API 壳的 HTTP 200。API 使用临时 MySQL 和随机端口，未启动系统 `MySQL80` 服务，也不等于正式部署。

命令、失败修复和限制见[Feature 验证记录](../功能/FEAT-APS-001-生产排程核心闭环/验证记录.md)。

## 3. 产品范围与模块

| 模块 | 核心职责 | 主要输入 / 输出 |
| --- | --- | --- |
| 1. 数据就绪中心 | 检查订单、路线、工时、数量、技能、资源、日历和物料是否可排 | 输入问题清单、责任对象、阻断级别 |
| 2. 调度范围与策略 | 在部署配置确定的单站点内选择计划窗口、冻结区、详细区、目标优先级和时限 | `PlanningScope`、`ObjectiveProfile` |
| 3. 日历编译器 | 把车间班制、个人班次、加班、休息、请假、培训和维修转成资源可用窗口 | 统一半开区间 `[start,end)` |
| 4. 候选资源生成器 | 按类型、中心资格、技能、有效期、设备兼容和窗口裁剪候选 | 每个资源角色的候选集合及淘汰原因 |
| 5. 约束模型编译器 | 将任务、阶段、依赖、供给、资源、锁定和实际占用转成 CP-SAT 模型 | `CpModel` 与变量映射表 |
| 6. 求解策略执行器 | 正排、倒排启发式、交期优化、局部重排、What-if 和多阶段目标求解 | 候选排程、状态、目标、bound、耗时 |
| 7. 独立校验器 | 不依赖求解器假定，再次检查硬约束、数量和发布水位 | PASS / FAIL、业务原因码 |
| 8. 解释与影响分析 | 解释未排、延期、资源选择和人工计划影响 | 原因链、候选资源、可替代窗口、KPI 差异 |
| 9. 计划版本与发布 | 保存草稿、场景和候选，比较基线，复验后在系统内原子发布 | 唯一当前正式计划版本；P0 不生成外发成功事实 |
| 10. 执行反馈与重排 | 接收开停、占用、数量、质量、故障和请假变化 | 修订号、过期候选、局部重排请求 |
| 11. 监控与基准 | 记录模型规模、求解状态、耗时、内存、目标和稳定性 | 运维指标、回归和历史基线 |

前端甘特、订单页、人员页和报表页均是上述能力的消费者，不各自实现一套调度规则。

## 4. 领域词义

| 术语 | 本文定义 |
| --- | --- |
| 任务 `Task` | 一个产品生产实例下稳定的工序身份 |
| 作业 `PlanJob` | 本计划版本内一次可执行安排；可承载一个任务或一个共享批 |
| 阶段 `Phase` | 准备、运行、卸料、等待、转运或恢复准备 |
| 分段 `Segment` | 阶段跨合法窗口后的实际计划区间；同一阶段可有多个分段 |
| 资源预约 `Allocation` | 某分段对具体人员、设备、工位、工装或容量的占用 |
| 可用窗口 | 资源经班次和例外合并后可以承担工作的半开区间 |
| 候选计划 | 已求得但尚未发布的独立版本，不产生现场派工效力 |
| 正式计划 | `aps_plan_version` 中 `status=PUBLISHED` 且 `is_current=1` 的唯一版本 |
| 锁定 | 计划员明确固定时间、资源或二者；必须和已执行事实区分 |
| 冻结区 | 当前时点附近默认不自动扰动的时间范围；遇现实冲突仍需显式处理 |
| 详细计划范围 | 本次必须形成具体人员 / 设备 / 时间的近端任务集合 |
| 远期结转 | 超出详细计划范围且合法保留到后续滚动窗口的任务，不等于排程失败 |
| 生产承诺 | 订单或产品行的 `promised_at`；由业务输入，不由引擎自行创造 |
| 预计生产完成 | 当前候选计划根据必要末端合格释放推导的时间 |

## 5. 引擎需求

### 5.1 功能需求

| ID | 优先级 | 需求 | 完成判据 |
| --- | --- | --- | --- |
| APS-REQ-01 | P0 | 对一个生产站点和明确 horizon 创建不可变求解输入快照 | 快照包含定义、执行两类修订号、内容 hash、基线版本和求解参数 |
| APS-REQ-02 | P0 | 在求解前完成数据就绪校验 | 缺路线、工时、单位、候选资源、日历或数量关系时返回具体对象，不启动伪求解 |
| APS-REQ-03 | P0 | 展开多产品订单、路线 DAG、阶段、非消耗依赖和物料转移关系 | 同一订单产品可独立、先后、汇合或共享批；无隐式产品顺序 |
| APS-REQ-04 | P0 | 对人员、设备、工位、工装及容量资源做有限产能调度 | 所有正式预约通过类型、资格、技能、窗口和并发校验 |
| APS-REQ-05 | P0 | 按已批准的阶段标准工时计算时长和人员可完成数量 | 标准工时来源、单位、版本和证据可追；首版不因具名人员不同暗加效率系数 |
| APS-REQ-06 | P0 | 支持准备、运行、卸料的人机不同占用 | 自动运行可释放人员但不释放设备；阶段同步可复算 |
| APS-REQ-07 | P0 | 支持完成依赖、数量门槛、转移批、物料可用和共享加工批 | 数量守恒、释放时点和共享设备工时无重复 |
| APS-REQ-08 | P0 | 支持不可中断与受控可中断阶段 | 不可中断阶段完整落入连续窗口；分段记录恢复准备和暂停占用 |
| APS-REQ-09 | P0 | 按硬约束先行、交期优先、稳定性其次的分层目标生成候选 | 每层目标值和停止原因可查，不能用“最优”代替 `FEASIBLE` |
| APS-REQ-10 | P0 | 支持时间锁、资源锁、全锁、冻结区和已执行固定事实 | 锁定与执行分别追溯；现实冲突阻止发布，不自动解锁 |
| APS-REQ-11 | P0 | 支持人工计划校验、局部重排和 What-if 场景 | 调整先计算影响闭包并生成新候选，不直接更新正式分配 |
| APS-REQ-12 | P0 | 计算产品行、订单预计生产完成和延期 | 必需任务未知时结果为 UNKNOWN 并给原因，不能取已排任务最大值冒充 |
| APS-REQ-13 | P0 | 支持求解任务的幂等、异步、时限、取消、过期和故障恢复 | API 不持有长事务；重复请求复用结果；正式计划不因失败改变 |
| APS-REQ-14 | P0 | 独立校验所有候选并提供业务解释 | 发布候选必须校验 PASS；冲突显示订单、任务、资源、时间和规则编号 |
| APS-REQ-15 | P1 | 支持顺序相关换型、清洗、连续生产 campaign | 规则版本化并通过相同产品族的换型矩阵样例 |
| APS-REQ-16 | P1 | 支持具名人员 / 设备速率、人员组合效率、多机看护和多维批容量 | 先扩展有效期化数据模型并压测，不在标准速率上暗中近似 |
| APS-REQ-17 | P2 | 支持多工厂能力协同与跨厂运输 | 各厂本地详细计划仍可独立发布，跨厂约束不破坏单厂审计 |

### 5.2 业务规则

- APS-BR-01：同一求解任务只使用部署配置确定的一个生产站点、一个 IANA 时区解释和一个整数时间刻度；站点不是 P0 业务表或外键。
- APS-BR-02：输入快照创建后不可修改；数据变化递增修订号并产生新快照。
- APS-BR-03：订单承诺是输入事实；引擎输出预计完成、延期及可行替代方案，但不自行改写承诺。
- APS-BR-04：交期默认是软目标。只有业务明确标记“绝不晚于”时才转为硬约束，并允许因此返回不可行。
- APS-BR-05：任务最早就绪时点取输入快照冻结的 `planningAnchorAt`、订单 / 任务最早开始、所有前置释放加 lag、所需物料预计可用时点的最大值。
- APS-BR-06：阶段只能放入所有必需资源可用窗口的交集，并扣除实际占用、固定计划和本候选预约。
- APS-BR-07：人员技能必须在计划执行时点有效；过期证书和技能不足不能通过提高软惩罚绕过。
- APS-BR-08：工作中心资格与借调有效期是硬约束；借调本身可计软成本。
- APS-BR-09：一个多技能员工同一时刻仍只有一份可用容量，不能在多个技能池重复计算。
- APS-BR-10：多个必需席位不得由同一独占人员重复充数；明确允许复用的非独占容量除外。
- APS-BR-11：独占资源使用 `NoOverlap`；容量资源使用 `Cumulative`，需求单位必须与容量单位一致。
- APS-BR-12：自动运行阶段只预约设备；准备和卸料需要人员时，人机区间共享同一阶段起止。
- APS-BR-13：不可中断阶段必须存在完整连续窗口，上午两小时加下午两小时不能容纳三小时连续任务。
- APS-BR-14：可中断阶段只按已批准的最大分段数、最小分段量和恢复准备规则拆分，不允许无限碎片化。
- APS-BR-15：完成依赖、数量门槛与消耗型转移批分别建模；一次达到首批门槛不代表后续数量无限可用。
- APS-BR-16：共享批只建立一个主作业和一套资源预约；成员数量、输出和质量归属分别记录。
- APS-BR-17：共享批成员必须满足兼容、共同单位、最小 / 最大容量和共同周期；不兼容或超量是硬冲突。
- APS-BR-18：已开始和已结束区间是实际事实，不能被重排；更正必须走冲正或事件流程。
- APS-BR-19：`addHint` 只作为搜索提示，不产生锁定语义。
- APS-BR-20：人工计划只提交意图。服务端失败时前端恢复到服务端确认位置，并保留用户输入供比对。
- APS-BR-21：局部重排必须包含上下游、供需、共享批、同资源竞争和连续性关系的影响闭包。
- APS-BR-22：闭包外计划作为固定占用；局部无解时可以扩大闭包，但不能静默全局改写。
- APS-BR-23：详细计划范围内的必需任务必须全部得到合法安排才可发布；远期结转任务单独标识，不算未排错误。
- APS-BR-24：产品行预计完成是达到需求量的最后必要末端合格释放时点；订单预计完成取所有必需产品行的最大值。
- APS-BR-25：存在必需任务无工时、无资源、无供给或尚未纳入可靠计划时，预计完成状态为 UNKNOWN。
- APS-BR-26：延期为 `max(0, predictedCompletion - promisedAt)`；自然时间与工作时间差异分开显示。
- APS-BR-27：求解结果必须区分 `OPTIMAL`、`FEASIBLE`、`INFEASIBLE`、`UNKNOWN` 和 `MODEL_INVALID`。
- APS-BR-28：超时且有经校验候选映射为 `TIMEOUT_WITH_SOLUTION`；超时无候选映射为 `TIMEOUT_NO_SOLUTION`，不能标为已证明无解。
- APS-BR-29：发布前必须重新核对当前正式版本、定义修订号、执行修订号、输入 hash、资源窗口和实际占用。
- APS-BR-30：任一水位变化使候选过期；系统只给差异和重排入口，不覆盖新报工、请假或维修。
- APS-BR-31：求解回调限频保存进度和最好候选，不能每个 incumbent 全量写库。
- APS-BR-32：相同幂等键与相同请求 hash 返回原求解任务；相同键不同载荷拒绝。
- APS-BR-33：求解失败、取消或 Worker 崩溃不得改变当前正式版本。
- APS-BR-34：未经独立校验 PASS 的候选不得发布，即使求解器返回 `OPTIMAL`。
- APS-BR-35：超出标准版的数据语义必须返回 `UNSUPPORTED_*` 原因，不得静默降级成另一种约束。
- APS-BR-36：`aps_actual_occupancy.end_at` 为空表示资源仍被实际占用；不得按原计划结束或经验时长自动释放。
- APS-BR-37：倒排只用于计算最新可行窗口、生成候选与 warm-start，不产生绕过有限产能模型的第二套正式计划。
- APS-BR-38：P0 部署必须保证只有一个 Worker 实例。Worker 用 `aps_plan_version.status` 与 `row_version` CAS 将 `DRAFT` 转为 `SOLVING`；这只防止同一版本的重复状态转换，不是租约或 fencing，禁止据此启动第二 Worker。
- APS-BR-39：输入快照、hash、`request_id` 与计划版本在一个短事务内提交。Worker 退出后由受控恢复任务按状态和更新时间把遗留 `SOLVING` 版本标为 `FAILED`，或基于原快照创建新候选；不得让旧进程继续补写半套结果。

## 6. 时间与资源计算

### 6.1 时间坐标

MySQL 使用 UTC `datetime(3)`；IANA 时区由单站点部署配置 `aps.timezone` 提供。输入编译器把时间转换为相对于 `horizon_start` 的非负整数，但不同边界必须采用保守方向，不能一律向下取整：

```text
earliest / start lower bound = ceil(offsetSeconds / timeUnitSeconds)
latest / availability end    = floor(offsetSeconds / timeUnitSeconds)
duration / positive lag      = ceil(seconds / timeUnitSeconds)
actual blocked start         = floor(offsetSeconds / timeUnitSeconds)
actual blocked end           = ceil(offsetSeconds / timeUnitSeconds)
```

这样不会把最早开工向前放宽、把可用窗口向后扩张，也不会提前释放实际占用。所有区间转换后裁剪到 horizon，`end <= start` 的可用窗口丢弃并记录数据问题。首版默认 `timeUnitSeconds = 60`。实际阻塞允许保守地向外扩张；需要原样显示和复算的已执行 / 锁定时点若不能无损对齐，则必须把整次求解切换到更细刻度或拒绝输入，不能移动事实来迎合时间格。取整方向和误差写入 `calculation_basis_json`。若某工艺的合法最小单位小于一分钟，则整次求解改用秒级，不能只让一部分任务使用秒。

### 6.2 阶段时长

标准模式：

```text
durationSeconds = fixedSeconds
                + ceil(workQty × secondsPerUnit)
                + resumeSetupSeconds × resumeCount
```

P1 在引入具名资源速率后，若某个具名资源是速率驱动角色：

```text
effectiveSecondsPerUnit = approvedResourceSecondsPerUnit
durationSeconds = fixedSeconds
                + ceil(workQty × effectiveSecondsPerUnit)
                + resumeSetupSeconds × resumeCount
```

一个阶段只能指定一个速率驱动角色。其他人员、设备和工装只影响资格与占用，不擅自相乘或相加效率。多人协作、特定人机组合速率属于 P1，必须有单独批准的数据模型。

当前 29 表候选只有 `aps_operation_phase.seconds_per_unit` 的标准工时，尚无具名人员 / 设备的有效期化速率表。因此 P0 按主 PRD 已确认的标准工时计算：个人可完成数量由其真实可用窗口、被占用时段和阶段标准速率共同得到；“相同工艺因具体人员不同而速度不同”属于 APS-REQ-16，补齐 APS-DG-02 后再进入 P1 验收。

### 6.3 日历合并

求解器读取的是每个具体资源最终可用窗口，不直接理解“白班”“午休”“请假”这些业务名词。日历编译器按优先级处理：

```text
人工维护 / 授权导入 / 后续 HR-MES 适配器
  把站点关闭、车间班制、个人班次、休息、请假、培训、维修和已批加班
  物化为每个具体资源的 AVAILABLE / UNAVAILABLE 绝对窗口
→ 日历编译器求净可用区间
→ 最终 APPROVED 可用窗口
```

所有窗口采用 `[start,end)`，相邻窗口可以合并，重叠冲突必须在求解前处理。车间关闭影响必须先物化到所属资源的不可用窗口；即使个人原班次显示在岗也不可排。加班只有批准后才产生可用窗口。P0 不在备注或 JSON 中暗藏循环班制模板。

独占资源把可用窗口之外的间隙编译为固定阻塞区间，与候选作业共同进入 `NoOverlap`。容量资源先把整个 horizon 分割成容量恒定的连续片段，包括容量为零的空档；以全范围最大容量为 `Cumulative` 上限，在每个片段加入“最大容量减当前容量”的固定占用。这样业务任务与固定占用之和不超过最大值，就等价于该片段不超过实际容量。容量单位、边界或片段覆盖不完整时必须在输入校验阶段拒绝，不能取全天平均值。

当前 29 表用 `aps_resource_availability` 保存展开后的绝对窗口并作为 P0 求解输入，没有本地班制模板和车间日历层级。IMP-01 已选择“人工/导入/适配器物化绝对窗口”的收窄模式，APS-DG-01 对 P0 关闭；若未来要求本系统维护循环班制，须先新增经评审的数据模型。

### 6.4 最早可排时点

对阶段 `p`：

```text
readyAt(p) = max(
  planningAnchorAt,
  order.earliestStartAt,
  task.earliestStartAt,
  everyPredecessor.releaseAt + lag,
  everyRequiredSupply.expectedAvailableAt
)
```

`planningAnchorAt` 是输入快照内冻结的计划基准时点，通常等于 `input_captured_at`，不是求解过程中不断变化的系统当前时间。重放同一快照时必须使用相同基准；发布前由修订水位复验判断新实际是否已使候选过期。

从 `readyAt` 开始，在必需资源窗口交集中寻找能容纳阶段的区间。一个“日总工时有富余”的员工，若没有满足同时到岗和连续时长的窗口，仍然不可行。

### 6.5 开放中的实际占用

`aps_actual_occupancy.end_at IS NULL` 不是缺失数据，而是“截至输入快照仍在占用”的事实。输入编译器必须按以下顺序处理：

1. 将 `start_at` 至 `planningAnchorAt` 编译为不可移动的实际区间，并按 6.1 的保守方向取整和裁剪。
2. 若执行状态、剩余数量 / 工时、当前阶段和继续占用的资源角色都可信，则从 `planningAnchorAt` 建立在制任务的 `carry` 计划段；仍被占用的具名资源固定给该段，预计完成只写入候选计划。
3. 若无法可靠计算剩余工作或判断哪些资源仍被占用，则把对应资源从 `planningAnchorAt` 保守阻塞到 `horizon_end`，同时返回 `OPEN_OCCUPANCY_UNKNOWN_RELEASE` 数据问题；不得用原计划结束时间猜测释放。
4. 候选中的预计完成、人工预计释放和求解结果都不能回写 M26 `aps_actual_occupancy.end_at`。只有真实停工 / 完工事件或受控冲正可以结束实际占用。

在制 `carry` 段与普通未来任务一起参加资源竞争、前后置和数量校验；实际段保持事实身份，两者不能合并成一条“看似全部实际”的甘特记录。

同一 M26 物理记录无论对应普通作业还是多成员共享作业，都只能以一个 `occupancyId` 进入输入。共享作业的任务成员及各自剩余派工量放在该占用的 `members` 投影中，不能复制人员或设备区间；若 M25 的总派工量不足以唯一还原成员分配，则释放置信度必须为 `UNKNOWN` 并按 horizon 保守阻塞，不能按成员计划量比例猜测。

当前执行侧已经按计划阶段维护事实：开工只打开最小 `segmentNo` 的来源分配；暂停/恢复只处理当前活动阶段；换资源关闭旧 M26 并打开新 M26，但以 `sourcePlanAllocationId` 保留原 requirement/seat/capacity；幂等阶段推进原子关闭当前阶段并打开紧邻下一阶段；只有最后计划阶段允许完工报工。历史换资源记录若没有可安全还原的来源分配仍按 `UNKNOWN` 处理，不能猜测。

求解侧已对可信活动 run 形成唯一固定 `CARRY` 作业：候选通过 `carryRunId` 唯一关联 M25，当前阶段从 `planningAnchorAt` 到预计释放保持不可移动事实段并沿用来源计划的 requirement/seat；成员在制剩余量从未来待排量扣除，未分配余量另形成 `SPLIT`。当前阶段之后的连续和受控可中断阶段按原工艺顺序进入同一 CP-SAT 作业，重新参加资源、容量、净日历和暂停保留竞争；可中断阶段保留最小分段、最大段数、恢复准备与跨段资源策略。最终阶段统一释放 carry 数量，完成依赖、数量依赖和物料需求等待完整 carry 或所需未来余量，不把当前阶段预计释放误报为整批完成。

### 6.6 倒排启发式与有限产能确认

主 PRD BR-28 的“倒排”不是另一套可发布算法。引擎先从订单 `promised_at` 沿路线 DAG 反向计算各阶段的 latest finish / latest start，扣除标准时长、正 lag 和已知工作日历，得到交期导向的候选窗口；反向贪心结果可以作为候选裁剪依据和 `addHint` warm-start。

倒排窗口早于 `readyAt`、`planningAnchorAt` 或合法资源窗口时，立即记录交期不可行线索，但仍将任务交给统一 CP-SAT 有限产能模型。最终是否满足交期，只以人机、日历、物料、锁定、实际占用和任务间竞争全部生效后的候选及独立校验为准：能满足则输出合法交期方案；不能满足则最小化延期，并给出最早可行正排结果或明确未排原因。倒排启发式绝不允许任务排入过去，也不单独写计划表。

### 6.7 资源选择

对每个阶段的资源角色：

1. 候选生成器先筛出合法资源。
2. 每个候选建立 presence 布尔变量和可选区间。
3. 每个必须席位满足 `ExactlyOne(candidatePresence)`。
4. 具有相同 `continuity_key` 的阶段约束为同一资源。
5. 属于相同 `distinct_group` 且时间重叠的席位不能选择同一独占资源。
6. 独占资源的所有 present 区间进入 `NoOverlap`。
7. 非独占容量资源的区间和需求进入 `Cumulative`。

### 6.8 工序依赖与数量

标准版领域语义：

| 业务关系 | 约束逻辑 |
| --- | --- |
| 完成后开始 | `start(B) >= release(A) + lag` |
| 合格数量门槛 | 只有 A 的实际或计划合格释放累计达到门槛，B 才可启动 |
| 转移批 | A 的每个释放批产生有限供给，B 对应分段不能消费尚未释放数量 |
| 共享加工批 | 多个任务成员链接同一批作业区间，设备占用一次，成员输出分别产生 |
| 独立并行 | 无依赖且资源不冲突时可同时安排，不创建虚假同步关系 |

DHTMLX 能画 FS / SS / FF / SF 不代表本产品全部支持这些语义。P0 只执行领域模型已定义的完成、数量和转移关系；M12/M17 允许保存 `SAME_START` 来源关系以满足“不丢失”，但数据就绪与发布必须返回 `UNSUPPORTED_SYNC_RULE`。P0 不执行该关系，也不把它降级为普通依赖或共享批；其他同步类型仍不在当前契约中。

`lag_basis=ELAPSED` 时可以直接使用线性时间差。`lag_basis=WORKING` 时，日历编译器必须按指定 CAPACITY 日历预计算“从每个可能结束 tick 累加 N 个工作 tick 后的结果”，再通过查找约束连接前置结束与后序就绪时间；午休、周末和停工段不计入工作 lag。该映射应按日历与 lag 值复用并进入性能基准，不能把工作时间等待静默近似成自然时间等待。

### 6.9 共享批候选

首版按主 PRD 的 P0/P1 边界处理：P0 支持人工计划或上游规则已经形成的共享批，以及有限的规则候选；“在全部任务子集中自动证明最佳合批组合”属于 P1。候选生成器先按工序规格、兼容键、单位、批容量、最早就绪和交期窗口分桶，再用最早交期、相同属性和容量装箱等确定性规则生成数量受限的候选批。CP-SAT 在候选批之间选择开始时间和资源，不枚举所有 `2^n` 成员组合。

每个任务待排量必须恰好由一个或多个被选作业成员覆盖；同一数量不能同时进入单任务作业和共享批。人工计划固定的批成员仍须通过兼容、容量、共同周期、数量和资源校验。

## 7. CP-SAT 模型

### 7.1 核心变量

| 变量 | 类型 | 含义 |
| --- | --- | --- |
| `start[p]`、`end[p]` | `IntVar` | 不可中断阶段的开始和结束 tick |
| `duration[p]` | 常量或受控 `IntVar` | 不可中断阶段的持续时间 |
| `interval[p]` | `IntervalVar` | 不可中断阶段主时间区间 |
| `present[p,k]` | `BoolVar` | 可中断阶段第 k 个候选分段是否存在 |
| `start[p,k]`、`end[p,k]`、`work[p,k]` | `IntVar` | 可中断阶段各分段的位置和有效工作量 |
| `interval[p,k]` | `OptionalIntervalVar` | 可中断阶段的有限候选分段；按 k 排序且总工作量精确覆盖需求 |
| `assign[p,k,r,s]` | `BoolVar` | 阶段 / 分段角色席位 s 是否选择资源 r；不可中断阶段省略 k |
| `resourceInterval[p,k,r,s]` | `OptionalIntervalVar` | 选择资源且分段存在时才存在的占用区间 |
| `orderCompletion[o]` | `IntVar` | 订单所有必要产品行完成最大值 |
| `tardiness[o]` | `IntVar` | 订单延期 tick，最小为 0 |
| `changedTime[p]` | `IntVar / BoolVar` | 相对基线的时间偏移与是否变化 |
| `changedResource[p]` | `BoolVar` | 人员或设备是否改变 |
| `scheduled[t]` | `BoolVar` | 远期可选任务是否排入；详细范围必需任务固定为 1 |

变量名必须带稳定业务 ID 映射，诊断层不能只得到数组下标。

可中断阶段不是把一个 `interval[p]` 跨过午休。模型按业务允许的最大分段数预建有限 `k`，约束分段按时间排序、每段达到最小工作量、总工作量等于阶段需求，并在第二段起增加恢复准备。资源连续性规则决定各段必须沿用同一人机还是允许重新选择；未定义这组规则的数据不得标为可中断。

当 `hold_on_pause=true` 时，指定设备或工装虽然停止加工，仍须从前一工作段结束到后一工作段开始保持预约。模型为该资源额外建立连接两段的 HOLD 区间，或建立覆盖首次开始至最终结束的连续保留区间；人员只有在工艺明确要求时才进入 HOLD。若无法明确“保留哪些角色”，输入校验必须拒绝，而不是默认释放全部资源。

### 7.2 硬约束编译顺序

1. 输入范围、时间域和任务必排标记。
2. 阶段时长、阶段内部先后与允许分段。
3. 路线、数量门槛、计划供给和物料可用。
4. 候选选择、席位、连续性与不同资源组。
5. 独占和累计资源容量。
6. 最终可用窗口、固定不可用区间与实际占用。
7. 已执行事实、人工锁定和冻结策略。
8. 共享批、输出释放和订单完成。
9. 目标变量和目标函数。

每类约束都带 `constraintCode` 和相关业务对象。重要锁定、供给和日历约束可以使用 assumption literal 辅助无解定位，但最终原因由业务诊断层确认。

### 7.3 分层求解

推荐顺序：

| 层级 | 目标 | 约束处理 |
| --- | --- | --- |
| L0 | 找到硬约束可行解，详细范围任务覆盖 100% | 无解不进入后续层 |
| L1 | 最小化延期订单数和加权延期时长 | 保存最优值或当前可行上界 |
| L2 | 最小化对正式计划的时间、人员和设备扰动 | 加约束不允许 L1 指标恶化 |
| L3 | 最小化换型、加班、借调、等待和 WIP | 不允许 L1 / L2 恶化 |
| L4 | 改善 makespan 与负荷均衡 | 仅使用剩余时间预算 |

总时限按策略配置分配给各层。若 L1 未证明最优但已有可行解，后续层只能在已记录的 L1 上界内搜索，结果状态仍为 `FEASIBLE` 或 `TIMEOUT_WITH_SOLUTION`，不能写成 `OPTIMAL`。

## 8. 求解与发布工作流

### 8.1 状态映射

当前 `aps_plan_version.status` 与 `solver_summary_json.resultKind` 组合使用：

| 业务阶段 | `status` | `resultKind` | 含义 |
| --- | --- | --- | --- |
| 已创建 / 正在抓快照 | DRAFT | NULL | 尚未启动求解 |
| 正在计算 | SOLVING | NULL | Worker 已领取命令 |
| 已证明当前目标最优 | FEASIBLE | FEASIBLE | 另存 `solver_status=OPTIMAL`；业务版本仍等待审查 |
| 有可审查候选 | FEASIBLE | FEASIBLE | `solver_status=FEASIBLE`，有合法解但未证明最优 |
| 超时但有候选 | FEASIBLE | TIMEOUT_WITH_SOLUTION | 候选经独立校验，可审查 |
| 已证明无解 | CONFLICT | INFEASIBLE_PROVEN | 当前输入和硬约束已证明不可行 |
| 超时且无候选 | CONFLICT | TIMEOUT_NO_SOLUTION | 未得结论，不等于无解 |
| 输入非法 | CONFLICT | INVALID_INPUT | 数据就绪或模型前校验失败 |
| 用户取消 | CANCELLED | NULL | 正式计划保持不变 |
| 系统 / 模型失败 | FAILED | NULL | 记录脱敏错误与恢复动作 |
| 正式发布 | PUBLISHED | 原求解结果 | 当前正式版本 |
| 被新正式版替代 | SUPERSEDED | 原求解结果 | 历史只读 |

OR-Tools 原生状态 `MODEL_INVALID` 映射为 `FAILED`，错误代码 `SOLVER_MODEL_INVALID`。CP-SAT 只要返回了 incumbent，原生状态就是 `FEASIBLE` 或 `OPTIMAL`；因应用时限停止且为 `FEASIBLE` 时映射 `TIMEOUT_WITH_SOLUTION`。原生 `UNKNOWN` 表示没有可供应用读取的解；确认停止原因为时限时映射 `TIMEOUT_NO_SOLUTION`，取消请求映射 `CANCELLED`，其他未知停止原因映射 `FAILED` 并保留错误码。

当前 M19 以 `solver_summary_json` 承载原生状态、停止原因、目标值和 best bound，但 JSON Schema 尚未批准，因此上述区分仍受 APS-DG-08 限制；在补齐并验证写入前页面不得显示“已证明最优”。

即使原生状态为 `OPTIMAL`，也要检查求解参数。若配置了非零 `absolute_gap_limit` 或 `relative_gap_limit`，对外只能表述为“达到配置的最优性容差”；只有未放宽 gap 且最终目标与 best bound 一致时，才表述为“在当前模型和范围内证明精确最优”。

### 8.2 异步流程

```text
1. API 校验权限、requestId 和基础参数；数据库唯一键拒绝重复请求
2. 在一致性读事务中读取当前正式版及输入行版本，形成不可变 input_snapshot_json 与 input_hash
3. 同一事务创建 DRAFT plan_version，提交后返回 planVersionId
4. 单实例 Worker 以 plan_version.row_version CAS 将 DRAFT 改为 SOLVING，在事务外构建和求解模型
5. Worker 在内存中形成完整候选；受控事务再次 CAS 版本，把完整 job/member/segment/allocation/lock 一次写入
6. 独立校验器按候选内容 hash 全量复验；同一事务写校验/求解摘要并将版本改为 FEASIBLE 或 CONFLICT
7. 计划员比较基线、调整或申请发布
8. 发布事务锁定目标版本及当前正式版本，重建输入 hash 并复核实际进度、日历和资源占用
9. 先将旧正式版改为 SUPERSEDED 且 is_current=0，再把新版本改为 PUBLISHED 且 is_current=1；唯一 current marker 处理并发冲突
```

求解期间不持有业务行锁，完整候选落库前不得把 job / segment 等结果分批暴露给审查端。当前 29 表雏形没有持久命令租约和 fencing token，只允许单 Worker 实例；进程退出后遗留的 `SOLVING` 版本须由受控恢复任务标记失败或重新创建候选。多 Worker 抢占、自动接管、外部命令或可靠发布通知进入范围前，必须恢复独立命令/收发箱及 attempt 隔离模型，不能仅靠 `plan_version.row_version` 冒充租约。

Worker 在候选事务中崩溃时由 MySQL 整体回滚。若未来单事务规模无法接受，必须先增加带 attempt ID 的隔离暂存模型并原子切换可见 attempt，不能直接把半套计划留在同一版本中继续补写。正式发布到本系统内部即完成；尚未确定 MES/ERP 接收方时不写假 Outbox，也不得声称已可靠下达到外部系统。

## 9. 人工调整与局部重排

前端提交：

```json
{
  "basePlanVersionId": "...",
  "targetType": "SEGMENT",
  "targetId": "...",
  "requestedStartAt": "...",
  "requestedEndAt": "...",
  "requestedResourceIds": ["..."],
  "repairScope": "IMPACT_CLOSURE",
  "reason": "计划员调整原因",
  "idempotencyKey": "..."
}
```

服务端执行：

1. 校验基线是否仍为用户看到的版本。
2. 计算直接硬冲突并给即时拒绝原因。
3. 计算上下游、供需、共享批、资源竞争和连续性闭包。
4. 固定闭包外任务，把用户期望作为约束或高优先级偏好。
5. 运行短时局部求解和独立校验。
6. 返回新候选版本、变化清单、订单交期前后差异及不可行原因。

如果计划员要求的位置违反硬约束，系统不得为了“看起来拖动成功”而自动放宽技能、日历、物料、锁定或数量约束。

## 10. 执行反馈

- 开工前再次检查当前正式版本、实际前置释放、具体人机资格、日历、资源实际占用和物料预留。
- 开工后创建 `aps_execution_run`，人员 / 设备实际占用写 `aps_actual_occupancy`；设备自动运行期间人员离场由不同阶段占用体现。
- 开工只为首个计划阶段写开放占用；暂停/恢复只作用于当前阶段，换资源必须保留来源计划分配身份，避免实际资源变化后丢失角色、席位和容量语义。
- 当前阶段完成但 run 尚未完成时，以带 `Idempotency-Key` 和 `expectedRowVersion` 的阶段推进命令原子关闭当前占用并打开下一计划阶段；不能跳段。非最后阶段的完工报工必须拒绝。
- 部分报工产生 `aps_output_lot`、数量事件和质量状态；只有已满足质量策略的数量能释放给下游。
- 请假、维修、停机、报工、质量隔离和返工使 `execution_revision` 递增，并将基于旧水位的候选标为过期。
- 实际变化只触发影响分析和候选重排，不静默改变正式未来计划。
- 已发生事实只允许追加更正或冲正，不能由求解器覆写。

### 11.3 已批准的数据契约决定与实施门

| ID | 原始差距 | 已批准 P0 决定 | 实施门 |
| --- | --- | --- | --- |
| APS-DG-01 | 只有逐资源绝对窗口，无站点/车间循环班制模板 | P0 由人工、授权导入或适配器把所有规则物化到 M05；循环班制模型转 P1 | M05 来源、修订和净窗口测试通过前不进入求解 |
| APS-DG-02 | 只有阶段标准工时，无具名资源速率 | P0 只用阶段标准工时；具名速率及有效期模型转 P1 | 页面和引擎不得暗加个人效率系数 |
| APS-DG-03 | 阶段要求固定单一中心，不能表达 OR 型替代中心 | P0 在工艺确认时先选定一个中心，再在中心内选具体资源；替代中心集合转 P1 | 求解器不得私自跨中心选人机 |
| APS-DG-04 | M24 的继承、目标唯一性和冲突顺序是服务规则 | 一个锁只锚定一个目标；新候选复制正式版锁锚并重验现实可用性 | IMP-07 服务事务与反例未通过前不声称锁可用 |
| APS-DG-05 | 有限 horizon 与全部覆盖存在冲突 | SolverInput 显式区分 `MANDATORY_DETAIL` 与 `FUTURE_CARRY_FORWARD` | 远期可结转；详细范围未排仍阻断发布 |
| APS-DG-06 | 生产完成、发运和到货边界未拆 | P0 只承诺预计生产完成；发运/到货里程碑转 P1 | 页面不得把生产完成写成客户到货 |
| APS-DG-07 | 独占与非独占容量语义有歧义 | 独占资源用 `NoOverlap`，非独占容量用 `Cumulative`；字段只决定相应容量校验 | Solver 与独立校验器必须使用同一语义 |
| APS-DG-08 | M19 只有摘要 JSON，无批准 Schema 或 attempt 历史 | IMP-01 固定摘要 Schema：计划状态、solverStatus、resultKind、停止原因、目标、bound、gap 和规模分层；多 attempt 历史表转 P1 | Schema/写入测试前不能证明 OPTIMAL 或形成历史性能基线 |

用户已随十阶段计划批准以上 P0 收窄决定和 29 表实现基线；实现状态仍由各 IMP 证据决定。任何尚未实现的门都必须阻断对应功能，不得在 Worker 内用未契约化 JSON 字段绕过，也不得把“决定已批准”写成“能力已完成”。

## 12. 解释与冲突模型

### 12.1 业务原因码

至少提供：

| 原因码 | 含义 | 最小上下文 |
| --- | --- | --- |
| `NO_ROUTE` | 无已发布工艺路线 | 订单行、产品、期望版本 |
| `MISSING_DURATION` | 工艺阶段无获批工时 | 任务、阶段、数量、单位 |
| `NO_QUALIFIED_RESOURCE` | 无满足类型 / 中心 / 技能的候选 | 角色、技能、候选淘汰原因 |
| `NO_COMMON_WINDOW` | 必需人机没有共同连续窗口 | 资源、窗口、阶段时长 |
| `RESOURCE_OVERLAP` | 独占资源冲突 | 两个占用及时间范围 |
| `CAPACITY_EXCEEDED` | 累计容量超限 | 资源、容量、峰值需求 |
| `PRECEDENCE_VIOLATION` | 前置或 lag 不成立 | 前后任务、释放与请求时间 |
| `QUANTITY_NOT_RELEASED` | 数量门槛 / 转移批供给不足 | 需求量、已释放、缺口 |
| `BATCH_INCOMPATIBLE` | 共享批不兼容或超容量 | 批成员、兼容键、容量 |
| `LOCK_CONFLICT` | 锁定与维修、实际或其他硬约束冲突 | 锁、资源、冲突事实 |
| `OPEN_OCCUPANCY_UNKNOWN_RELEASE` | 开放实际占用无法可靠计算剩余工作或释放时点 | 执行记录、资源、开始时点、缺失字段 |
| `STALE_INPUT` | 求解后输入水位变化 | 旧 / 新 revision 与差异类型 |
| `UNSUPPORTED_SYNC_RULE` | 当前标准版不支持同步语义 | 来源关系及建议处理 |
| `TIME_LIMIT_NO_SOLUTION` | 时限内没有得到候选 | 时限、模型规模、已尝试范围 |

### 12.2 为什么选择这个资源

任务详情至少能显示：

- 被选择资源的类型、中心资格、技能等级、有效期和可用窗口；
- 其他主要候选被淘汰或得分较低的原因；
- 使用该资源对交期、基线扰动、加班、借调和换型的影响；
- 这是求解器证明最优、时限内最好可行，还是人工计划后的合法候选。

不能直接把 SAT literal、变量下标或原生求解日志展示给计划员。

## 13. 非功能要求

| ID | 领域 | 要求 |
| --- | --- | --- |
| APS-NFR-01 | 性能 | 以 PRD 的单站点 30 日、1,000 订单、20,000 未完成任务、200 设备、500 人员为目标基准；在固定硬件上记录首解和最终结果，不事先承诺全局最优 |
| APS-NFR-02 | 时限 | 全量求解目标 120 秒内返回经校验候选或准确状态；局部影响预览目标 P95 不超过 5 秒，均须真实压测后确认 |
| APS-NFR-03 | 可用性 | 单 Worker 崩溃、取消、超时和重复请求不改变正式计划；遗留 `SOLVING` 由受控恢复标失败或创建新候选 |
| APS-NFR-04 | 一致性 | 系统内发布使用短事务与乐观 / 悲观复验，唯一正式指针原子切换；P0 不声明外部已接收 |
| APS-NFR-05 | 可追溯 | 保存求解器版本、模型版本、输入 schema、数据 hash、目标配置、随机种子、线程数、状态、目标、bound、耗时和校验结果 |
| APS-NFR-06 | 可复现 | 相同快照和配置可复跑；多线程搜索可能不逐字节一致，要求业务可行性与指标在容差内一致 |
| APS-NFR-07 | 安全 | 按角色、车间和必要的工作中心范围授权；Worker 只读输入快照并写指定候选版本，不可绕过发布权限 |
| APS-NFR-08 | 隐私 | 求解输入只保留人员稳定 ID、技能和可用性，不复制薪资、身份证或无关 HR 信息 |
| APS-NFR-09 | 可观测 | 记录模型变量 / 约束数量、候选数、裁剪率、首解时间、总时长、内存、状态、gap、取消和失败码 |
| APS-NFR-10 | 升级 | OR-Tools、JDK 或模型版本升级必须用黄金样例和历史数据回归，不能直接滚动替换全部 Worker |

最优 gap 只有在目标和 bound 可比较且分母有效时计算；无目标、目标为零或状态不适用时显示 N/A。

## 14. 验收场景

以下为引擎专项验收，主产品 AC-01 至 AC-24 仍是完整产品验收的唯一正文。

| ID | 输入 / 动作 | 必须结果 |
| --- | --- | --- |
| APS-AC-01 | A、B 多产品订单，各自路线，无跨产品依赖 | 只因真实资源冲突产生等待；不按产品显示顺序串行 |
| APS-AC-02 | 技能三级任务；甲二级空闲、乙三级请假、丙三级在岗 | 只能选择丙；丙无窗口则返回未排原因，不降低技能 |
| APS-AC-03 | 车间关闭已物化为所属资源不可用窗口、个人原班次仍显示在岗；随后批准车间加班并物化新窗口 | 关闭时不可排；加班审批并写入绝对窗口后才出现合法窗口 |
| APS-AC-04 | 两个任务同时需要同一多技能员工 | 不重叠；单站点可用工时只计一次 |
| APS-AC-05 | 设备自动运行2小时，装卸各0.5小时需王工 | 设备占3小时、王工占1小时；王工可在自动运行段做其他合法任务 |
| APS-AC-06 | 三小时不可中断任务只有上午2小时、下午2小时 | 判无连续窗口；改为可中断后按规则分段并增加恢复准备 |
| APS-AC-07 | 上游20件/小时，下游40件/小时，每20件转序 | 下游每段只消费已释放20件，中间正确等待，数量守恒 |
| APS-AC-08 | A60+B40共享100容量炉；再加不兼容或超量成员 | 合法批设备只占一次；不兼容 / 超量阻断 |
| APS-AC-09 | P1：相同技能两名人员具有不同获批速率 | 速率影响时长、候选选择和交期；依据可查。P0 与数据模型未补齐时本项明确 NotRun |
| APS-AC-10 | 不可能交期但资源计划可行 | 给出最早可行正排、延期时长和瓶颈；不因交期软目标使全模型无解 |
| APS-AC-11 | 分别设置时间锁、资源锁、全锁后重排 | 只有未锁维度变化；锁定撞维修时发布被阻止 |
| APS-AC-12 | 从甘特拖动任务，跨订单下游和共享批受影响 | 返回完整影响闭包及新候选；取消后正式基线不变 |
| APS-AC-13 | 求解中新增报工或请假 | 发布复验返回 reasonCode=`STALE_INPUT`，不能直接发布；M19 不新增同名业务状态，实际事实不被覆盖 |
| APS-AC-14 | 时限内有候选但未证明最优 | M19 为 `FEASIBLE`，`solver_summary.resultKind=TIMEOUT_WITH_SOLUTION`，显示目标与 bound，不显示“最优” |
| APS-AC-15 | 时限内无候选且未证明无解 | M19 为 `CONFLICT`，`solver_summary.resultKind=TIMEOUT_NO_SOLUTION`，与 `INFEASIBLE_PROVEN` 明确区分 |
| APS-AC-16 | 同幂等键重复提交相同 / 不同参数 | 相同参数返回原任务；不同参数拒绝且不重复求解 |
| APS-AC-17 | 单 Worker 在求解或候选写入中退出，随后运行受控恢复 | 正式计划不变；候选写入全部回滚且审查端看不到半套结果；遗留版本标失败或从原快照创建新候选，过程可审计 |
| APS-AC-18 | 30日 horizon 之外仍有未来任务 | 近端详细计划可发布，未来任务显示结转；近端必需任务未排仍阻断 |
| APS-AC-19 | 独立校验器注入一个重叠资源预约 | 即使求解状态为 FEASIBLE / OPTIMAL 也拒绝发布并定位冲突 |
| APS-AC-20 | 复算 PRD 第13节订单样例 | 订单预计完成 2026-09-15 09:00；F1 3机时、王工1人时，数量不重复 |
| APS-AC-21 | M26 `aps_actual_occupancy` 存在 `end_at=NULL` 的人员和设备占用，分别提供可信 / 不可信的剩余工时 | 可信时生成固定资源的 carry 候选；不可信时阻塞至 horizon 并报原因；两者都不回写实际结束 |
| APS-AC-22 | P1：旧 Worker 租约过期后暂停，新 Worker 重新领取；随后旧 Worker 恢复并尝试写候选 | 待新增命令、attempt、租约和 fencing 模型后验证；不计入 FEAT-APS-001 当前 P0 完成率，P0 环境禁止启动第二 Worker |

## 15. PoC 与实施顺序

### 15.1 PoC-0：数据契约

- 冻结 `SolverInput` JSON Schema v1 与变量命名规则。
- 解决 P0 数据契约差距 APS-DG-01、03、04、05、07、08；记录 APS-DG-02 的 P1 扩展方式和 APS-DG-06 的产品边界。
- 建立 20 至 50 道任务的黄金数据，覆盖人机、日历、数量、共享批和锁定。
- 为每条硬约束建立独立校验器测试，不先追求复杂优化。

### 15.2 PoC-1：可行排程

- 使用已锁定的 OR-Tools `9.15.6755` 完成业务模型 PoC；Windows 目标运行时的 JNI、制品和进程启动已在 IMP-10 复验。
- 完成区间、候选资源、前置、NoOverlap、Cumulative、日历和锁定。
- 在 PRD 样例上逐项对比人工计划可复算结果。
- 保存求解状态、目标、bound、时间和模型规模。

### 15.3 PoC-2：数量与动态重排

- 增加数量门槛、转移批、共享批、供需配对和预测释放。
- 覆盖开放实际占用的 carry / 保守阻塞、倒排提示与统一有限产能复验。
- 完成人工拖动的影响闭包、固定闭包外计划和稳定性目标。
- 故障、请假、急单、部分报工、返工各做回归。

### 15.4 PoC-3：规模与生产门槛

- 使用 1k、5k、20k 任务分层数据，记录裁剪前后模型规模。
- 固定硬件比较快速启发式基线、CP-SAT 首解、时限内最好解和人工计划历史结果。
- 验证取消、单 Worker 崩溃与受控恢复、重复请求、过期结果、并发发布和回滚；多 Worker 租约/fencing 留到 P1。
- 通过许可证、漏洞、SBOM、目标运行时、内存和监控检查后，才形成正式采用决定。

### 15.5 退出条件

出现任一情况时启动 Timefold 或其他方案的同数据集对照 PoC：

- 核心约束无法在可维护模型中准确表达；
- 真实规模在裁剪和窗口分解后仍无法在业务时限内给出可用候选；
- 原生库部署无法满足目标环境；
- 动态重排或解释的自研复杂度明显超过替代方案；
- 团队无法建立稳定的 CP-SAT 建模与回归能力。

替换求解器不改变 `SolverInput`、候选计划输出、独立校验和发布契约。

## 16. 本期明确不做

- 不承诺所有行业、任意约束和任意规模下的全局最优。
- 不让自然语言或大模型直接写正式计划；AI 可以辅助配置、解释和提出方案。
- 不用一张甘特图的视觉重叠代替底层资源容量判断。
- 不把远期粗产能计划和近端具名人员详细排程混成同一粒度。
- 不在首版实现任意同步组、多源复杂返工、任意部分混批、多维炉容量和特定人机组合效率。
- 不用计划预测释放代替真实库存、质检放行或现场领料凭证。
- 不在求解过程中长时间持有 MySQL 事务，也不把整套模型变量逐条实时写库。
