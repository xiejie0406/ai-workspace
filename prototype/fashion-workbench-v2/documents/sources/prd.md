本系统面向内部销售，为团购和批发客户从自有商品库中选择单品或一至四品类组合，生成搭配示意及电商图片，核算销售报价，并交付可编辑 PPT。商品价格与库存来自企业维护的数据；每份已确认报价版本保留当时的商品、价格来源批次、库存业务时间和图片版本，使销售能够解释并复查报价。

本版是完整产品规格与交互原型的实施基线。用户此前授权 Codex 决定常规产品规则并连续完成本地原型制作与验证，因此已明确的产品默认值不再作为待问问题反复确认。最新执行边界是：产品与架构基线已经确认，`IMP-01`～`IMP-10` 十阶段执行包必须先由用户审核，审核通过后才启动新的生产实现。实际阶段、验证和用户决定分别见[控制入口](../../../../文档/项目/智能选品项目/README.md)、[Feature 任务清单](../../../../文档/项目/智能选品项目/功能/FEAT-FASHION-001-服装智能选品生产首版/任务清单.md)与[验证记录](../../../../文档/项目/智能选品项目/原型/服装工作台原型验证记录.md)。

本次交付对象是生产级 PRD 和高保真、可操作的完整原型：能处理实际本地文件、完成业务状态变化、复算报价并下载真实 PPTX。原型中的示例数据、规则推荐和样例图片任务须明确标识；生产系统的数据库、服务端鉴权、真实生图、真实京东采集适配和上线运行仍须按第 14 节取得对应证据。该区分不减少任一核心流程或将 AI 图片后置。

## 1 需求依据与本版变化

### 1 1 已明确的业务要求

- 商品资料支持导入，商品价格与库存分别支持全量更新。
- 获取京东商品图片，经 Chrome 插件下载后上传到系统。
- 支持单品、二品类、三品类、四品类报价，例如上衣，上衣加裤子，上衣加裤子加帽子，上衣加裤子加帽子加鞋。
- 为商品和组合生成 AI 示意图、电商图及模特示意图。
- 将选定的搭配和报价输出为 PPT。
- 首期由内部销售操作，为团购或批发客户提供服务。此项由用户在本次补充答复中明确。

### 1 2 与原始需求的关系

原始需求为 2026-08-30 的 V1.0 Word；关联任务为“规划需求文档与页面原型”。本版在其商品库、需求解析、搭配编辑和 PPT 输出基础上，细化全量更新、京东图片和一至四品类报价。原稿及旧原型将 AI 模特图后置，本版依据本次明确要求纳入首期。已有 HTML 原型只作为交互参考，不能证明新版功能已实现。

本版是服装项目后续讨论的需求正文；Word 导出版由本文生成，不单独维护第二套规则。旧稿保留原位置和原内容，供追溯使用。

### 1 3 产品边界

“报价”按现货商品对客户的销售报价理解；工厂成本核算、面辅料 BOM 和采购询价不进入首期。口述“ipa a”具体工具不影响业务定义：基础路径确定为 Chrome 图片插件下载、系统批量上传和映射；ImageAssistant 作为公开可核实的操作参考，不要求系统依赖某一插件品牌。RPA 或京东 API 直连保留为可选增强，不能影响基础路径交付。

### 1 4 v1.4 决定与版本边界

v1.3 的 17 项 REQ 和 32 项 AC 全部保留；本版按[历史数据库设计 v2.3](../../../../文档/项目/智能选品项目/归档/设计/2026-10-01-设计归一前/架构/数据库设计.md)的 16 表模型统一持久化口径，不改变产品状态或 P0 范围。首期仍为“一 SKU 一套当前销售价”，多客户价、渠道价和预约价另立未来需求，不进入首期。价格和库存不建立独立完整版本表或当前有效指针：`fq_product`、`fq_stock` 保存当前行，`fq_import_batch`、`fq_import_detail` 保存批次、逐行前后值和恢复依据。已确认报价版本由 `fq_quote`、`fq_quote_combo`、`fq_quote_detail` 三层记录自身留档，不另建报价快照表。需求正文仍只有本文件，生产任务转由 `FEAT-FASHION-001` 的唯一任务清单维护。既有 `prototype/business-suite-v1/` 与 `prototype/fashion-workbench-v2/` 保留为原型证据，不覆盖生产实现。

| 决定 | 本版默认值 | 可调整的边界 |
| --- | --- | --- |
| 客户与报价 | 内部销售服务团购/批发客户；默认备选报价 | 合并采购须主动切换，按实际选中项汇总 |
| 数量与候选 | 采购套数默认 100；四档默认各 2 个候选 | 每档 1–3 个，总候选不超过 12 个；采购套数须为正整数 |
| 价格与费用 | CNY 含税销售价；费用单列；优惠率默认 5% | 可改为固定折扣；未税模式需显式选择并填写税率，不能混算 |
| 取价 | 每个 SKU 读取唯一当前销售价 | 客户切换不改变基础售价；商务调整按报价修订留痕，不回写商品当前价 |
| 全量更新 | 价格按指定来源与商品范围、库存按指定仓库与商品范围严格全量 | 缺行整批失败，不提供“缺行自动归零”首期模式 |
| 时效 | 库存业务时间超过 24 小时需刷新或记录再次核实；报价默认有效 7 天 | 管理员修改后仅影响新确认版本；历史有效期保持 |
| 折扣授权 | 销售可优惠 0%–10%；超过 10% 或触发底价规则需负责人确认 | 负责人例外绑定单个报价修订版；更改商品/金额后例外失效；零额正式报价始终阻断 |
| 搭配和图片 | 默认递进比较、锁定基础款；每次图片任务默认 2 张，可选 1–4 张 | 商品变更使已采用关联图重新复核；原图拼版可交付但不记为 AI 生图成功 |
| 企业展示 | 品牌“织选”、16:9 商务模板、深蓝与暖白配色 | 品牌、Logo、联系人和颜色可配置；默认联系方式只作示例，正式版本须替换 |

演示样例中的采购量、预算、商品和联系人均为虚构。生产种子数据不得沿用样例身份或将样例库存置为真实已核实。

## 2 产品目标与市场依据

### 2 1 要解决的问题

销售目前需要跨商品表格找款、核对最新价格库存、挑选图片、组合服装并手工制作 PPT。价格更新、商品换色或客户更换预算后，容易出现页面图片、组合清单与报价不一致。系统应让销售在同一份方案中完成这些动作，并清楚知道哪些内容已确认、哪些仍需补齐。

“智能选品”在本产品中指从自有可售商品库中按客户需求筛选和搭配。销量预测、全网爆款发现和自动选供应商是不同业务，首期不包含。

### 2 2 竞品对产品范围的启示

| 对标对象 | 已核实能力 | 本产品采用的思路 |
| --- | --- | --- |
| [JOOR](https://www.joor.com/line-sheet-software) 和 [NuORDER](https://helpdesk.nuorder.com/hc/en-us/articles/16409979437339-NuORDER-Flat-File-SFTP-Integration) | B2B 数字目录、客户价、库存与商品维护 | 以商品及变体为基础，显示价格和库存更新时间 |
| [Vue.ai](https://www.vue.ai/products/outfit-recommendations/) | 基于商品目录、主题、库存及业务规则推荐搭配 | 先检查客户硬条件，再产生可编辑候选组合 |
| [Style3D](https://help.style3d.com/cloud/en/74be/0b0a/5abd1) 和 [FASHN](https://docs.fashn.ai/api-reference/tryon-max) | 服装及部分配饰试穿、视觉生产或 API | 作为图像供应商候选，实际四件一致性单独验证 |
| [Photoroom](https://help.photoroom.com/en/articles/11154440-how-to-use-ai-fashion-models) | 应用支持多服饰图组成 outfit，另有视觉 API | 重点评估多商品图与电商图片处理，核对应用和 API 差异 |
| [Botika](https://botika.com/resources/faqs) 和 [OnModel](https://onmodel.ai/misc/faq/?header=show) | 换模特、商品上身、部分批量流程 | 借鉴作图操作；公开鞋帽限制使其难以单独覆盖四品类 |
| [Plumsail](https://plumsail.com/docs/documents/v1.x/user-guide/processes/examples/create-pptx-from-template-processes.html) | 用模板和结构化数据生成可编辑 PPTX | PPT 使用已核算报价和已确认图片，避免再次人工抄录 |

以上是公开资料证实的局部能力。完整来源、日期与限制见本次调研；尚未完成实际产品试用和生成质量对比。本版采用自建商品、方案和报价工作台、按真实样本评估图像服务的路线。PRD 固定业务输入输出和质量门，不把未经样本测试的供应商固化为生产承诺。

### 2 3 成功标准

首要目标是缩短“收到客户需求至可发送 PPT”的时间，并避免图片错款、报价算错和库存误承诺。试点记录至少 10 个同等复杂度的历史或新方案，与人工方式比较；制作时间中位数降低 50% 为业务改进目标，须先取得人工基线，不能将页面操作速度替代全流程效率。

客观验收要求包括：报价金额可精确复算，正式导出与已确认版本一致，所有报价商品均可追溯，更新失败不污染有效数据。AI 搭配采纳率和图片可用率由业务人员评估，具体测试方法见第 13 节。

## 3 用户角色与业务对象

### 3 1 用户角色

| 角色 | 日常职责 | 权限边界 |
| --- | --- | --- |
| 商品运营 | 导入商品，维护价格库存，上传并匹配图片，修正属性 | 可发布授权范围内的数据批次，不能读取无权查看的成本或底价 |
| 销售或选品人员 | 录入客户需求，选择搭配，复核图片，生成报价和 PPT | 仅使用分配的客户及销售价格，可在授权折扣范围内调整 |
| 业务负责人或管理员 | 维护品类、当前销售价规则、人员权限及模板，决定例外 | 可处理低于价格底线等例外；首期用确认记录，无需建设复杂审批流 |
| 团购或批发客户 | 查看提案并线下反馈选中方案 | 首期接收文件，无需登录后台，客户版不包含成本价或内部备注 |

一人可以承担多个角色。首期按单企业内部工具设计；多企业 SaaS、租户计费和跨企业共享需另行定义。

### 3 2 术语与数量口径

| 对象 | 定义 | 示例 |
| --- | --- | --- |
| 商品款式 | 同一款号的商品主体 | 某品牌短袖款 TS100 |
| 颜色款 | 款式加颜色，通常对应同一组主图 | TS100 白色 |
| SKU | 可定价及核库存的最小销售变体 | TS100 白色 M 码 |
| 品类槽位 | 一套搭配里的商品角色 | 上衣、裤子、帽子、鞋 |
| 搭配方案 | 客户的一组候选搭配、图片和报价 | 秋季团购建议方案 |
| 组合或 Look | 1–4 个槽位组成的一个候选 | 白色上衣加黑裤加帽加鞋 |
| 组合数量 | 供客户选择的候选款数 | 每个品类档位 3 个候选 |
| 采购套数 | 客户实际需要的份数 | 某组合采购 100 套 |

同一品类采购 100 件仍为单品类；一双鞋按一个鞋类槽位计算。一个槽位首期选择一个款式及颜色，允许因尺码分配展开为多条 SKU。多尺码行不会增加品类数量。“生成 3 个四品类候选”和“采购其中 1 个候选 100 套”必须是不同字段。

## 4 首期范围与交付顺序

P0 为首期闭环必需项，P1 为可独立后续补充的增强项。下述顺序便于分段验证，不意味着将 AI 图从首期删除。

| 能力 | 首期 P0 | P1 或后续 |
| --- | --- | --- |
| 商品资料 | Excel或CSV导入、字段映射、查询、上下架、颜色尺码和原图 | 多来源自动归并、复杂供应商协同 |
| 价格库存 | 分别进行严格全量更新、校验、差异预览、批次历史与前后值追溯 | ERP 实时同步、增量接口、库存预占和订单 |
| 京东图片 | 维护京东映射、插件下载后批量上传、错图确认和重试 | 定制 RPA、插件直接入库、京东授权 API 自动同步 |
| 客户需求 | 客户、预算、数量、场景、品类及自然语言解析后确认 | 历史偏好学习、客户自助选品 |
| 搭配选品 | 1–4 品类、多个候选、锁定、替换、重搭、约束说明 | 超过四槽位、复杂叠穿、销售趋势优化 |
| 图片制作 | 原图拼版、AI 模特或搭配示意、电商图、复核和失败处理 | 视频、3D 服装建模、真人客户试穿及尺码预测 |
| 报价交付 | 销售价、数量、折扣、费用、版本、PPTX预览与导出 | 在线发送、客户在线接受、合同签署、支付 |

交付顺序为商品数据和核价、组合编辑、AI 图片、整套 PPT 联合验收。完整首期要求上述 P0 均达到验收标准；如果图像能力未达标，只能单独评审有限试点，不应称完整生产首期已完成。当前原型交付标准见第 14 节，实际模型验收仍是生产接入的必要项。

## 5 端到端业务流程

商品运营导入商品，分别校验并发布价格和库存导入批次，再将下载的京东图片上传并匹配到颜色款。发布事务直接更新商品当前价格行或库存当前行，批次及逐行前后值用于追溯；必要资料齐全后，商品进入可推荐状态。

销售新建客户方案，填写预算、采购套数及目标人群，勾选需要报价的品类档位。系统展示自然语言解析结果，销售确认后生成候选搭配。销售可锁定、替换单品，选择每个档位的备选方案。

销售为选中组合生成图片，核对真实商品原图与 AI 图；随后确认尺码、数量、价格、折扣和费用。系统复查当前数据变化，保存已确认报价版本，按模板生成 PPTX。客户反馈在线下发生，销售可记录选中结果，或复制已有版本继续调整。

页面顺序为“商品中心 → 客户方案 → 搭配工作台 → 图片工作台 → 报价确认 → PPT 交付”。销售应能从异常提示直接返回对应的图片或商品位置，不必重建整个方案。商品运营和销售从各自默认首页进入，跨页切换保留客户方案及草稿状态。

## 6 商品中心

### REQ 01 商品资料导入与维护

支持 Excel、CSV 和页面手工维护。导入过程为选择模板或映射列、校验、查看新增及修改差异、确认生效、下载结果。重复提交同一批次不应重复建商品。

| 字段组 | 核心字段 | 规则 |
| --- | --- | --- |
| 标识 | 数据来源、内部款号、颜色代码、SKU、品牌、商品名 | 使用来源与内部 SKU 定位；禁止只用商品标题匹配 |
| 分类 | 一级品类、细分类、槽位角色 | 至少能映射至上衣、裤子、帽子、鞋；裙装等可另配模板 |
| 规格 | 颜色、尺码、单位、材质、季节、人群 | 颜色尺码以实际资料为准；无尺码配饰可用均码 |
| 商务 | 当前销售价、可选成本价、仓库、可售数量 | 由独立价格和库存批次管理，不由图片或模型推断 |
| 图片 | 主图、细节图、京东商品ID及链接、图片来源 | 图片匹配到颜色款或明确 SKU，至少一张已确认原图 |
| 状态 | 上下架、资料完整性、可推荐性、更新时间 | 缺图、缺价、库存未知分别说明原因 |

商品资料导入默认更新所映射的非空字段；清空可选字段须显式选择并在预览列出字段，必填字段不允许清空。价格和库存不随普通资料导入静默覆盖，应进入专用更新流程。未知价格或库存 SKU 先报错，不自动生成残缺商品。

允许保存缺图或缺属性的商品草稿。正式候选须满足当前需求必要资料，缺价格或库存不可用的商品不进入可交付候选池。成本价不是基础选品必填项，若使用毛利底线规则则需另行补齐。

### REQ 02 价格全量更新

“全量”定义为：在已选来源和商品范围内，以一个业务时间点建立一次完整导入批次。范围在开始校验时冻结为 SKU 清单，范围内在用 SKU 的当前销售价均须明确提供；范围外数据不受影响。该批次不是独立价格版本表，也不通过当前版本指针取价。首期一个 SKU 在同一时点只保留一套当前销售价，不支持客户价、渠道价、阶梯价、预约生效价或自动到期回退。默认范围为所选来源的全部在售 SKU；运营若选择品类等子范围，界面必须持续显示“范围全量”及 SKU 数，不能显示成全库更新。将来确有同一 SKU 同时存在多套价格时，必须通过新需求、表结构迁移和兼容方案引入，不能提前宣称本版支持。

更新必须展示文件来源、业务时间、应覆盖和实际覆盖 SKU 数、新旧价格差异、缺失和重复行。价格字段必须有币种、计价单位及含税口径，默认人民币、含税销售单价。空值、负数、重复键、单位冲突和缺行使整批失败；0 可用于暂不可报价的资料记录，但阻断零价商品进入正式报价。新增或下架 SKU 导致校验范围改变时，旧预览作废并要求重新校验，不能忽略新 SKU 后发布。

报价统一读取 SKU 当前销售价；缺价、币种不符、税费口径不符或价格业务时间非法时提示不可报价。显式调整报价单价属于商务例外，不回写商品当前价；须记录原价、调整价、原因、授权人和报价修订版本。商品图上的标价和京东展示价均不覆盖本系统当前销售价。

### REQ 03 库存全量更新

全量范围至少包括来源、商品范围、仓库和库存业务时间。输入值为业务确认的可售数量；如果源系统只提供账面量，必须先明确扣减预占等规则，不能由 AI 猜测。

严格全量要求范围内应覆盖的 SKU 全部出现，库存为非负整数，明确的 0 表示缺货。缺行、空白或未知 SKU 均使整批不生效，不能自动视为 0 或保留旧值后宣称全量成功。首期没有“未出现即归零”模式；停用商品应通过上下架状态处理，不能借空白文件清空库存。

价格与库存更新各自独立；系统记录两者的来源批次和业务时间，不能把同日上传说成实时同步。发布时重新校验 `scope_hash`、`base_data_hash` 和目标行 `row_version`，并在一个事务中更新 `fq_product` 价格字段或 `fq_stock` 库存行，同时写入 `fq_import_detail` 实际前后值和批次结果；任一写入失败即整体回滚，原当前行保持不变。旧时间数据默认拒绝覆盖新时间；并发修改使任一摘要或行版本变化时必须重新预览。

运营可按导入批次查看 `fq_import_detail` 保存的 `before_data` 和 `after_data`，并选择明确的历史值发起恢复。恢复必须生成新的 `restore` 批次：以当前值作为新的 `before_data`、以选定历史值作为拟写入值，重新执行完整范围、摘要和行版本校验；成功后再事务更新当前行，不能移动所谓“当前版本指针”。恢复旧库存不表示库存重新确认，恢复值仍保留原始业务时间并按原时间判断过期。库存业务时间超过 24 小时标为需刷新；正式导出前须发布新库存，或由有库存核实权限的运营逐 SKU 记录核实数量、来源凭据摘要、核实人及时间。核实不是修改旧批次时间，且只覆盖明确列出的 SKU；销售单击“已了解”不能解除该阻断。未来时间超过服务器时间 5 分钟的批次拒绝，避免错误时钟让库存长期不过期。

### REQ 04 京东图片获取与入库

首期基础路径为：选择内部商品 → 维护京东链接及商品 ID → 运营在 Chrome 中使用图片插件下载 → 以文件或 ZIP 批量上传 → 自动建议匹配 → 人工确认主图与细节图。系统提供映射表模板，包含内部款号、颜色或 SKU、京东 ID、文件名和图片用途。

优先用明确映射表或规定文件名匹配；标题和视觉相似性仅能提出建议。京东商品 ID 与企业 SKU 不默认一一对应；同款不同颜色必须核对，配图不能误挂到另一颜色。相同内容可去重存储，但商品关联仍各自保留。

支持 JPG、PNG、WebP，显示像素和预览；过小、模糊、错色、拼接详情长图或带促销文案的图片需人工选取适当用途。上传失败只重试失败项，重复上传不重复添加同一关联。文件解压不接受路径越界或超出配置大小的内容。

图片至少记录来源链接、来源商品 ID、取得时间、上传人和企业确认的使用范围。进入模型生成或客户提案前，所用素材须处于可使用状态。插件不需要接触企业价格、客户报价或后台凭据。

插件未取到图片时显示待补图，运营可重新下载或手工上传。登录或页面变化不能被记录为采集成功。系统提供下载步骤、规范文件名和映射模板，适配任何能够导出支持格式的 Chrome 插件；首期不依赖插件直接写入本系统。生产试点需用真实授权商品完成一次“京东页面下载 → 文件上传 → 颜色款确认”实测，不能把通用图片提取能力等同于已通过京东适配。

### REQ 05 商品理解与人工修正

AI 可根据图片和文本建议品类、颜色、风格、场景、季节及可观察外观标签。页面同时保留 AI 建议和人工确认值，后续推荐优先使用人工确认。面料成分、品牌、尺码、价格、库存和质量认证等事实不得依据图片猜填为已确认。

资料调整后仅重新分析受影响商品。图片替换导致颜色或品类判断变化时，提示复核现有标签；标签任务失败不影响已保存商品及人工标签。当前主图或某次生成使用的素材被更正、替换、禁用时，即使 SKU 未变，相关草稿和采用的 AI 图也须标为需复核，新交付须处理该变化。仅新增未使用的细节图不自动使所有旧图失效；历史报价始终保留原素材版本。

### 6 2 批次确认、发布与恢复

价格批次先选择来源和商品范围，库存批次另选来源、仓库和商品范围，再上传；系统在一致性读取中冻结应覆盖 SKU 集合，生成 `scope_hash`，并根据目标当前行的业务字段、`row_version` 或不存在标记生成 `base_data_hash`，再完成全文件校验及差异预览。预览显示新增/变更/不变/缺失/错误数量、业务时间和影响到的草稿数量。存在任何阻断错误时没有生效入口；用户修正后产生关联的新批次，旧失败记录仍可查询。

发布不切换独立有效版本或当前指针。服务端须重新计算并比较 `scope_hash`、`base_data_hash` 及目标行 `row_version`；一致时在一个事务中更新 `fq_product` 当前价格字段或 `fq_stock` 当前库存行，并同步把实际 `after_data`、明细状态和批次成功状态落库，不能分段提交后显示整批成功。重复点击、网络重发或同一文件同范围同业务时间再次提交返回已有批次结果；同文件换业务时间视为新的声明，仍需完整校验。价格与库存各自独立发布，不要求两种数据同时成功。范围或任一目标行发生变化都必须返回冲突并重新预览，禁止最后写入者静默覆盖。

发布前可取消，取消后当前商品价格或库存行不变；发布事务内取消若来不及，返回已生效事实及恢复入口，不显示虚假的取消成功。恢复历史价格或库存须展示所选历史批次的 `before_data` 或 `after_data`、目标范围、原业务时间、当前值和受影响草稿；经授权运营确认后建立新的 `restore` 批次，以当前值形成新 `before_data`，按正常发布规则重新校验并事务写入，历史报价不变。恢复造成 SKU 缺失、当前商品不存在或范围冲突时拒绝直接恢复，须重新完整导入。

## 7 客户需求与一至四品类搭配

### REQ 06 新建客户方案

必填客户或客户简称、方案名称、要报价的品类档位、预算口径和采购数量；补充场景、季节、人群、风格、颜色偏好、禁止项及交付日期。预算应明确“每套或每件”及“整次采购总额”，并写明是否含费用，默认均按最终对客应付金额判断。

方案名 1–100 字，客户简称 1–80 字；预算为空表示不设预算上限，0 不是未填写；输入预算时必须为正数。采购套数为 1–100000 的整数。客户记录包含名称、联系人、客户类型、地区、分配销售和内部备注；联系人和内部备注均不是生成图片所需字段。切换客户必须重新核对当前价格的来源批次、业务时间、`row_version` 及该客户的方案访问权，不能沿用原客户已确认报价。

支持自然语言输入并展示结构化理解结果。例如“给 100 人准备活动服装，分别出上衣、上衣加裤子、加帽子、加鞋的报价，每档 3 个候选，每套含运费不超过 300 元”。系统应区分 100 套采购量、4 个品类档位、每档 3 个候选，以及全单和单套预算。低置信或互相矛盾的条件须由销售修正后继续。

未取得尺码分配时可以探索款式和形成参考预算，但不得标记为已核实 100 套可供货。正式报价需要完整尺码配比，或记录业务已核实且适用的均码采购方式。

### REQ 07 组合模板与候选生成

| 档位 | 默认槽位 | 展示目的 |
| --- | --- | --- |
| 单品类 | 上衣 | 单件采购报价及商品展示 |
| 二品类 | 上衣、裤子 | 基础套装和组合价格 |
| 三品类 | 上衣、裤子、帽子 | 在套装上增加配饰的报价 |
| 四品类 | 上衣、裤子、帽子、鞋 | 完整搭配和报价提案 |

销售可以选择一个或多个档位。默认档位对应用户提出的例子；管理员可配置其他模板，但每个模板的槽位互异、数量不超过四，且模板版本进入方案记录。首期一个槽位一个颜色款；复杂外套叠穿等另行扩展。

可选择“各档独立选款”或“递进比较”。递进比较时，下一级继承已锁定基础商品，例如同一上衣逐级加裤子、帽子和鞋，方便客户理解新增费用；独立模式允许各档选择不同商品。界面必须说明当前模式，不能在增加品类时悄悄换掉基础商品。

生成先检查品类、上下架、客户明确排除项、数量及尺码可供货、预算和价格权限，再按风格、颜色及场景给出候选和简短理由。预算比较使用与报价相同的折扣、费用和税口径；尚未给定商务调整时使用页面显示的默认调整，不只比较裸商品价。主观匹配不能抵消库存不足或超预算等硬性失败。AI 返回的商品都必须对应库内稳定商品标识。

尚未提供尺码配比时允许“参考选款”，明确显示未完成逐 SKU 核验。系统可按目标套数给出可编辑的整数均分建议：依尺码排序均分，余数顺序分配，各槽位总数准确守恒；该建议须销售确认，不代表真实客户尺码分布。参考选款不得直接确认正式报价。递进模式变更基础款时，受影响档位展示批量更新清单；有单独锁定冲突时保留旧组合并提示选择，不自动拆锁。

候选数不足时展示实际数量和原因，例如“符合预算且有指定尺码的鞋不足”。允许销售改预算、数量或范围后重试，不能自动放宽硬条件或编造商品凑数。同一组内完全相同组合去重，可设置单个商品复用上限以增加差异。

### REQ 08 人工编辑与约束复核

支持锁定某件、替换同品类、保持锁定重搭、整套重生、调整候选顺序、修改文案和选择要交付的候选。替换后即时更新报价和库存判断，旧 AI 图标为待重生成或复核；异步返回的旧结果不能覆盖销售刚做的修改。

颜色或尺码变化重新绑定相应图片与 SKU。仅改变文字说明或报价数值时可复用原图，但 PPT 必须使用新方案版本。保存草稿、刷新页面和失败重试均应保留已确认内容。

## 8 图片工作台

### REQ 09 图片类型和生成入口

| 图片类型 | 输入与输出 | 使用位置 |
| --- | --- | --- |
| 商品原图拼版 | 选中 1–4 件真实商品原图，按槽位排列 | 搭配编辑和 PPT，作为商品清单直观对照 |
| AI 模特或搭配示意图 | 确定的商品图、模特设定、场景和姿势，生成穿着效果 | 客户理解整体搭配，不承担尺码合身保证 |
| 电商商品图 | 单品或组合原图，加纯色或场景背景及版式 | 下载供电商使用，也可作为 PPT 配图 |

“AI 示意图”与“模特示意图”共用同一生成工作流，不重复建设两个只换名称的模块；选择有模特或无模特搭配画面即可。电商图首期默认保留商品主体，支持抠图、背景及阴影，若模式会改变服装主体必须明确提示并按同样标准复核。下载图片不等于自动发布到京东店铺。

销售先选组合再生成，可设置模特呈现、场景、姿势、画幅和候选张数，每次 1–4 张、默认 2 张。生成前展示所用商品与原图、预计张数、预计费用或积分、可用额度及任务来源；额度不足不提交。默认使用供应商提供的可用模特或企业可用素材，不收集终端客户人像。模特全身图默认 3:4，电商图默认 1:1；可选 4:5 与 16:9，至少提供 1024 像素长边交付规格，实际以所选供应商支持能力限制选项。

原型必须提供两种清楚分开的可操作入口：“体验样例任务”展示排队、失败、复核、采用、取消和版本失效；“上传已生成图片”接收用户已有的真实模特图或电商图并走同一复核流程。样例任务结果标记样例，不宣称针对任意上传商品实时生成；上传图片标记来源为外部上传，不伪造供应商任务、生成时间或费用。生产接入模式启用真实供应商后才显示“生成”，并采用同一套复核及版本规则。

### REQ 10 商品一致性与图片复核

原图与生成图并排展示，销售逐项确认槽位数量、商品款式、颜色、印花或 Logo、鞋帽完整性、穿着自然程度和关键细节。四品类组合若只出现上衣裤子，不能当作完整成功。不可见背面由模型推断时不能用作真实细节图。

系统为每张图记录组合版本、输入商品和图片版本、生成时间、供应商及任务标识、人工复核人和结果。错误图可标记问题并重试或替换上传，未通过图片不能进入正式客户 PPT。复核必须选择通过项或失败原因，不能用查看图片自动推定已确认；失败原因至少含缺件、错款、错色、标识错误、姿态异常和质量不足。生成图显示“AI 搭配效果示意”，实际商品以原图和规格为准；单品方案图里的非报价陪衬服饰标注不包含，并尽量避免干扰主体。电商图仍需商品一致性确认；原图拼版不是模特图，也不能用“AI 已生成”标签表示。

### REQ 11 异步任务与失败处理

任务状态为待提交、排队、生成中、待复核、已采用、未采用、失败或取消。系统展示阶段进度和超时反馈，不虚构精确剩余时间。可只重试失败图片，重复点击不重复创建同一任务；主动增加候选为新任务。

多图任务部分成功时保留成功图，失败图独立处理。修改商品后返回的旧图进入旧版本记录，不能自动变成当前采用图。取消只阻止后续使用；供应商已处理的任务可能仍产生费用，应记录实际账单状态，不能承诺必然退款。

若图片始终不可用，销售可选择“使用商品原图拼版交付”，PPT 明确采用原图方案，任务仍记为生成失败或未采用。此降级保证报价可继续，但不能替代首期 AI 生图功能验收。

超时进入“待查结果”，先按供应商任务 ID 查询，不能直接重提并造成重复扣费。自动重试仅限确定未接收或明确可重试的网络失败，最多 2 次；内容质量问题需要销售主动创建新候选。重试、取消、部分成功和未知账单均保留任务关联记录。恢复页面时从已保存任务状态继续，生成失败不清空客户需求或已采用图片。

## 9 报价规则与库存核对

### REQ 12 报价计算

价格由 SKU 当前销售价和已确认商务调整产生，金额计算不得由生成模型自由输出。报价保留单件或单套金额、采购量、折扣额、费用和应付总额。以人民币含税销售价作为默认口径，税额说明与加收税费不能重复出现。全部商品的税费模式和报价币种一致后才能核价。

计算顺序固定为：SKU 行金额等于销售单价乘实际采购数量；商品合计等于各行金额之和；折扣金额按商品合计计算并四舍五入至分；含税模式应付总额等于商品合计减折扣金额再加附加费用。首期只选整单折扣率或固定折扣额其中之一，避免叠加歧义；费用名称及含税口径必须明确。费用默认名称“运费”，默认 0，演示方案可显式预填 300.00 元；页面必须把演示预填与模板默认区分。服务端和数据库使用固定精度 `DECIMAL` 保存、计算金额与百分率，在规定核算层四舍五入到分；不得使用 `FLOAT`、`DOUBLE` 或其他二进制浮点参与报价计算。

人民币单价、附加费用和固定折扣额最多两位小数，超精度导入报错，不静默取整。折扣统一表示优惠比例，如 95 折即优惠 5%；优惠比例允许 0%–100%，最多两位百分数小数，仍受销售权限及底价限制。固定折扣不得超过商品合计，费用不得为负，应付总额不得为负；0 单价商品、100% 商品折扣或 0 应付额只可保存为参考草稿，不能确认为正式报价。固定折扣的授权比例按固定折扣额除商品合计计算，不能通过切换折扣类型绕过 10% 上限。平均每套金额四舍五入至分，仅作展示，不反向乘回覆盖整单总额。

如按未税价加税，须显式选择未税模式，所用 SKU 的当前销售价须统一为未税口径，并填写业务提供的税率；税率为 0%–100% 且最多两位百分数小数，0 必须明确确认，不能把空值当作 0。每项费用选择应税或已含税/不再加税。税基＝商品合计−商品折扣＋应税费用，税额＝税基×税率后一次四舍五入至分，应付＝商品合计−折扣＋全部费用＋税额。默认含税模式的加收税额固定为 0，不再由展示税率重复计税。此处定义计算约定，不判断业务适用税率；首期不支持一个报价内混合税率。

例如未税商品合计 100.00 元、优惠 5%、应税运费 10.00 元、业务输入税率 13%，税基 105.00 元、税额 13.65 元，应付 118.65 元；税率仅为虚构计算示例。改为含税商品和含税运费后应付 105.00 元，不能继续加 13.65 元。

低于授权销售底价或超过销售折扣权限时，不能直接正式导出；业务负责人可调整或记录允许本次报价的原因和范围。默认销售优惠上限 10%；例外记录包含报价修订号、原值/允许值、确认人、时间、原因和到期时间，报价内容改变即失效。成本未提供时不启用虚构的毛利判定；可配置的销售底价若存在则由服务端判断。底价或成本不可见的销售只看到“需负责人确认”，不能由提示推算隐藏价格。

### REQ 13 备选方案与实际采购

默认输出为“备选报价模式”：每个候选分别核算，客户任选，不把所有候选金额相加，也不把备选之间共享 SKU 的库存重复消耗。单品至四品类的递进档位同样属于备选，除非销售明确勾选合并采购。

“合并采购模式”只对已选中的组合及各自采购数量汇总。同一 SKU 在多个选中组合中的需求必须累计后比较可售量。PPT 顶部说明是备选比较还是合并采购，避免客户把不同口径混用。

备选模式的折扣和费用分别应用于每个候选的独立报价，并在比较表表明“费用按该候选整单计”；合并模式先汇总所选组合商品金额，再对整单应用一次折扣、一次费用及税额。切换模式即作废先前确认的报价预览并重算，不能把多个候选各自折扣后金额直接相加冒充合并计算。空选中项不可生成正式报价。

### REQ 14 尺码库存与可供套数

每个槽位每套默认 1 件或 1 双，采购套数会展开为相应 SKU 的数量。均码组合的可供套数为各项可售量除每套用量并向下取整后的最小值。非均码商品必须逐 SKU 检查尺码配比，不能只按款式总库存计算。

每个组合、每个槽位的尺码数量之和必须等于采购套数乘每套用量，各行数量为非负整数；同一槽位重复 SKU 先合并，不允许重复计数。采购 100 套时，上衣 M 60 件加 L 50 件属于超配，上衣总计 90 件属于缺配，均不可正式确认。合并采购先分别检查每个组合的配比，再跨组合汇总同一 SKU 需求。

默认以选定仓库或明确可合并的仓库范围核验。多仓未批准合并时不能直接相加。库存不足则显示缺少的具体款色尺码及数量，可替换、减少采购量或重新核实；补货日期未知时不自动承诺交期。

正式报价通过库存检查只表示“截至所记录时间已核实可售”，首期不进行库存预占或订单扣减。PPT 写明库存核对时间和最终订货需复核。报价有效期控制价格承诺时间，不等同锁定库存。

各槽位默认每套用量为 1；首期不支持用户把同一槽位每套数量改成 2 后仍称原模板。上衣、裤子、帽、鞋的单位分别显示，鞋的尺码行数量表示“双”。调整采购套数后保留原配比比例并给出整数分配预览，须确认新分配后重新核库存；不能只修改总套数而让旧 SKU 数量留存。删除全部尺码行或分配不存在的尺码均阻断。

### REQ 15 报价版本与变化处理

销售确认时创建不可静默改写的已确认报价版本，包含客户、模式、候选或采购清单、SKU、数量、单价、折扣、费用、价格来源批次、库存业务时间、图片及模板版本、有效期和备注。该版本由 `fq_quote`、`fq_quote_combo`、`fq_quote_detail` 三层记录自身冻结和留档，不另建报价快照表；后文“已确认报价版本”均指这三层记录的同一版本。

默认有效期为确认日起 7 个自然日，以 Asia/Shanghai 时间显示明确到期时刻；允许 1–30 天，超过默认值须在商务说明清楚展示。过期报价可查看、复制和标明“已过期”后内部下载；重新面向客户交付须基于最新数据确认新版本。作废须填写原因，作废记录保留，不能恢复原编号为有效版；复制产生新草稿、新修订号。

价格或库存全量更新后，已确认报价版本中的冻结价格、来源批次和库存核验值保持原值。当前草稿提示受影响项，销售选择刷新并重新核价。正式导出新版本前比较 `fq_product`、`fq_stock` 当前行及其来源批次、业务时间和 `row_version`：价格变化须接受新价或取得保留旧价的业务确认；库存变化重新检查可供货；所用原图更正或禁用须复核关联 AI 图及素材可用性。已经发出的文件不能被系统远程更新，可重导出原版本并保留原日期和过期状态；若历史素材已被明确禁用，则限制再次对外导出并提示创建修订版。

生成 PPT 期间新数据到达时，生成内容仍来自同一个已确认报价版本，并提示存在更新待复核，不允许半份 PPT 使用旧价、半份使用新价。

### 9 1 可复算的报价示例

以下为虚构说明数据：上衣 80 元、裤子 60 元、帽子 20 元、鞋 90 元，均为含税单价；每槽位每套 1 件或 1 双，各项已确认可供至少 100 套。

| 备选档位 | 每套商品金额 | 采购 100 套商品合计 |
| --- | --- | --- |
| 单品类上衣 | 80.00 元 | 8,000.00 元 |
| 二品类上衣及裤子 | 140.00 元 | 14,000.00 元 |
| 三品类增加帽子 | 160.00 元 | 16,000.00 元 |
| 四品类增加鞋 | 250.00 元 | 25,000.00 元 |

客户选择四品类 100 套，整单 95 折，运费含税 300 元：商品合计 25,000.00 元，折扣 1,250.00 元，最终应付 24,050.00 元，含运费平均每套 240.50 元。上表四档不得相加为客户应付总额。

若帽子库存从 130 顶更新为 90 顶，100 套四品类方案应提示短缺 10 顶；历史报价金额保留，新的正式交付需要补充核实、换款或减少数量。若客户合并购买 60 套三品类和 50 套四品类，同款帽子需求为 110 顶，不能分别比较 60 和 50 后都判可售。

## 10 PPT 方案与图片交付

### REQ 16 PPT 内容和布局

首期提供一套可配置企业 Logo、颜色和联系方式的固定模板，包含 1–4 品类页布局。可选择要交付的候选、调整顺序和编辑文案；首期不建设完整在线自由拖拽演示文稿编辑器。

| 页面 | 必须表达的内容 |
| --- | --- |
| 封面 | 客户、方案主题、日期、方案及报价版本 |
| 需求与报价口径 | 场景、人群、品类档位、预算、采购量、备选或合并模式 |
| 档位比较 | 一至四品类的组成、每套价格、采购金额和差异；只展示本次勾选档位 |
| 组合详情 | 每个选中候选一页或自动续页，原图、采用的 AI 图、品类、商品款号、规格、价格、数量及搭配理由 |
| 报价明细 | 选中方案的 SKU 明细、折扣、费用、总额、币种及税费口径 |
| 商务说明 | 有效期、库存核对时间、交付条件、AI 示意标识和联系方式 |

单品页突出商品；二品类并列展示；三或四品类提供原图清单与模特图的对应关系。报价汇总不得只显示一个未说明口径的“大总价”。较长商品名称或尺码明细自动换行、续表或续页，不能省略关键字段。

### REQ 17 生成预览与下载

导出前执行缺图、图片复核、报价口径、价格变化、数量与尺码、库存和权限检查。显示阻断项和可修正入口，通过后选择模板、生成文件并预览，再下载 PPTX。失败可基于同一已确认报价版本重试，不能迫使销售重新编辑方案。

PPTX 内的标题、说明、SKU 和金额表须可编辑，商品及 AI 图作为嵌入图片，可离线打开。不能使用整页截图作为全部内容。图片保持宽高比，主体适配，禁止拉伸或裁掉鞋帽等关键物品。成本价和内部备注不能隐藏在备注页、图层或文档元数据中。

画幅为 16:9；同时支持单张 AI 图、电商图和整组图片 ZIP 下载，文件名包含方案简称、版本、图片用途和序号。ZIP 包含图片清单，写明关联商品、来源类型和复核状态，不夹带内部报价信息。原型导出的客户演示 PPT 明确标记示例身份与图片来源；正式生产 PPT 必须使用已经确认可交付的真实资料。

PPTX 以原生可编辑文本和表格为主，文件下载后需要检查实际包结构及页面视觉；生产发布前再在部署验收指定版本的 PowerPoint 与 WPS 实际打开、编辑一处金额说明并另存。该兼容目标不是单凭文件扩展名可判定的结果。客户或销售在外部软件修改文件后，不自动回写系统；系统中的已确认报价版本保持不变。

## 11 页面与状态要求

### 11 1 页面清单

| 页面 | 主要操作 | 必要反馈 |
| --- | --- | --- |
| 商品库与详情 | 检索、筛选、编辑、上下架、查图价库存 | 缺资料、不可售原因、版本及时间 |
| 导入和更新中心 | 资料导入、价格全量、库存全量 | 范围、覆盖率、差异、错误、发布或取消 |
| 图片采集与素材 | 京东映射、批量上传、选主图 | 待匹配、疑似错色、失败项和使用状态 |
| 客户方案列表 | 新建、查询、复制、关闭 | 客户、版本、进度和待处理事项 |
| 搭配工作台 | 条件、档位、候选、锁定和替换 | 预算、尺码库存和无法生成原因 |
| 图片工作台 | 生图、比较、复核、采用、重试 | 异步状态、预计及实际用量 |
| 报价和 PPT 交付 | 数量、价格、模式、费用、预览和下载 | 最新数据差异、版本、有效期和导出结果 |

商品资料空时提供导入入口；候选为空时解释限制；操作中提供状态和取消能力。无权限时拒绝读取或写入对应数据，不只是在页面隐藏按钮。外部任务失败保留用户输入及成功结果。

### 11 2 状态与恢复

| 对象 | 主要状态 | 恢复原则 |
| --- | --- | --- |
| 导入批次 | 待校验、校验失败、待确认、生效、取消 | 失败不改有效数据；修正文件后产生新批次 |
| 方案 | 草稿、候选生成中、待确认、已确认、已关闭 | 可复制旧版本；关闭保留记录 |
| 图片 | 排队、生成中、待复核、已采用、失败、取消 | 只重试失败项；旧任务不能覆盖新组合 |
| 报价版本 | 草稿、已确认、已过期、已作废 | 修改产生新版本，历史保留 |
| 导出任务 | 排队、生成中、成功、失败、取消 | 基于同一已确认报价版本重试，保留已成功文件 |

“可报价”是当前数据检查结果，“已确认”是保存的业务决定，“已下载”是实际文件交付动作，三者不能混为一个状态。首期可以由销售记录客户反馈，但不自动把下载当作成交。

### 11 3 交互与冲突处理

| 触发 | 用户看到的状态及可执行动作 | 必须保持的事实 |
| --- | --- | --- |
| 第一次进入或空数据 | 商品导入、使用明确标记的示例、查看操作说明 | 不把样例复制为真实企业商品，不伪造已成交方案 |
| 文件校验失败 | 行级错误、下载错误报告、重新选择文件；保留映射和范围 | 当前商品价格或库存行不变，无部分成功的全量批次 |
| 候选条件无解 | 列出预算、品类、库存或排除项原因，可逐项调整 | 不悄悄放宽硬约束，不创建不存在的 SKU |
| 保存或下载处理中重复点击 | 操作显示进行中，复用任务结果 | 不生成重复方案、重复费用或多个逻辑相同的版本 |
| 草稿在另一标签页或用户处更新 | 显示已有新版本，保留本地未保存副本，可重新载入或复制 | 不静默覆盖他人修订，不把冲突显示为保存成功 |
| 关闭弹窗或切页 | 输入可恢复；会丢失未保存输入时显示保存/放弃/继续编辑 | 取消是退出当前动作，不等于删除已有业务记录 |
| 商品、价格、库存或素材改变 | 具体差异、受影响对象、跳转修正入口；报价需再确认 | 已确认报价版本保持，旧任务结果不进入新组合 |
| 本地存储已满或写入失败 | 清楚提示未保存、可下载备份并清理本原型数据 | 不显示保存成功，不破坏上一份可读取状态 |
| 请求结果不明或外部超时 | 待查结果，可按任务 ID 查询或稍后继续 | 未知不等于失败；不自动重复扣费 |
| 文件生成失败 | 展示原因，重试同一已确认报价版本，保留已确认输入 | 已冻结金额不重算为新价，不产生空文件冒充成功 |
| 无权限、会话过期 | 明确拒绝并保留可恢复草稿；提示重新登录或联系授权角色 | 生产 API 同时拒绝，不能以页面隐藏作为权限证明 |

桌面布局以 1440×900 为主要评审尺寸，同时验证 1280×720、1024×768 与窄屏浏览；表格可横向滚动但标题、主操作、校验信息不截断。所有主要操作具备清楚文字、键盘焦点、表单标签和错误关联；状态不只靠颜色表达，弹窗可用 Escape 关闭并回到原焦点。异步状态通过可读文本提示，不能只显示无限旋转图标。

### 11 4 角色操作矩阵

| 操作 | 销售 | 商品运营 | 业务负责人/管理员 |
| --- | --- | --- | --- |
| 查看自己被分配的客户、销售价及方案 | 允许 | 未分配时拒绝客户方案内容 | 按企业管理范围允许 |
| 导入商品、图片、价格或库存并发布/恢复 | 拒绝 | 允许授权来源/商品范围/仓库 | 允许企业范围 |
| 建方案、搭配、复核图片、普通报价、下载客户 PPT | 允许自己方案 | 需同时具有销售角色 | 允许授权客户范围 |

原型角色切换用于展示拒绝状态，浏览器状态可被本机用户修改，不能承担生产安全边界。生产权限必须在每次服务端读取、变更、任务回读和文件下载时校验企业、客户归属及字段权限；下载地址不得通过更改 ID 访问他人文件。已确认报价版本按对客字段白名单冻结，避免成本在隐藏列、备注、CSV、PPTX 元数据或备份入口泄露；实现只使用 `fq_quote`、`fq_quote_combo`、`fq_quote_detail`，不另建报价快照表。全企业内部备份不属于客户交付文件。

## 12 非功能要求

以下为生产设计与验收目标，未写成已实测性能。原型使用小规模示例或用户本地数据验证流程和算法边界，不以浏览器演示证明 10 万 SKU 的生产吞吐。

| 类别 | 默认目标 | 验收方法及失效行为 |
| --- | --- | --- |
| 容量 | 10 万在售 SKU、每 SKU 最多 5 张当前关联图片、单批 10 万价格/库存行、20 名并发用户 | 生产候选环境明确 CPU/内存/数据库/网络版本，在基线数据量和并发下执行；超过单文件限制先拒绝，不崩溃后部分保存 |
| 查询 | 商品检索 P95 ≤3 秒；普通页面交互立即反馈处理中 | 混合关键词/筛选 100 次以上样本，记录全链路耗时与错误；失败提供可重试入口 |
| 批次 | 10 万行完整校验 ≤5 分钟，事务发布当前行时不暴露部分数据 | 覆盖成功、缺行、重复键、`scope_hash` / `base_data_hash` / `row_version` 冲突和进程失败；展示进度而非阻塞页面 |
| 候选 | 每轮最多 12 个，30 秒内返回或进入可恢复异步状态 | 记录实际找到的有效候选与原因；无结果不无限请求 |
| PPT | 20 页、40 张图，2 分钟内生成或给出可恢复超时结果 | 检查实际下载、包结构、页面、金额及文本可编辑；不以按钮反馈代替文件证据 |
| 金额和完整性 | 固定精度十进制金额按规则舍入到分；正式导出 100% 引用单一已确认报价版本；全量失败 0 当前数据污染 | 独立 `DECIMAL` 复算、故障注入和确认版本差异检查，不靠模型判断，不使用浮点 |
| 可用性 | 生产服务月度可用性目标 99.5%；业务故障须可诊断和恢复 | 监控登录后关键读写及导出任务，维护窗口单独记录，不把 AI 供应商故障隐藏为成功 |
| 备份恢复 | 数据 RPO ≤24 小时，RTO ≤4 小时；每天自动备份，至少保留 30 天 | 发布前至少完成一次隔离环境恢复，核对 SKU 当前行、来源批次及前后值、报价金额、素材引用与审计链 |
| 草稿安全 | 每次关键确认后保存；刷新恢复最近已保存状态；失败不覆盖旧数据 | 原型检查真实本地存储和备份恢复；生产检查数据库事务与失败重试 |

### 12 1 数据保留与运维

默认保留方案、已确认报价版本与必要审计 365 天；原始导入文件 90 天，失败生成的未采用素材 30 天。被有效报价引用的素材与导出文件随报价保留，不能因普通素材清理导致历史文件缺图。保留到期进入待清理清单，管理员可按企业实际义务延长；删除须先验证未被保留对象引用并记录范围，禁止一键硬删历史报价。合法请求或业务保留约束另行按实际处理，不在原型中假设通用法定年限。

原型提供带版本标识的完整本地工作区备份下载、导入校验与恢复；恢复前展示将替换的本原型范围并可先导出当前备份。重置只清理该原型专属存储键，不触及其他网页或项目。损坏备份、未知结构版本或缺少关键集合拒绝恢复，旧状态保持。浏览器清理数据或换设备不会自动同步，原型中必须清楚说明保存位置。

生产提供每日备份、受控恢复、任务异常列表、批次失败率、图片任务失败/待查数量、库存过期商品数量、PPT 生成耗时与失败率。负责人/运维可从关联 ID 定位批次、方案、模型任务和导出。日志只保留必要对象标识和错误摘要，不记录 API 密钥、下载签名、Cookie、原始密码或未脱敏客户联系方式。

### 12 2 图像任务用量与费用

每个任务记录来源模式、预计张数、实际结果数、采用张数、预估单价及币种、预计费用、实际账单状态和供应商任务 ID。业务指标同时计算“每次任务成本”与“每张被采用图的总成本”，重试和失败消耗进入分子，不只统计成功单次费用。没有真实账单时显示未知或待核对，不能写成 0 元真实成本。

生产默认关闭付费供应商，支出上限为 0；管理员完成供应商配置、授权、预算和测试后才能启用。启用配置至少含每次任务最大费用、每日/月度预算和预警阈值；达到预算 80% 提醒，预计会越过 100% 时不提交新任务。额度按待执行任务预留，最终按供应商已知结果结算；取消或超时不自动退款，待查费用保持保留，人工对账可补记并保留依据。配置额度不是本次会话采购或付费调用授权。

原型的默认 120 积分只表示流程示例额度，每张样例候选预留 1 积分，标签明确“演示积分，不发生收费”；外部已生成图片上传不消耗示例额度。生产配置值、密钥和账单不得放入浏览器持久化。向视觉供应商仅发送确认可用于 AI 处理的商品图片和必要视觉指令，不发送客户名称、联系人、采购预算、价格、库存或内部备注；不假设供应商天然不留存输入，实际条款在接入时核查。

| AC 18 对应 REQ 05及15 | SKU 不变但生成所用原图被纠错或禁用 | 关联草稿和采用图需复核；新交付受控，历史已确认报价版本不换图 |

### 13 2 AI 质量验证

生产视觉试点选 80 个内部可用商品，覆盖上衣、裤子、帽子和鞋，以及纯色、条纹、格纹、Logo、小字、深浅色、平铺与人台图。建立 40 个搭配任务，每种品类数量各 10 个；每任务首轮 3 张候选，最多重试 1 轮。保持供应商输入、输出尺寸和人工审核条件一致，明确四品类任务确实以四件指定商品为目标。原型样例图和外部上传流程不计入此真实生图样本。

记录四个指标：首轮可用率、允许重试后的任务可交付率、每张采用图总成本、从提交到采用的总耗时。分母分别明确为提交任务数和最终采用图片数；不能剔除失败任务来提高指标。

试点门槛为各品类组在最多两轮内至少 8 个任务取得业务可用图；被采用图中不允许关键款式、颜色或标识错误，四品类缺件不得通过。该小样本门槛支持受控试点，不代表所有商品的稳定成功率。上线后持续统计不同品类、纹理和标识的退回率，发现某一组低于门槛时停用该生成配置并保留原图交付途径，不把失败样本从分母删除。

搭配建议由销售逐项评判硬约束、风格和修改量，记录保留、替换及原因；不预设“AI 综合分达到 90 分”等缺乏业务含义的标准。金额、库存计算与商品标识应做确定性校验，不采用审美评分。

### 14 3 发布与停止条件

生产初次发布顺序为数据库/媒体存储及备份准备 → 角色与配置 → 商品导入和价格库存校验 → 图片来源及生成服务试点 → 报价与 PPT 冒烟 → 限定销售试用 → 扩大用户范围。涉及价格和库存的步骤回读当前行、来源批次、业务时间及 `row_version`，报价和文件步骤回读已确认报价版本；试用期间保留人工业务处理渠道，单纯刷新前端不能替代数据库迁移回滚。

出现以下任一事实立即停止扩大使用：报价金额不一致、价格/库存批次部分生效、客户或成本字段越权、已禁用素材外发、四件清单与采用图片明显不一致、任务费用越过配置上限、恢复演练无法恢复有效引用。停止受影响功能并保留审计，按上一可用程序版本和已校验数据备份恢复；历史报价不能因程序回滚被重算。修复后重跑对应 AC 和受影响链路，有新证据再恢复。操作负责人及实际发布/恢复命令在正式执行包填写，PRD 不虚构已经存在的生产服务器或负责人签字。
